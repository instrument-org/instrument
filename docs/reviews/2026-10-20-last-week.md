## Findings

### A. Placing a file onto an exFAT drive or a share fails outright on the Mac

- Status: fixed `fa726ae77`
- Where: [execute.ts:250](/apps/studio/src/electron-main/lib/finder-placing/execute.ts#L250), [exclusive-rename.ts:17](/apps/studio/src/electron-main/lib/exclusive-rename.ts#L17)
- What: placing tries `renamex_np` with `RENAME_EXCL` first and throws whatever errno it returns. On exFAT (most USB sticks) and some SMB and FUSE volumes that is `ENOTSUP`, so dragging or pasting a file there fails where the hard-link or check-then-rename path would have worked.

### B. The own-log cursor row can run ahead of the synced log after a power loss

- Status: fixed `78f74a7fd`
- Where: [chat-records.ts:958](/packages/workspace/src/lib/records/chat-records.ts#L958)
- What: the cursor row in `workspace.db` was upserted on every append, but the log was only fsynced at commit. A crash or power loss mid-turn left the log shorter than the row, so the next launch read the log as unrecognized and started a new one whose header claimed to continue from records that never reached disk.

### C. Topic and memory saves write through a link left at the temp file's name

- Status: fixed `c126a14c2`
- Where: [rewrite-file.ts:33](/packages/workspace/src/lib/rewrite-file.ts#L33)
- What: `rewriteFileSync` wrote its predictable temp name (`.~<name>.<pid>.tmp`) with the default `w` flag, following a symlink there, while `writeOwnFile` in the same commit already removed the name and opened with `wx`. Two worker threads in one process could also share that temp name.

### D. Every appended log line pays a synchronous SQLite upsert and a hash on the main thread

- Status: fixed `78f74a7fd`
- Where: [chat-records.ts:971](/packages/workspace/src/lib/records/chat-records.ts#L971)
- What: a streaming turn appends many part records per second, and each one blocked on a prepared-statement write and a sha256 of the last 4 KB, for a check that only matters when a log is opened. The fix for B keeps the cursor only at sync, which removes this cost too.

### E. Linux has no scheduling deny, so `systemd-run --user` could launch a job outside the sandbox

- Status: not a defect
- Where: [create-bash-env.ts:474](/packages/workspace/src/lib/create-bash-env.ts#L474)
- What: the claim was that only macOS gets the job-creation deny, leaving `systemd-run --user` and user timers open on Linux. Checked: the Linux sandbox blanks `/run/user/<uid>`, so there is no session bus to reach, and bubblewrap always sets no-new-privs, so the setuid `crontab` and `at` cannot write their spools.

### F. land.sh skips the contracts of a file the branch renamed and edited

- Status: fixed `11257efac`
- Where: [land.sh:56](/scripts/land.sh#L56)
- What: the `Commits-to:` scan used `--diff-filter=MD`, so a renamed-and-edited file (status R) was dropped and its contracts never printed, for exactly the restructuring most likely to break one.

### G. land.sh ends a wrapped contract at any prose line shaped like `Word: ...`

- Status: fixed `47b3804dc`
- Where: [land.sh:56](/scripts/land.sh#L56) (the continuation parser below it)
- What: a `Commits-to:` value wrapped onto further lines stops at the first continuation line that matches `^[\w-]+: `, so the printed contract is cut short.

### H. A Stop pressed as the turn ends can append two `stopped` records

- Status: fixed `6f59ce311`
- Where: [chats.ts:346](/packages/workspace/src/lib/chat/chats.ts#L346) (`markChatStopped`, read at :354)
- What: `markChatStopped` reads the newest stop and then appends as two async steps, so a concurrent save of the turn's own stop can interleave and both append a `stopped` record, contrary to the commit's contract that either order leaves one.

### I. The home-folder line of the computer-change note ends on a bare path

### J. The chat digest reads the transcript and the stop one after the other

- Status: not a defect
- Where: [chats.ts:593](/packages/workspace/src/lib/chat/chats.ts#L593)
- What: the claim was a second sequential read per chat across the chat list. Checked: digests are cached per session and both reads are served from memory, so the cost is negligible.

### K. A second stop by the same actor is never written

- Status: fixed `65451ddf3`
- Where: [chat-records.ts:423](/packages/workspace/src/lib/records/chat-records.ts#L423)
- What: `saveSession` wrote a `stopped` record only when the folded stop's actor differed. A later user message retires a stop but leaves it in the fold, so stopping the same task again wrote nothing and the task showed as finished rather than stopped.

### L. Stopping a tool call after it posted progress output leaves it unfinished in the records

- Status: fixed `0135bc29c`
- Where: [execute-tool-call.ts:66](/packages/workspace/src/machines/execute-tool-call.ts#L66), [agent.ts:181](/packages/workspace/src/machines/agent.ts#L181), [chat-records.ts:1511](/packages/workspace/src/lib/records/chat-records.ts#L1511)
- What: a preliminary output (`generate_image`, `web_search`) lives only in the turn's memory and reads as a finished call, so both the stop guard and the end-of-turn sweep skipped it. The stored part stayed `input-available` until the next launch's sweep, and `asCutOff` dropped the preliminary output, so the model lost the call; on the timeout path the next step read a partial frame as the result.

### M. A converted chat whose `chat.db` could not be moved aside is flagged half-written for good once used

- Status: fixed `91f43a784`
- Where: [convert-chat.ts:237](/packages/workspace/src/lib/records/convert/convert-chat.ts#L237), `sameShape` at [:686](/packages/workspace/src/lib/records/convert/convert-chat.ts#L686)
- What: "already converted" required the records to equal `chat.db` exactly. If the move aside failed (a Windows lock is enough) and the person then sent a message, every later launch got `half-written`, so `chat.db` never left, the format version never rose and the bell kept warning.

### N. A chat's folder never follows a rename made mid-turn or a title the model chose

- Status: fixed `90fcf47ae`
- Where: [chats.ts:216](/packages/workspace/src/rpc/routes/chats.ts#L216), [retitle.ts:158](/packages/workspace/src/lib/chat/retitle.ts#L158)
- What: the rename route skipped `followTitle` while the chat worked, expecting the turn's settle to catch up, but `renameChat` marks the title settled so `retitleOnSettle` returned before following, and the route that names a chat from its conversation never followed at all.
- Note: `73135f3d4` later fixed a duplicate "… 2" folder this fix exposed when the follow raced the turn-end CHAT.md write.

### O. A rename that only changes capitalization moves the folder to a numbered name on a Mac

- Status: fixed `24e455d24`
- Where: [chat-folder.ts:103](/packages/workspace/src/lib/chat-folders/chat-folder.ts#L103)
- What: `renameChatFolder` claims the new name with a mkdir first. On a case-insensitive disk that fails with EEXIST against the folder's own old name, so "dinner plans" to "Dinner plans" lands at `Chats/Dinner plans 2/`.

### P. On an AppImage, a restart with an update downloaded never comes back

- Status: fixed `78997e5bc`
- Where: [relaunch.ts:103](/apps/studio/src/electron-main/lib/relaunch.ts#L103)
- What: the restart shell runs the path in `$APPIMAGE`, but the teardown's quit runs electron-updater's install-on-quit, which deletes that file and moves the update to a new versioned name, so the shell's `exec` hits a missing file.

### Q. A settings take-in that fails partway strands sign-ins permanently

- Status: fixed `500555c5f`
- Where: [setup-environment.ts:160](/apps/studio/src/electron-main/setup-environment.ts#L160), early return at [machine-data-migration.ts:110](/apps/studio/src/electron-main/lib/machine-data-migration.ts#L110)
- What: `moveMachineData` ran even when the settings take-in had stopped partway, moved the half-filled `settings/` and raised the format. The next launch finished the take-in into `settings/`, which nothing reads, and the move returned early, so the ChatGPT account and app sign-ins opened empty.

### R. The launch cleanup removes an empty `Downloads` folder in a picked workspace

### S. Going up from a network share in Files opens a folder that doesn't exist

- Status: fixed `df8d41c93`

### T. A file opened into a Files tab is never selected in its folder on Windows

- Status: fixed `3874bb258`
- Where: [files-screen.tsx:335](/apps/studio/src/client/components/window/files-screen.tsx#L335)
- What: `besideSelect` tested whether the file started with the root plus `/`, which a backslash path never matches, so the folder beside the file opened with nothing selected.

### U. A `.bat` or `.cmd` in a folder with a space never runs on Windows, and `&` in an argument splits the command

- Status: fixed `75714f7d9`
- Where: [path-program.ts:257](/packages/workspace/src/lib/shell-commands/path-program.ts#L257)
- What: batch files ran as `cmd.exe /d /s /c <path> <args>` with no outer quotes, and `/s` strips the first and last quote, so `C:\Program Files\nodejs\yarn.cmd` failed with `'C:\Program' is not recognized`. Arguments were not escaped for cmd, so `&` started a second command.

### V. On Linux, a granted folder that links into a closed one breaks every native command in the chat

- Status: fixed `f2f4fcb6d`
- Where: [bwrap.ts:318](/packages/workspace/src/lib/native-sandbox/bwrap.ts#L318)
- What: `opensInside` compared rule paths as written while binds land at real paths, so `~/work` linking to `~/Documents/work` did not count as opening inside Documents. Documents was made read-only before the bind inside it, which bubblewrap cannot then create.

### W. `tar -xO` is refused when the current folder isn't writable

- Status: fixed `3e36db66c`
- Where: [tar-args.ts:119](/packages/workspace/src/lib/shell-commands/tar-args.ts#L119)
- What: `tarWrites` counted every extract as writing to its `-C` folders or `.`, even with `-O`/`--to-stdout`, so printing one member from a read-only grant failed with a permission error and an ask for write access it never needed.
