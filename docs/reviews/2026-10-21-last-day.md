## Findings

### A. Any tab, including one an agent drives, can put the window into macOS full screen

- Status: fixed `bf888508d`
- Where: [guest-session.ts:88-90](/apps/studio/src/electron-main/browser-view/guest-session.ts#L88-L90)
- What: the permission handler grants `fullscreen` to every guest with no check on who asked, and an agent's CDP click counts as a user gesture, so a background task clicking a video's full-screen button moves the window into a full-screen Space. Full screen is now granted only to a tab shown in a focused window that a person used within the last few seconds. Hand-testing the fix also found that a page leaving full screen on its own stayed stuck in it after the window's exit animation; `701523ea7` fixes that.

### B. A task forked after its chat rolled over skips an app's guide its model never saw

- Status: fixed `00ccdd297`
- Where: [last-told.ts:94-96](/packages/workspace/src/lib/last-told.ts#L94-L96), called from [app.ts:407](/packages/workspace/src/lib/shell-commands/app.ts#L407); the inherited cutoff is copied at [fork.ts:211-219](/packages/workspace/src/lib/capabilities/task/fork.ts#L211-L219)
- What: the "already shown" check only counts rollover marks tagged with the task's own session id, so a task inheriting the chat's cutoff searches the whole inherited history, finds the guide from before the rollover, and makes its first `app request` without the endpoint docs. The fix replaced the text scan with a structured hand-off record and one function for what a session's model is sent.

### C. A slow listing under `/Volumes` or iCloud Drive raises a false "Your Mac is asking" card

- Status: fixed `0e199fb8a`
- Where: [rules-fs.ts:287-308](/packages/workspace/src/lib/permissions/rules-fs.ts#L287-L308)
- What: "asking" was inferred from a one-second timer on a guarded listing, so a network share, a disk spinning up or a large iCloud folder raised the card, and when the listing finished the card settled as allowed and woke the agent with an answer nobody gave. Asking is now raised only while macOS's prompt window is on screen and a guarded look is still waiting, and a card whose look got in on its own closes quietly.

### D. Any EPERM, writes included, is reported as macOS refusing the folder

- Status: fixed `0e199fb8a`
- Where: [rules-fs.ts:318-330](/packages/workspace/src/lib/permissions/rules-fs.ts#L318-L330)
- What: a Finder-locked or root-owned file inside Documents marked all of Documents as refused by macOS and told the agent to ask for permission, and the ask answered "already allowed", a loop. A refusal now counts as macOS's only when a listing of the containing folder is refused too; otherwise the agent is told the file is locked or owned by another account.

### E. Seeded workspaces open with every chat's work folder empty

- Status: fixed `0a131596d`
- Where: [seed-workspace.ts:107](/packages/workspace/scripts/lib/seed-workspace.ts#L107)
- What: the seeder still writes work under the machine folder's `work/`, and the launch step that moved it to where the app reads work folders was removed in the range, so `studio-drive boot --workspace <fixture>` showed seeded chats with no files. The fix reseeded in the current layout, fixed the other drift a survey found (preferences location, a granted folder the file viewer refuses, a `legacy-tasks` fixture that imported nothing, forked tasks, boot reusing a stale instance), and added a guard test in `d96aa7a57` that reads every fixture back through the app's own readers.

### F. Skills discovery starts a new listing on every pass while a macOS prompt is unanswered

- Status: fixed `827b9e733`
- Where: [skills.ts:713-723](/packages/workspace/src/lib/skills.ts#L713-L723)
- What: each pass (a chat's context, the Settings list, `load_skill`, the end-of-turn link check) started another listing that held a file thread until the person answered, so about 60 passes would exhaust the pool the range had just enlarged and stall every file read. Each source's waiting listing is now shared until it settles.

### G. Waking a chat for one app's sign-in records every app as told

- Status: fixed `af41ba3cf`
- Where: [wake.ts:227-230](/packages/workspace/src/lib/chat/wake.ts#L227-L230)

### H. Only one chat can wait on an app's sign-in, and asking again disconnects a working app

- Status: fixed `6cfe4e75c`
- Where: [connect-app.ts:127-135](/packages/workspace/src/tools/connect-app.ts#L127-L135)
- What: the connection record had a single `askedIn`, so a second chat asking overwrote the first, which then waited forever; and `connect_app` never checked whether the app was already connected, so asking again flipped a working app to "needs sign-in" for every chat.

### I. Two concurrent token refreshes for one MCP sign-in can delete its stored tokens

- Status: fixed `690f0b260`
- Where: [oauth-provider.ts:114-120](/packages/workspace/src/lib/apps/mcp/oauth-provider.ts#L114-L120)
- What: with a server that rotates refresh tokens, the refresh that loses the race invalidates credentials and clears the tokens the winner just saved, so the person has to sign in again. Refreshes of the same token now share one request, and a provider clears only tokens it read or saved itself.

### J. `app test` shows the agent a local MCP server's stderr unredacted

### L. An APP.md that doesn't parse lets `app new` create a duplicate with the same id
