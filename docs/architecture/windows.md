# Windows

A person can have any number of app windows open on one workspace. They are full windows of the same app, each with a strip of tabs across its bar, and everything behind them (the workspace machine, the chats, the agents, the RPC routes) is one process they all talk to. Each window is its own `BrowserWindow` with its own renderer, Jotai store and React Query cache. For why they are separate renderers rather than one renderer drawing into several native windows, and why a chat can be open in two of them, see the [decision](../decisions/2026-11-03-windows-are-separate-renderers.md).

## Which window is which

[`windows/app-window.ts`](../../apps/studio/src/electron-main/windows/app-window.ts) keeps every open window by the id it keeps its state under: `app` for the first a workspace ever had, a fresh one for the rest. `getAppWindow()` is the window last in front, which is what the rest of the main process means by "the window"; `getAppWindows()` is all of them, front to back. A window's page learns nothing of its own id: main names a web contents as it makes it (`app-window-ids.ts`), and answers whatever that web contents asks with that window's own things.

## What belongs to a window, and what they share

| What | Where | Who sees it |
| --- | --- | --- |
| The strip of tabs, the tab groups it lists (`tab-group-list.v2`), the drafts and chats floating over it, whether the inbox is out | `window` kept file, `window/windows/<id>.json` | That window alone |
| Each tab group's sides, their tabs and the one up on each, which side has the keyboard, its pin, its share and when a window last stood on it | `groups` kept file, `window/groups.json`, one key per group (`tab-groups.v3/<group>`) | Every window, live |
| Where else the person left off (billing notes and the like) | `layout` kept file | Every window, live |
| How things are laid out (widths, views, zoom) | `view` kept file | Every window, live |
| Size and place, which windows are open and in what order, which can come back | `window/window-state.json` | Main |

A tab group is a record of its own, the same whichever window shows it, so its tabs are kept by the group and not by the window. A group exists only while some window lists it, open or closed to come back: main removes every group no window file lists, and every group with no tabs left, as a launch first reads the kept state and whenever a closed window is forgotten (`unlistedTabGroups`), and tells the open windows. A group moving to another window is listed there before the one it leaves lets go of it: Move to New Window waits for `window.openNew` to open the window on it, and main lists a whole group carried onto another window there before telling that window to take it (`sendGroupTabToWindow`). The tabs with no group and a site's group have lifetimes of their own. A kept file that is not an object of JSON is set aside beside itself (`<name>.corrupt-<ms>`) as it is read, and one that cannot be is never written over. The main process owns the tabs ([`tab-service.ts`](../../apps/studio/src/electron-main/stores/workspace/tab-service.ts)). A window changes none of them itself: it asks for one change by name, with plain data ([`tab-ops.ts`](../../apps/studio/src/client/components/window/tab-ops.ts)), and main applies each ask to the tabs as they are kept when it arrives, one after another whichever window sent it, through the tab model the windows draw by. So two windows that each change a group before hearing of the other both land, the second over the first's result. Main then tells every window the groups that changed, all of one change at once, and tells the window that asked which ask that answers. A window shows its own asks at once, laid over the tabs as main last told them, and lets each go as its answer comes, so it ends on what main made of it. What is true only of the asking window goes with the ask: the group it has on screen, and which tab it saw each opened from. A page drawn inside a window's surface is that window's alone, and main keeps it in that window's file. Anything that lets go of a group has to remember that other windows share it: a window drops a site's group only when it held that group itself and no tab in another window stands on it, closed windows that can come back included (`siteGroupsInOtherWindows`), and the sweep of empty drafts at startup keeps those floating in any window.

Tabs open and close in Chromium's order ([`tab-openers.ts`](../../apps/studio/src/client/components/window/tab-openers.ts)). A window remembers, until it loads again, which tab each of its tabs was opened from, and a strip is one side of one group. A link opened behind lands after the ones already opened from its tab. A tab closed in front gives way to what it opened, else what was opened from the same tab, else the tab it was opened from, else the right neighbor, else the left. The memory goes as the person switches to a tab of no relation or sends the tab to an address of their own. Back has a record of its own, which a switch leaves alone: from the start of a tab a link opened, Back closes the tab and returns to the one the link was in, while that one is on the same side and at the address it had. A bookmark opened in a new tab goes to the end of its side. A bookmark, an agent's opens, a drop and a reopen are linked to nothing.

A group made from another (⌘N, Duplicate, Open in New Tab Group) goes back to that one as it closes, until the person goes on to a third ([`group-return.ts`](../../apps/studio/src/client/components/window/group-return.ts)). Open in New Tab Group puts the group under the one it was asked from, or at the top from a pinned one; ⌘N puts it at the top.

What a window has drawn of a group is the window's alone. A screen (a file, a folder, a built-in page) stays drawn once another tab or another group comes up, invisible on the side of the group it was up on, so it comes back as it was left: scrolled and edited where it was, a film still playing ([`kept-screens.ts`](../../apps/studio/src/client/components/window/kept-screens.ts)). The group's sides stay drawn with it, as a group behind the one up, with no keyboard, no page and nothing a chord or a drag can reach. Ten screens are kept behind the ones up and the one longest out of sight is let go first, to be drawn afresh where it was scrolled ([`kept-scrolls.tsx`](../../apps/studio/src/client/components/window/kept-scrolls.tsx)). A chat is not kept: it opens at its end each time. A page needs none of this, since its guest is the browser pool's ([in-app-browser.md](in-app-browser.md)). A screen moved to the other side, or to another group, is drawn afresh there.

A group a window closes goes on that window's closed list (`recentlyClosed` in its `window` kept file, the hundred newest closes of a tab, a side or a whole group), which is where it comes back from: Shift+Cmd+T and History. Picking a chat on the Chats page, in the bookmarks bar's Chats menu or in the command menu (`useShowChatGroup` in [`chat-group.ts`](../../apps/studio/src/client/components/window/chat-group.ts)) brings its group up, and a group holding only a new tab or the Chats page gives its place in the list to what was picked (`showGroup` and `reopenClosed` on the window's shell).

## Asking one window

Almost everything main publishes for the windows is read by all of them (`liveRead` routes re-read for themselves), and that is right for state. A request to do something is not: `window.command` names a web contents, published through `commandWindow`, and the route hands each window only what names it. A chord goes to the window it was pressed in (`bindAppWindowChords`), and a menu row to the focused one.

What something outside the app asks for goes to the window that already has it (`appWindowShowing`, and `windowWithGroupTabShowing` for a tab in any group a window lists, read from what each window keeps): a notification, a link to a chat, a file, a folder or a screen, or a file handed over from the Finder brings that window, that group and that tab forward and lights the tab, and otherwise it opens as a new tab group of the window in front. Several things handed over at once always open as one new group ([`deep-links.md`](deep-links.md#a-new-tab-group)).

A tab of a window's own is the person's to keep as many of as they like: `open` on the window's tabs always opens another, even where a tab already shows the same file, folder, chat or screen, and `go` walks the tab up there. A rail place sends the tab up there. Beside a chat it is the other way: the chat's own tabs are looked in (`tabShowingIn`), by what a tab shows rather than its exact address (`tabIdentityOf` in [`shared/tab-identity.ts`](../../apps/studio/src/shared/tab-identity.ts): a file by its path, a folder in Files, a chat, a draft, a task, an app, a screen, however far the tab has walked within it), so a reply's file comes up in the chat's pane where it is already open there rather than piling up beside the conversation. When main asks a window for a tab another window wants (`showTab`), the window brings up the one showing it and walks it to what was asked when that asks more (`asksMoreThan`).

What an agent asks of a chat's tabs must be answered exactly once, or a page it opens would open per window, so each ask names one window as it goes out (`appWindowForChat`): of the windows whose page can hear it, the one with the chat's group up, else one that lists it behind (`windowListingGroup`), else the one in front. Which of a chat's tabs its agent works from is one rule the windows and main both read (`workingTabOf` in [`shared/working-tab.ts`](../../apps/studio/src/shared/working-tab.ts)): of the chat's tabs in groups an open window lists, the one last sent from, else the first; a chat with none there opens nothing, since an agent never makes a tab group. A blank page an agent makes for itself goes to the same window. The workspace package asks through `WorkspaceConfig.windowForChat`, which a host with one window leaves out.

## Opening something in a new window

Wherever something opens in a new tab, it opens in a new window too: a menu that offers Open in New Tab offers Open in New Window under it, and a click with Shift asks for a window where a click with the command key asks for a tab, as a browser built on Chromium has it. Shift with the command key is a tab. Shift reads this way only on a link, something a plain click opens; on a row a plain click selects (Files, the chat list, a table) it extends the selection. Every one of them is `newWindow` on the window's openers (`OpenOptions`), which open the thing as the first tab of a window opened through `window.openNew` (`openInNewWindow`); several things, as a selection in Files, are tabs of one window. A page opens on its own there, as a site, whichever chat it was opened from. Inside a page, Chromium reports a Shift-click as a `new-window` open with no features and no name, which no page's popup is, so it opens a window of the app's own (`newWindowOpenOf`) and a sign-in popup still opens as one. The Dock's menu on macOS and the taskbar button's on Windows (`offerNewWindowTask`) have New Window. A tab's menu is one list of rows in the window's strip and a chat's pane (`TabMenuItems`): the window's moves the tab itself, and a pane's opens a copy in the window's own strip (Open in Window Tab Bar) or a new window, since "new tab" there means a tab in that pane, as a link's Open Link in New Tab does.

## Moving a tab

A drag takes one of two paths, decided by what was grabbed ([`drag/types.ts`](../../apps/studio/src/client/components/window/drag/types.ts)). A piece of the window (a tab, a whole group by its sidebar row, a bookmark of the bar) is held by the pointer (`WindowHeld`, `pressToHold` in [`session.ts`](../../apps/studio/src/client/components/window/drag/session.ts)): it moves where it lands, draws its own picture at the pointer, and leaves the window only as main carries a tab or a group, below. Content (a file or folder from Files, a file card, the address field, a link in a reply, a chip, a row of the Chats list) is held by the system's drag (`useContentDrag` in [`content-drag.ts`](../../apps/studio/src/client/components/window/drag/content-drag.ts)): a file as the file (`webContents.startDrag`), anything else as a link, so it can leave the app. Inside the window that content takes the same way in as files from the Finder or a link from another browser (`useSystemDrags`), and every target answers both the same. Over a side's page one rule says what takes a drop, in order (`pageLandingOf` in [`accepts.ts`](../../apps/studio/src/client/components/window/drag/accepts.ts)): a split target at a lone side's end; for content, whatever in the page takes it itself (a composer, a field for a link, a web page, a folder in Files); a new tab nobody has written in; then the side. Where content goes to the page, the window neither cancels the drag nor draws a landing, and over a web page it never hears the drag at all. A pointer drag ends the moment a move arrives with the button up, since the release went somewhere the window never heard, so nothing it held stays on the pointer and pages take the pointer back. A side's strip takes a piece of the window among its tabs (`useStripTarget`), and a side of one tab, which draws no strip, takes it at the row at the top of its page, where the strip comes up to land it in. A whole group lands as its tabs wherever a tab does, among a side's tabs or at a split target, whether it is held in this window or carried from another: a window dragged back onto one arrives as its group, and the window it lands in moves the group's tabs where they were let go (`receiveWhole`).

A tab moves one way, whether a drag or a menu asks. A tab's menu moves it with one row, as a browser's does: Move Tab to New Window with no other window open, and Move Tab to Another Window, which lists New Window and the windows, with one. Either is a drag let go straight away (`moveTabNow` in [`tab-carry.ts`](../../apps/studio/src/electron-main/windows/tab-carry.ts)): the same phases, the same choice of what goes and who reopens, and the window takes the outcome the same way (`settleTabMove`). So a page keeps its state from a menu exactly as it does from a drag. The window stands a step off where it was, since there is no pointer to say where.

Merge All Windows and opening a link in a new window are the two that open a tab afresh: a merge has more than one tab to bring and only one window can keep its renderer, and a link has nothing to keep. A merge is main's alone (`mergeAllWindows`): it reads each window's tabs from what the window keeps and writes them into what the window in front keeps, refusing a front window whose page is not listening yet, which would miss them, hands over the pages those windows hold and their floats, and closes them with nothing to come back to (`closeEmptiedWindow`). A link opens through `window.openNew`, which writes the tab into the kept state of the window it then opens, which reads it as it loads.

Tearing a tab off ([`tab-carry.ts`](../../apps/studio/src/electron-main/windows/tab-carry.ts), with its pure rules in [`tab-carry-rules.ts`](../../apps/studio/src/electron-main/windows/tab-carry-rules.ts), and `useTabCarry` in the renderer) moves nothing, windows and pages alike, until the release, so going back to the row or Escape has nothing to undo. The renderer keeps the drag. Pages are out of the pointer's way for the drag (`data-tab-held`), because a page runs in a process of its own and otherwise takes a pointer that crosses it, the release included: pointer capture does not reliably hold it back, and a window that never hears the release stays on the pointer. Main keeps one phase for the drag (`CarryPhase`): on its row (`row`), free of every strip (`free`), or held in another window's (`docked`). Everything the drag does is an effect of going into or out of one, or of following the pointer within one, and main reads the cursor itself to follow it.

A tab in the hand is drawn at the pointer and placed by where its left edge is (`heldAt`, `onPlace`), the same way whether its strip is its own or another window's: the strip's own reorder measures from the press, and the row closing up and opening again moves a tab out from under those measures. Nothing else in the window answers to the pointer while it holds a tab, hovering included.

Off its row a tab leaves its strip as if it had gone: the strip closes up with its own motion (`carriedKey`), the tab beside it comes up, and a small picture of the tab's page as it stands, the whole window for a whole group, goes with the pointer (`openTabPicture` in [`tab-picture.ts`](../../apps/studio/src/electron-main/windows/tab-picture.ts)), a window of its own for the length of the drag that takes neither focus nor the pointer. All of that happens in the one renderer, with the tab still among its tabs, so back on the row or Escape it simply returns.

On the release whichever side has less to lose is the one that opens afresh (`whatGoes`), and what opens stands across the pointer with the pointer just under its bar, or as near that as keeps all of it on the screen (`boundsAtRelease`). By default that is the tab: it opens in a spare window (`keepSpareReady`, `takeSpareWindow`), an ordinary app window kept booted and hidden, on none of the window lists, given it through the kept state the way a window coming back from a launch is, and the window it came from stays as it is, with every page in it. A tab whose page has been used cannot do that, since a page cannot change renderers and keep what it holds (`isPageUsed`: a person's click, key or scroll, or an agent's input, where being sent to an address leaves nothing to lose). So the pressed window leaves with it, renderer and all, and the page, the words typed into it, its selection and scrolling are never touched. A press on any tab takes the keyboard out of a page before the drag begins, so Escape reaches the window, and a click in the page puts it back. The spare takes the other tabs and the floats in its place, as the window stood. It comes up over the pressed window first, and the pressed window is told what it holds from there out of sight (`kind: "reshaping"`, which also keeps its strip from animating) and goes to the pointer once it has drawn, so that neither window is seen changing. A window wholly covered by an opaque one counts as out of sight on macOS and stops drawing, so the spare is a shade short of opaque for those few frames. From the release the picture grows from the pointer to fill where that window is coming up (`growTo`), while that window draws; a whole window's picture puts on that window's tab bar once it has drawn it (`wearBarOf`). The picture goes once the window is up. A tab pressed while a release is being carried out stays on its row for that drag, since a window is still being told what it holds.

The spare is given what it will hold as the tab leaves its row, and until the release it is told it is beneath (`kind: "beneath"`), so a chat up in it does not count as read. Where a window can be kept unseen it is on screen at no opacity by then, so that it has drawn when it is wanted. The tab that comes up in the spare takes its page on the release (`neighborPages`). Any other page the spare shows it asks for only once it has been adopted (`adoptSpareWindow`, `canTake`), and a drag undone has moved nothing.

A full-screen window stays, and so does one in a session that cannot place a window: the tab goes to the spare whatever its page holds. Out of a full-screen window the picture and the spare float in that window's Space, unable to go full screen themselves, since macOS would otherwise switch Spaces mid-drag, and on the release the spare goes full screen as the window it came from stands. A maximized window that leaves does so at its own size, and the window left behind fills the work area in its place. On Linux a window of ours under the pointer takes the press's release, even one that takes no mouse events, so there the picture hangs just clear of the point of the pointer, where elsewhere it is centered on it. A window there has no opacity to keep it out of sight until it is wanted (one given an opacity stays a few percent see-through, so the drag gives it none), so the spare comes up only on the release, and a window manager there keeps a window a program moves on screen, so a window following the pointer stops at the screen's edge. A Wayland session goes further, telling a window nothing of where it is and letting it place no window, so nothing follows the pointer, the tab stays showing in its strip, and Move Tab to Another Window is the way into another window's strip. GNOME on X11 says a window opening without focus over the focused one "is ready", which a pressed window leaving costs that notice. At a fractional scale on Windows a move that names only a place grows a window by a pixel each time, so whatever follows the pointer names its size on every step.

Main answers which strip the point is over (`phaseAt`), since only it can see every window. Windows are tested front to back from the order they were last focused, because Electron cannot read the OS's stacking order, and a window covering a strip takes the release. A tab held in a strip stays in it for 24px past its edges (`DOCKED_REACH_PX`), so that it does not come straight back out for a pointer that barely moved. Over another window's strip that window draws the tab among its own at the pointer (`kind: "incoming"`), its tabs making way, without loading any of it, and says where the tab stands (`placeTabCarry`), which is where it lands. Let go there, whichever side has less to lose is the one that reopens (`landsBy`): the tab goes to that window as `receiveTab`, and the window stays as it is, unless the tab has a used page, in which case the pressed window takes on the other's tabs in its place, and that window closes. It comes forward only once its strip holds just those tabs (`drawnHolding`), drawing the held tab where the strip it replaces has it (`held`), so the two read as one until the tab settles. With used pages on both sides the tab in hand wins, and the other page reloads when it is next looked at. A window's only tab leaves nothing behind and needs no spare window or picture: its window follows the pointer, and over another strip it goes unseen, where a window can, for that strip to show. Another window takes the tab only where the person could see it: the pressed window comes first in the test and takes nothing over what it has covered all through the drag (`hidden`), which is where it stood at the press less what it has uncovered since by following the pointer. A window moved a little by its only tab does not jump into the window it lay over, and once it has moved off part of that window, that part takes the tab. The press that starts a drag has to reach the page, so app windows set `acceptFirstMouse`: without it the first press on a window behind another only brings it forward, and over the bar it drags the window. An instance kept off screen never shows a window, has no picture, and starts no spare until a drag asks for one, so a drag driven over CDP exercises the same path.

## A page is in one window

A page tab belongs to a group every window can see, but its guest is a `<webview>` in one renderer, and Electron cannot move one between renderers. So a page is in the window that showed it last. [`in-app-browser.md`](in-app-browser.md#a-page-is-in-one-window-at-a-time) has what that does to a guest. A page drawn inside a surface (a file's page in its viewer, the page under Quick Look) is not one of those: its tab is kept in the `window` file of the window drawing it (`fileOfTabGroup`), since the surface makes it as it comes and closes it as it goes, and each window showing that tab draws a page of its own. Such a page never changes windows, but a person having used it keeps the window with the tab like any other (`hostedPages`).

## Coming back

A launch brings back every window that was open, each where it was with its tabs, the one last in front on top (`restoreAppWindows`). A quit leaves those records alone, so closing the app is what keeps them. Closing a window while the app runs moves it to what can come back: File › Reopen Closed Window, or Shift+Cmd+T once no closed tab is left to reopen. The last ten are kept; past that a window's file and place go. With every window closed on macOS, the Dock icon brings back the one closed last.

On macOS the last window on screen is put away rather than closed (`holdPutAway` in [`on-screen.ts`](../../apps/studio/src/electron-main/windows/on-screen.ts)): hidden with its page still running, so the chats at work in it go on, the pages they drive included, with no window on screen and nothing asked. It stays among the open windows, so a quit and a launch bring it back like any other. It comes back as it was for the Dock icon and for anything else a person asks of the app (`showPutAwayWindows`): a new window, a link from outside, a notification's chat, a sign-in that finished in the browser. So a window is put away only while none is on screen, and there is never more than one. A prompt about the whole app, a quit's above all, hangs from no window while the one in front is put away (`getPromptWindow`). A run that keeps its windows off screen holds a closed one as it holds them all, for the Dock icon alone.

No window opens before a launch restores them. Electron hands things over from the main module's first line, well before boot gets that far: the link or file the app was launched with, a second launch (the taskbar's New Window task among them), the Dock icon. Every one goes through the launch ([`windows/launch.ts`](../../apps/studio/src/electron-main/windows/launch.ts)), which is booting until boot calls `openWindows`, open after, or refused for a workspace that will not open. While booting, what a request asks to see waits for the window boot opens, and the window it would bring forward or open is the one boot restores, which comes up taking the focus once a person asked for the app even on a launch meant to come back as it was left. Every way to a new window (New Window, Reopen Closed Window, a quit's reveal, the Dock) checks `windowsMayOpen`, and `createAppWindow` reports one that opens anyway. A window opened early would come up beside the restored ones and before its page could reach the main process; the main process also listens for a page's RPC port from the moment its module loads (`rpc/initialize.ts`), so a page that gets there first waits rather than losing it.

Closing a window quits the app only where it is the last one on Windows or Linux (`quitsWithLastWindow`), and asks about running work only then. While setup is up, only the window it draws over is open; the rest come back as it goes down, and New Window does nothing until then.

What a window puts off (a deletion while its toast offers Undo, typing not yet written into its draft) is a job in `client/lib/before-leaving.ts`, run on its own time or when the window goes, whichever is first. A reload or a closed window runs them on `beforeunload`. A quit ends in `app.exit`, which unloads no page, so its teardown starts by asking every app window to run them and waits for each to answer, up to two seconds (`windows/finish-before-leaving.ts`), before anything closes.
