# Agent sandbox

`instrument` is an Electron desktop app where users chat with an AI agent that works inside the chat's work folder and can start background tasks, each a session of the same chat working in the same folder. The agent runs as ordinary code in the Studio main process on the user's machine, in no VM or container. What holds it to the person's wishes is one set of rules, Settings › Permissions, applied at every layer: in the process for the shell's own commands and the file tools, and by the operating system for the programs it starts, through Seatbelt on macOS, bubblewrap on Linux and MXC on Windows. Where the system offers no such wrapper (a Windows build MXC's canary launch fails on, an AppImage, a host process already sandboxed), the programs it starts follow the rules only as far as Instrument can read their command lines, and Settings says so.

For why the first version was userland only, see the [decision record](../decisions/2026-07-15-userland-agent-sandbox.md). For why the agent now works at real paths and what that replaced, see [the decision](../decisions/2026-10-11-the-agent-works-at-real-paths.md).

## Tools and where they live

The one agent (`packages/workspace/src/agents/instrument.ts`), which runs a chat and each of its tasks, gets a fixed set of tools from `packages/workspace/src/tools/`: `EditFile`, `ReadFile`, `WriteFile`, `BashTool`, `WebSearch`, `WebFetch`, `GenerateImage`, `LoadSkill`, plus `Choose`, `ConnectApp` and `AskPermission` for asking the user. `ask_permission` is the only way a permission card goes up: the agent asks for a folder or a Mac app, the server decides which folder the card names, and the turn ends on the call (`shouldContinueAfterHandingOff`). Running into a closed folder or app raises nothing; the refusal names what to ask for. File discovery and search are not tools: they live in the shell, on the real `rg` binary (see the [decision record](../decisions/2026-07-28-real-ripgrep-in-the-sandbox.md)). Each tool's `execute` runs as host Node.js code; the file tools read and write through the shell's own filesystem, so the rules hold them where they hold the shell (layer 1 below), not by the runtime.

What differs between a chat and a task is the shell, not the tools. A chat's shell adds `instrument task` and reaches the workspace's `Apps/` folder; a task's `instrument memory` only lists and shows, its `instrument window` only lists and reads, and each refusal says what the task does instead (`create-bash-env.ts`), and the task's own turn tells it that no question or app sign-in reaches the user from there, while a folder or Mac app it needs is still asked for with `ask_permission`, whose card's answer wakes the task (`from-chat-model-text.ts`).

## What decides reach

The rules live in `packages/workspace/src/lib/permissions/`. Every layer below asks the same question of a host path: may the agent read it, may it change it.

- **The rules** (`rules.ts`) are a list of `{ path, level, source }`. A level is Allowed, Ask first or Not allowed, which are the three a person sets, or `readOnly` (readable, never changeable), which the app sets for its own folders. `reachOf` finds the deepest rule holding a path, by the path the rule names or where that path really is, each at its own depth (a rule named deep through a link holds what it leads to only as deep as that really is), and that rule decides; at an equal depth the rule closing the app's own data outranks every other, the app's own rules outrank a chat's grant, which outranks a folder rule, which outranks a built-in place, and a rule naming one hidden entry of a folder outranks the rule for all of them (`ruleRank`, which both native profiles order by too). A path no rule holds is readable and asks before it changes, and so is a path in the home folder whose deepest rule is an allow above the home, since the native profiles close the home to changes beneath every rule above it. "Use folders without asking" turns every Ask first into a yes but the sign-in folders' (below), which hold sign-ins rather than work; nothing turns a Not allowed into anything else. Matching is without case on macOS and Windows, and a path on the Mac's Data volume (`/System/Volumes/Data/Users/...`, joined to `/` by firmlinks that `realpath` leaves alone) is matched as the rest of the system spells it (`withoutDataVolume`), as is a name ending in dots or spaces on Windows, which Windows opens without them (`withoutTrailingDots`); Seatbelt matches the path the kernel resolved, so it needs no such step.
- **Built-in places** (`places.ts`) are the folders every computer starts in: the output folder (always allowed), Desktop, Documents, Downloads, iCloud Drive and other drives, other apps' files (`~/Library` on macOS, `~/AppData` on Windows, `~/.config` and `~/.local/share` on Linux), on macOS the Photos library and the Music and TV libraries (`~/Music/Music`, `~/Music/iTunes`, `~/Movies/TV`), and the passwords place. On macOS and Windows the app-files place is listed while it asks first: programs and the shell's own `ls`, `find` and globbing see the names, sizes and dates in it (`listed` rules, `reachOf`'s `list`), and opening or changing a file there names that one app's folder to ask for, the first below the folders that hold a folder per app (`~/Library/Application Support/Code`, `~/Library/Preferences`, `AppData\Roaming\Discord`; `appFolderParents`). The apps' containers on macOS (`~/Library/Containers`, `~/Library/Group Containers`) ask without being listed, since macOS asks the person before a program looks into another app's container. What stays closed inside the place (sign-in places, startup places, Windows' activity folders, the app's own data) is not listed either. Linux lists nothing there, since bubblewrap cannot show a folder's names without what is in it. Allowed opens the place whole and Not allowed closes it and its names. Its caches (`~/Library/Caches` and `~/.cache` on macOS, `~/.cache` on Linux) are open while it asks first and closed only when it is Not allowed (`openUnlessClosed`), but for the browsers' caches, which hold the pages the person visited and are closed with the profiles, and the updater's downloads, which are the app's own data. A tool that keeps code in the caches and runs it later outside the sandbox (Playwright's browsers, Go's builds) is one of the person's programs, which a chat can leave things for (threat model). macOS puts up its own dialog before any program reads those libraries, and a native walk over the home folder waits on it; as places they are refused by the sandbox first, which is checked before macOS's question, and each is asked for on its own. Each starts at Ask first except the output folder. The passwords place holds two lists: the folders where command-line tools keep sign-ins (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.azure`, `~/.config/gcloud`, `~/.kube`, `~/.docker/config.json`, `~/.netrc`, `~/.git-credentials`, `~/.config/gh`, `~/.config/op`, `~/.password-store`, `~/.m2/settings.xml`, `~/.gradle/gradle.properties`, `~/.pypirc`, `~/.cargo/credentials.toml`, `~/.gem/credentials`, `~/.terraform.d/credentials.tfrc.json`), which take the place's level and so ask first by default, and the places that hold every sign-in at once (the Keychain, cookies, browser profiles and caches, 1Password's data), which stay Not allowed unless the place is set to Allowed. A sign-in folder is asked for whole, a file such as `~/.netrc` by itself, whatever path in it the agent ran into, and a grant of `~/.ssh` also passes the app's `SSH_AUTH_SOCK` to native commands and opens the ssh-agent's socket in the Seatbelt profile, which refuses connecting to it otherwise, and binds it back under bubblewrap, which otherwise covers it. The person changes a place, adds a rule for a folder of their own, and flips the switch above in Settings › Permissions (`rpc/routes/permissions.ts`, stored in `permissions.json` in the workspace's machine folder, since its paths are this computer's). The page ends with what every chat reaches whatever the list says (the view's `alwaysOpen`: the work folders, the chats' records read-only, the caches the app-files place opens, on Windows `AppData\Local\Programs` read-only) and what programs can see listed without asking.
- **A chat's grants** are Allowed rules that win at an equal depth (`chat-rules.ts`). A grant comes from an allow on the card the agent puts up with `ask_permission` (`rpc/routes/permissions.ts`), or from attaching a folder to a message with the folder picker or by dropping it in, which says where the work is and grants it when the message is sent (`new-message.ts`; a folder in a chip over the words, picked by name or shown by a screen in view, is a hint only, which the agent asks for); "Always allow" on the card also writes a folder rule, so every chat has it. A chat also holds, without a grant, its topic's folders: the ones granted under the topic on this computer, in `permissions.json` under `topics` (`permissions/topic-folders.ts`), never read from its `TOPIC.md`, which the agent can write where the workspace is the person's own folder. A grant is this computer's alone, so a chat continued on another computer reaches none of the first one's grants there and asks for what it needs. The agent hears of a grant on the next message (`data-folderChanges`, `lib/folder-changes.ts`), and of one taken back only where this computer had granted it: what it was told records which computer's grant each folder was (`ToldFolders`), and a folder told on another computer is simply not granted here.
- **The app's own folders** are rules too, ranked above everything the person sets (`layoutRules` in `workspace-fs-layout.ts`). The app's own data is closed (`appData` rules, Not allowed): this computer's folder (`WorkspaceConfig.userDataDir`, Electron's userData: the app's Chromium profile, the registry of workspaces, the runtime folder, each workspace's machine folder with its keys, browser profiles and folder rules), the workspace's `.instrument/`, `~/.instrument/`, every workspace's chats' work folders, and the updater's downloads in the caches (`appUpdateCaches`: electron-updater's folder and on macOS ShipIt's, which an install outside every sandbox reads, as root through dpkg on Linux). The workspace's folder around that is the person's: once they picked it, it is the output folder, and it follows their rules and the output folder's like any folder. A folder holding this computer's folder whole (the home folder) mounts read-only as a whole, and one inside the app's own data too (`effectiveFolderAccess`); a folder holding only a workspace's `.instrument/` carries its grant. Inside the app's own data only the app's own rules open anything: every chat's work folder, in every workspace (`~/.instrument/work/`), Allowed, since chats share their work as they share everything of the person's; every chat's records (`.instrument/chats/`), `readOnly`, so one chat can search and read what was said and done in another; in the chat's record folder (`.instrument/chats/<id>/`) `attachments/`, `readOnly`, and `handoff-notes.md`, Allowed; the skills (read-only for what the app ships and what other agents left, Allowed for the workspace's own `Skills/` at its top level); for a chat the workspace's `Apps/` folder, Allowed; the runtime folder's `caches/` and `config/`, Allowed; and its `python/`, `skills/`, `environments/`, `preload/` and `bin/`, `readOnly`. Its `build/` stays closed: what the app builds or loads from it every chat then runs, so no chat may write it, and only a build the app runs for a chat reaches it (below). Everything else there, `workspace.json`, `preferences.json`, the keys and the browser data, is refused plainly, naming nothing to ask for, with a note saying it is the app's own data and that the chat's work folder and what the person sent stay open (what the person sent sits inside that data, and a note that only closes the way in talks the agent out of reading it): a person's rule inside it, by its path or by where that path leads, is dropped (`layoutRules`), one on a folder holding it (a card's yes to `~/Library/Application Support` or the home folder, Settings allowing `/`, folders used without asking) is outranked by the deeper rule that closes it, and a card for something beside it never names a folder that holds it (`folderToAskFor` names the folder below it, and `ruleRefusal` names none where that cannot be done, `holdsAppData`). The folders above an open one answer a `cd` and a `stat` but are not listed. The same rules reach the Seatbelt and bubblewrap profiles, so a program the agent starts is refused there too. A chat's records are not in the folder it works in, so a program the agent starts there finds no record of the chat beside its files. The workspace's own `Skills/` is open for every chat to change, by design: what one chat leaves there loads, runs and has its dependencies built by the app in every chat after it, so a chat steered by what it read can leave code there for the others. Attributing each change to the chat that made it (`setup-changes.ts`, below) is all that stands between such a change and the next chat that loads the skill.
- **What the agent is told** when a rule stops it is spelled out with the path, quoted as a JSON string so a file's name reads as a name rather than as words of the note: a Not allowed place says it is closed in Settings and not to look for another way in; an Ask first place names the folder to ask for with `ask_permission` (`askableFolder` over `folderToAskFor`: one level below the place, so the person sees a folder they made rather than all of Documents); a read-only folder says to copy out what it needs. One function, `ruleRefusal` (`permissions/rules-fs.ts`), says all of this for the shell's own commands, the file tools, the commands that check their operands, and a path outside every folder the shell reaches, and `ask_permission` decides the folder the same way, so a path is asked for alike whichever of them met it. The person's answer wakes the agent, and once they allow the folder every session of the chat reaches it. On macOS an Allow first looks inside the folder from the app, which is when the system's own Desktop or Documents prompt comes up; if macOS refuses, the card stays up, `macos-refused`, offering the system's folder panel and System Settings until a retry gets in.

## The layout

`packages/workspace/src/lib/workspace-fs-layout.ts` builds what a chat's shell reaches, shared by the file tools, the shell, `rg`, `du`, `git`, and the agent's browser. Every folder is at its real path on the disk, spelled as the shell spells it (`shellPath`): the same on macOS and Linux, and `/c/Users/sam` for `C:\Users\sam` on Windows, as Git Bash does, converted back at the edge (`hostPathOf`). Paths shown to the person stay in the host's form.

- **The chat's work folder** is the shell's working directory and the file tools' base for a relative path, for the chat and for every task it starts alike (`workDir` in `lib/work-dir.ts`, `~/.instrument/work/<workspace>/<id>/`). It is made by the chat's first command, and again, empty, by a later one once it was removed, which the app does when the chat and its tasks come to rest with nothing in it (`reapWorkDir`: no session of the chat running and nothing it left running in the background, and only a `.DS_Store` counts as nothing). It is always allowed, and nothing is scaffolded into it. The shell names the folders the agent works with (`FOLDER_VARIABLES`): `INSTRUMENT_WORK` this folder, `INSTRUMENT_OUTPUT` the output folder, `INSTRUMENT_SKILL_DIR` the folder of the skill the session loaded last (`lastLoadedSkillDir`), `INSTRUMENT_APPS` the workspace's apps, `INSTRUMENT_WORKSPACE_SKILLS` its own writable skills and `INSTRUMENT_CHATS` every chat's records (none for the window), which every native command gets too, in the host's spelling (`resolveCommandContext`).
- **Every chat's records** (`.instrument/chats/`, `layout.chats`), read-only, mounted so the record folder's own rules can open what they open inside it.
- **The chat's record folder** (`.instrument/chats/<id>/`, `layout.record`), for its `attachments/`, which the agent reads, and its `handoff-notes.md`, which it writes. The rest of it is read-only, like every other chat's records. The window, which keeps no such records, has none in its layout.
- **The folders the chat reaches** (`folderReach` in `lib/chat/folder-reach.ts`): the home folder and the output folder always, the folders granted in the chat, the folders of the topic it is filed under, and the folders Settings › Permissions allows everywhere, the folders of a place of work set to Allowed among them (Desktop, Documents, Downloads, iCloud Drive, the drives). The home folder is reachable so the agent can look around and then ask for the right folder; the built-in places in it ask before the agent reads them, and changing anything outside a grant asks first.
- **The skill sources**, each at its own directory. The two bundled sources share the prepared copy of the skills in the runtime folder's `skills/`, since the app bundle is signed and replaced wholesale by the updater. Only the workspace's own `Skills/` is writable, created when missing, and wrapped in `setupTrackingFs` so edits to a skill are attributed; a native program's edits are read off the folder around the call instead (`setup-snapshot.ts`). `load_skill` copies nothing: it names the folder the skill is read and its scripts run from, and the app builds the dependencies of what it ships and of the workspace's own skills in the runtime folder's `environments/`, read-only to every chat (`skill-environments.ts`; Python and pnpm below). See the [decision record](../decisions/2026-07-20-skills-as-a-mount-not-a-tool.md).
- **The workspace's `Apps/` folder**, writable, for a chat only; a task reaches its apps through `instrument app`.
- **The system's temp folders** (`/tmp`, `/var/tmp`, and `os.tmpdir()`, at both their spelled and real paths), writable, each held by a system allow rule so the native profiles open them as well; a deeper rule (a workspace or a planted home inside one) still decides there.
- **`/dev`**, a small in-memory stub (`null`, `zero`, `stdin`, `stdout`, `stderr` as plain writable files, rebuilt per call) so `cmd > /dev/null` resolves instead of dying with EROFS.
- **Everything else** is a read-only base (`read-only-base-fs.ts`) that reads the disk where the rules allow reading (the system's own folders and anything no rule holds; empty on Windows), held to the rules at a path and where it really leads, and walked against the home folder's budget. A write outside the folders (`/opt/x`) fails with EROFS and says where files can go, instead of succeeding and evaporating when the call ends.

A folder inside one already reached is reached through the outer mount, because just-bash's `MountableFs` refuses a mount inside another (`mountRoots`). In practice the home folder holds nearly everything: the chat's work folder, the workspace, the skills, `apps/`, and a grant under home all sit inside it, so one read-write mount of the home folder serves them and the rules say what in it is open. A read-only mount (`OverlayFs`) is used for a read-only source only when no writable one sits inside it. The writable mounts are `ReadWriteFs`, because `OverlayFs` copies on write into memory and the filesystem is rebuilt per bash call, so a `mv` into a folder would report success and leave the person's files alone. [bash-sandbox-mounts-and-native-binaries.md](bash-sandbox-mounts-and-native-binaries.md) has the mount design and its quirks.

## Containment layers (strongest -> weakest)

1. **The shell's filesystem: just-bash builtins and the file tools** (`BashTool` via `src/lib/create-bash-env.ts`, and `ReadFile`/`WriteFile`/`EditFile`/`GenerateImage`): a TypeScript bash interpreter running against the mounted filesystem built from the layout (`shellFs` in `src/lib/shell-fs.ts`). Standard unix commands (`cat`, `sed`, `awk`, `jq`, etc.) are reimplemented in TS and see only that filesystem. Each mount is wrapped in `rulesFs` (`permissions/rules-fs.ts`), which asks the rules before every read, write, listing, copy and move: a refused path throws `EACCES` naming the path and the reason. A builtin reports any failed read as a missing file, so `create-bash-env.ts` collects the refusals during a call and appends them to the call's stderr, with the path spelled out ([just-bash-upstream.md](just-bash-upstream.md) says why). The file tools build the same filesystem for each call and do every read and write through it (`src/lib/tool-fs.ts`), so a path means to them what it means to `cat` and `>`: relative to the work folder, the shell's working directory, with `..` and `~` as the shell takes them, and absolute in the shell's spelling. A path the rules refuse is refused to a file tool with the note the shell appends; a symlink inside a mount is refused to both, since `ReadWriteFs` follows none; a write outside every folder fails as a redirect does; and a file past the shell's read bound (256 MiB) is too large for both. A tool that hands a file to a native helper (`ffprobe`) takes its host path from the filesystem only once the filesystem has let it read the file. On a missing file, `read_file`, `edit_file` and `generate_image`'s sources also try the spellings macOS gives a name a model retypes another way (a screenshot's narrow no-break space before AM or PM, a decomposed accent, a curly apostrophe), through the same filesystem. `generate_image` writes only into the work folder, since its result names a path relative to it. What the app reads and writes itself in a folder the agent can change, a background command's log in the work folder and an app's manifest, guide and icon in the apps folder, follows no link from that folder's own name down (`own-file.ts`): the app runs outside every sandbox, and a program the agent ran can put a link at any of those names, the folder's own included. The home folder's listings run against a smaller traversal budget than the chat's own folder. `du` is the exception that does not go through the interpreter's walk: `shell-commands/du.ts` resolves each operand through the same layout, refuses one the rules keep from the agent and a symlink out of its mount, and walks the real directories in a worker thread, because the builtin's walk over a large folder runs on the main thread and spends the whole traversal budget without answering. Since it walks as the app, outside every sandbox, it leaves out what the rules don't open for reading (`walkBounds`): the app's own data, neither counted nor named, and every place that asks first or is closed, named on stderr, since reading inside Desktop, the Music library or other apps' files as the app raises macOS's own prompts over a size; what opens inside either is walked. Anything it does not implement falls through to the builtin. The interpreter also blocks JS escape vectors and prototype pollution; see just-bash's own `THREAT_MODEL.md`, reachable through the `just-bash` agent reference. The network commands (`curl` among them) are just-bash builtins too, not host binaries, and they fetch through just-bash's own `network` config: every address is open, the internet and the local network alike, loopback included, with the body capped at the sandbox's byte limit. `WebFetch` and app requests reach the same addresses. Instrument's own workspace server is on loopback too and guards itself: its model proxy and CDP bridge each require a per-launch secret the sandbox never holds ([decision record](../decisions/2026-10-10-the-workspace-server-guards-itself.md)). The shell's own `PATH` names no folder it mounts, so a binary in the home folder cannot shadow a command registered under the same name.
2. **`agent-browser` flag/subcommand policy** (`src/lib/shell-commands/agent-browser.ts`): the harness owns daemon session identity and config/plugin-registry discovery (`--session`, `--config`, `--namespace`, `AGENT_BROWSER_PLUGINS`, plus a managed empty `--config` so the agent-writable chat folder's `agent-browser.json` is never discovered) and blocks meta subcommands (`auth`, `plugin`, `state`, etc.). By default invocations route to the in-app browser through a `browser.provider` plugin (`src/lib/agent-browser-plugin.ts`, `AGENT_BROWSER_PROVIDER=instrument`). Connection-targeting flags (`--cdp`, `--auto-connect`, `--provider`, `--profile`, `--state`, `--executable-path`) and the `profiles` subcommand are refused: the in-app browser is the only browser, since a Chrome the person is using exposes no debugging port to reach their live sessions. Screenshots land in the chat's `screenshots/` and downloads in its `downloads/`, both in its work folder. An `upload` operand must exist in the shell's filesystem and is passed on in the host's spelling, which Chromium requires. A page the agent opens by a file path is loaded at its real `file://` address, and the CDP bridge checks every navigation to a `file://` address against the chat's layout (see [in-app-browser.md](in-app-browser.md)). Page-level behavior inside Chromium is currently unrestricted, and page content the CLI returns arrives as the CLI prints it, with no boundary markers ([decision record](../decisions/2026-10-09-outside-content-arrives-last-and-unmarked.md)).
3. **Native commands**: `pnpm`, `node`, `ffmpeg`, `git`, `uv`/`python`/`pip`, `rg`, `instrument mail`/`notes`/`messages` (macOS only), and the other custom commands in `src/lib/shell-commands/`. These shell out to the real binary through `execShim` or `execaNodeForChat`, with their arguments exactly as the agent typed them (on Windows an absolute path in the shell's spelling becomes the host's, `hostPathArgs`) and the shell's current directory, which starts as the chat's work folder, as the working directory. Once running they have the host user's network, `process.env` and `child_process`; what holds their files is the operating system, from the same rules. The agent's two script runtimes are among them: `python` (alias `python3`) is the interpreter of the `.venv` nearest the shell's folder, or the managed Python's own where none is near, and `node` is Electron run as Node, so a script has whatever was installed and is held to the same profile as any other binary ([decision record](../decisions/2026-10-12-python-and-node-run-native.md)). A script also reaches the agent's capabilities as values ([decision record](../decisions/2026-10-27-scripts-reach-instrument.md)): a `node` script through an `instrument` global, from a preload `node.ts` passes with `--import` (`node-preload.ts`), and a `python` script through `import instrument`, a module found by a `.pth` in whichever virtualenv runs or, for the managed Python run bare, on `PYTHONPATH` behind a `sitecustomize` (`capabilities/python-runtime.ts`). The app writes both into the runtime folder's `preload/`, which every native command reads and none changes, so no chat can change what another chat's programs load. The command listens on a loopback port for that one process and passes the port and a random token in `INSTRUMENT_CHANNEL`, which the preload, the `.pth` line or the `sitecustomize` takes out of the environment before the script's code runs. Each request goes over that connection to the command, which answers it through the capability registry's dispatcher (`capabilities/dispatch.ts`) with the bash call's chat, session, model and role, the same gate the shell's own `instrument` passes, so the token opens nothing the shell does not. Loopback is the channel on every platform because every sandbox lets a program connect to it, where Node's IPC handle does not reach a program MXC holds; only the process the command started has the token, and the listener closes when it exits. An `instrument` program on the runtime folder's `bin/` (first on every native command's PATH) prints how to reach these from a script and exits 127, so `subprocess.run(["instrument", ...])` hears why rather than "not found". The preload also reads past a package.json the sandbox refuses in a folder above the script (Node fails outright on one where a missing file would do), only after Node's own look was refused.

   **Programs on the PATH.** A name no builtin and no command of ours answers runs the program by that name on the computer's PATH (`shell-commands/path-program.ts`), searched first match first for a regular file this user may execute, or on Windows for the name with each PATHEXT extension in turn. The PATH is the one a native command runs with: the app's own, which holds its bin folder, with the virtualenv nearest the shell's folder, where there is one, and the bundled uv ahead of it. just-bash asks for the program only once its own lookup misses, through the `resolveExternalCommand` option our patch adds ([just-bash-upstream.md](just-bash-upstream.md)), so a builtin, a function, or one of our commands keeps its name, and a program of the same name is reached only by its path. A name with a `/` runs natively when it names a script with a `#!` line or a Mach-O, ELF or PE binary; an executable file with neither is a shell script, and just-bash runs it as a shell would. The program runs through `execShim` like every native command, with the environment allowlist, the shell's directory, stdin, cancellation and background streaming, under Seatbelt or bubblewrap; a `.bat` or `.cmd` goes through `cmd.exe`. `command -v`, `type` and `hash` answer from the same lookup, and `which` (ours) asks `command -v`, so each names what will run: a program by its path, one of our commands by the program it runs (`python3` by the interpreter it runs in the work folder, `git` by the bundled git; `COMMAND_PROGRAMS` in `create-bash-env.ts`), and a just-bash builtin or a command of ours with no program of its own as a shell builtin (`file is a shell builtin`, `command -v file` prints `file`), through the `registeredCommandPath` option the same patch adds. A name found nowhere is `command not found` with status 127. On a Mac without Apple's Command Line Tools, a developer tool stub (`make`, `cc`, `/usr/bin/python3`, `xcrun`) runs like any program and fails, since the profile keeps it from asking for the installer, and `execShim` adds a line saying the person installs the tools. There is no list of programs and no card per program: the folder rules hold a program the way they hold `python`. A command we wrap with checks of its own (`git`'s argv policy, `agent-browser`'s flags) has them only under its bare name; the same binary run by its path gets the folder rules and the environment, as it would from a script. See the [decision record](../decisions/2026-10-12-programs-on-path-run-natively.md).

   **macOS: Seatbelt.** Every spawn runs under a profile `seatbeltProfile` builds from the rules (`src/lib/native-sandbox.ts`), started through the app's launcher, `instrument-seatbelt` (`apps/studio/native/mac-helper/seatbelt`, built with the Mac helper): the profile is compiled to Seatbelt's bytecode once per set of rules, held in memory, and handed to the launcher in its arguments, which applies it and execs the program, or exits 126 without running it when the bytecode cannot be applied. Where the launcher is missing or cannot compile a profile, the spawn goes through `/usr/bin/sandbox-exec`, which compiles the profile again for every process. It allows everything by default, so system directories, devices and services stay where a binary expects them, and then, ordered shallow to deep because the last matching rule wins, denies changes anywhere in the home folder and lets each rule open or close its folder: a folder allowed inside a place that asks is open, and one closed inside it is closed again, the same answer `reachOf` gives. A path is written in both spellings where a symlink lies on the way. Opened regardless of the rules (`nativeReachFor` in `permissions/chat-rules.ts`, `toolCaches`): the chat's own folder, the apps folder for a chat, the workspace's own skills, uv's data folder (but the managed Pythons and the base packages in it, which are for reading only, so no chat can change the interpreter or the packages every other chat runs) and the node-tools folder for reading and changing, the other skill sources and the app's bin folder (with the folders its links lead to) for reading, and macOS's per-user cache folder (`DARWIN_USER_CACHE_DIR`, `toolCaches`) for both; `~/Library/Caches` is the app-files place's to open (above). A listed folder is closed with `file-read*` and then lists its folders (`file-read-data` limited to directories) and answers metadata (`file-read-metadata`). Seatbelt ranks a rule naming one operation above a `file-read*` rule whatever their order, since last match wins only between rules naming operations alike, so every rule inside a listed folder also says the same for those two operations, or a closed folder in it would list and an open one would not read. The app's own pnpm, uv and node-gyp keep their stores, caches and config in the app's folders rather than the person's, so nothing else in the home folder is opened for them. Apple Events and opening apps are denied (see the user's other apps, below), as is the launchd service the `/usr/bin` developer tool stubs ask to show the Command Line Tools installer, so no command can raise that dialog however it clears its environment ([finding](../findings/macos-command-line-tools-dialog.md)). Registering a launchd job is denied (`job-creation`), since `launchctl` and the `cron`/`at` spoolers would otherwise hand code to a daemon to run later, in the login session, under no profile; the operation holds whatever starts the job, a copy of the binary or a script included, and those names are also refused in the shell (`SCHEDULING_COMMANDS` in `create-bash-env.ts`) so the agent hears why rather than a launchd error. Signals are denied outside the command's own sandbox: a program still stops its own children and itself, while `kill`, `pkill` and `killall` run as programs get EPERM for what an earlier command left running and for the person's other processes. The agent stops its own through the shell's `kill`, which runs in the app and takes only a pid one of the session's commands started ([background-processes.md](background-processes.md)). Seatbelt also refuses a program that runs as another user (`ps`, `top`, `sudo`), so the shell runs `ps` and `top` by name outside the profile, read-only (below); when a program or script starts them, `setuidRefusalNote` tells the agent to run them as a shell command instead. The profile binds every process the command starts, a `python` script's own `subprocess` included. It is built from the person's rules and the chat's reach and does not carry the app's own hidden entries, so [the finding](../findings/private-dir-masking-is-not-a-boundary.md) still applies to what a program the agent starts can read. A spawn through the launcher costs about 6 ms in the shell against about 22 ms through sandbox-exec.

   **Linux: bubblewrap.** The same rules become `bwrap` arguments (`bwrapArgs`): the whole system as it is, the home folder read-only, then each rule's folder bound back from shallow to deep, read-write, read-only, or replaced by an empty folder or an empty file when it is closed. A closed folder that a folder opens inside can only be passed through: it holds what opens in it, with the folders on the way there searchable and no more, and nothing else, so a program naming anything else there finds it missing, and the note below says why. Nothing a closed folder holds is listed to build the arguments: bubblewrap refuses more than 9,000 of them, and a stand-in per entry would reach that once a workspace holds about a thousand chats. The login session's runtime folder (`XDG_RUNTIME_DIR`, `/run/user/<uid>`) is an empty one: it holds the session bus, through which `systemd-run --user` would start a command outside the sandbox, and the ssh and gpg agents' sockets, which sign with keys the rules may keep closed. The ssh-agent's socket is bound back once the rules reach `~/.ssh`, and one elsewhere (`/tmp/ssh-…`) is covered until then. A socket in the abstract namespace has no path, so this does not reach one; blocking `socket(AF_UNIX)` with seccomp, as some sandboxes do, would take a helper the app does not ship and would break programs that talk to their own children over a socket. A folder the person allowed by name before it existed (the one a refused `git init ~/newproj` names to ask for) is made before it is bound, where the folder holding it is there. The command runs in its own process namespace (`--unshare-pid`), so what it leaves running dies with it when the app quits, and a program sees and signals only what its own command started, by the namespace's pids rather than the computer's (`jobs -l` prints the computer's), and behind a `bash -p` step that closes every descriptor it inherited but its standard streams: on Linux a spawned program inherits whatever the app holds open without close-on-exec (Chromium's databases and sockets, the debug port), and an open descriptor reaches past every closed folder. macOS needs no such step, since libuv spawns there with every descriptor closed on exec. `bwrapAvailable` probes once; Ubuntu closes user namespaces to unprivileged programs, and the `.deb` installs an AppArmor profile for the app that opens them for it and what it starts, while an AppImage installs none and runs unwrapped.

   **`agent-browser`** is spawned directly rather than through `execShim`, so neither profile holds it; its flag and subcommand policy (layer 2) is what does.

   **uutils calls that cannot reach a file** run unwrapped too, to save the sandbox's start-up cost in loops and pipelines (`shell-commands/unsandboxed-uutils.ts`; the full rules are in `native-and-builtin-commands.md`, "Calls that skip the OS sandbox"). What stands in for the profile is that the program is given no path: its options are a closed list reviewed against the pinned release's sources, a single file it names is opened by the shell after the checks a read through the layout gets (realpath inside a folder the chat reaches, allowed by the rules, one name, the inode it checked) and handed over as stdin, its environment is built from a fixed set rather than inherited, and its binary must hash to the reviewed sha256. Anything outside that runs under the profile as before.

   **`ps` and `top`** run unwrapped on macOS and Linux so the agent can read the person's process list (`shell-commands/unsandboxed-process-list.ts`; the lists are in `native-and-builtin-commands.md`). On macOS both are setuid root, which Seatbelt refuses to start; on Linux procps runs under bubblewrap but sees only the command's own pid namespace. Each runs from its fixed system path, which must be root-owned and writable by no one else, with the environment built from nothing that unsandboxed uutils get, and only with options on a closed list per platform that only read: nothing that shows another process's environment, names a file, or puts `top` in its interactive mode. Any other option is refused before anything runs. On Windows they stay programs on the PATH; there `tasklist` runs unwrapped instead, from `System32`, since under MXC a program sees only its own container's processes, without `/s`, `/u` and `/p` (another computer, an account and its password). `taskkill` stays held.

   **Elsewhere**, a native command no sandbox holds is refused (`NativeSandboxUnavailableError`) unless the person turned on "Run programs without a sandbox" in Settings › Permissions ([native-sandbox-off.md](native-sandbox-off.md)); Windows runs them under MXC (`native-sandbox/mxc.ts`) when its launcher is there and a canary launch through it works, and unwrapped otherwise. The system's own settings say why no sandbox can be made (no `sandbox-exec` on a Mac, no bubblewrap or user namespaces closed on Linux); a probe that fails for any other reason, whatever it printed, is no answer, logged and run again by the next command. Settings › Permissions reads the reason (`sandboxOff`) from the same probes and warns, and the notifications bell carries a notice for it, Windows' included. The one command-line check is `git`'s, below.

   **What that leaves on Windows.** A native program there reads and changes everything the person can, the app's own data included: the workspace's keys and account sign-in (which `safeStorage` cannot keep from it, below), `permissions.json`, which the next bash call reads back as the person's folder rules, every chat's records and work folder, and the runtime folder's `python/`, `environments/`, `skills/`, `bin/` and `preload/`, which every chat and the app's own builds then run. The refusal notes name those paths. What the rules close is kept from an ordinary walk only: `rg` adds exclusion globs for the app's own data under every folder it may walk from (`withAppDataLeftOut`), and `du` leaves it out of its own walk, so a search of the output folder or the home folder does not read the workspace's keys or settings; every chat's records are open to reading, so such a search walks them. A program set on reading it is not held: `python`, `node`, `pnpm`, `uv`, `ffmpeg` and any program on the PATH open what they are given, `rg -L` follows a junction the agent made, and `git add -A` in a repository holding the workspace's `.instrument/` stages its records.

   **When the system stops a command.** Nothing is read out of a native command's output: its own `Operation not permitted` reaches the agent as the program printed it, and the prompt's folders section says which folders ask, so the agent asks with `ask_permission`. Under bubblewrap a name in a closed folder that something opens inside is missing, and the home folder is read-only, so there the same refusal reads as a missing file or a read-only disk.

   **What a hatch prints** reaches the agent through `filterShellOutput`, which redacts credentials (a token in a URL's userinfo, git's `password=` and `username=` lines) and, on Windows, turns backslashes into slashes. Paths are not rewritten: what a tool prints is the path it was given. Subprocess **stdin** crosses as raw bytes (`subprocessStdin`), because handing just-bash's latin1-packed stream string to `execa` would UTF-8 re-encode every non-ASCII byte. The subprocess **temp dir** (`TEMP`/`TMP`/`TMPDIR`) is the system's, as the shell exports it, respelled for the host in `resolveCommandContext` with the folder variables (`INSTRUMENT_WORK`, `INSTRUMENT_OUTPUT`).

   **The user's other apps** are reached through Apple Events, and only through the commands the app has for them, so no AppleScript the agent writes runs. The Seatbelt profile denies sending Apple Events and opening apps, so a command could not have another app do what the profile keeps from it. `osascript` by its bare name is refused with the commands that reach the apps, and run by its path it runs inside the profile, where no app takes its events. `instrument mail`, `notes` and `messages` (`shell-commands/mail.ts`, `notes.ts`, `messages.ts`) each run a fixed AppleScript the app ships, one per subcommand, as `osascript -e <script> -- <values>` (`app-scripts.ts`): whatever the agent supplies, an address, a body, a search, a note's id, reaches the script only as an `on run argv` value, and past `--` osascript reads none as an option. Each first holds its app to the app rules in Settings › Permissions (`appRefusal` in `permissions/apps.ts`: an app that asks is named to ask for with `ask_permission`, as a folder is), then runs unwrapped, since an app takes no Apple Events from a sandboxed sender, with none of the shell's variables. A file `instrument mail` attaches is held to the folder rules for reading first, where a link leads too, since Mail reads it outside every sandbox. Calendar, Reminders and Contacts are read through the app's own Swift helper instead (`instrument calendar` and `contacts`, [mac-native-bridge.md](mac-native-bridge.md)), held to the same app rules first: `instrument contacts` asks for Contacts, and `instrument calendar` passes on only its own subcommands, each asking for Calendar or Reminders by what it reads, so no other answer of the helper's is reachable through it. Shortcuts is the same kind of app with no command of ours: macOS's `/usr/bin/shortcuts` runs as any program on the PATH, but a shortcut runs in Apple's own services (siriactionsd, reached over `com.apple.siri.VoiceShortcuts.xpc`, and the runner it starts), outside every sandbox. One table, `REACHABLE_APPS` in `permissions/apps.ts`, lists each such app with the programs that act through it and the services its work runs in. The profile denies the mach-lookup of the services of every listed app the chat may not use (`closedServices` on the reach, read when the shell is made, and every listed app's where absent), and a program at a listed path first asks for its app as the app commands do (checked in `path-program.ts`), so the refusal naming Shortcuts to ask for comes before `/usr/bin/shortcuts` runs. Any other way to start it, a script or a copy, meets the closed services and fails with "Couldn't communicate with a helper application". The app claims `com.apple.security.automation.apple-events` and names a reason in `NSAppleEventsUsageDescription`, and macOS asks the user once per app it controls.

   **macOS privacy prompts** for anything a native command does (Screen Recording for `screencapture`, Camera, Contacts) name Instrument, not the program. The program is the app's own child, started through `sandbox-exec`, which applies the profile and then runs it in place, and macOS holds the app that started a process responsible for its privacy requests. A permission the person grants is Instrument's, for everything it runs, and the agent is told to name the setting for Instrument itself.

   **Stored secrets.** Studio's stores encrypt with Electron's `safeStorage`, whose key on Windows (DPAPI) and Linux (libsecret) any process running as the same user can use, so these hatches can decrypt the session, provider keys, and app credentials on those platforms; only the macOS keychain's per-app ACL keeps the key from them.

   **Git.** Same trust level as the other hatches. Two pieces: `src/lib/git.ts` holds the environment that isolates git, and `src/lib/shell-commands/git.ts` is the `git` shell command's argv policy on top of it. Both use the git distribution dugite ships, located via dugite's `resolveGitBinary()`, with `setupEnvironment()` supplying `GIT_EXEC_PATH`, templates, and the CA bundle. It must be listed in electron-builder's `asarUnpack`, since a binary inside the asar cannot execute.

   `gitSubprocessEnv()` is merged into `resolveCommandContext` **and** `execaNodeForChat`, so it reaches every task subprocess rather than only the shell command. That is deliberate: `<userData>/runtime/bin` (where `setupBinDirectory` puts a `git` symlink for the user's apps) and `/usr/bin` both hold a `git` that a script can invoke by bare name, so isolation anchored to one command shim would leave those uncovered — and stripping those directories from `PATH` would make it worse, since the fallback is a host git that reads the user's real config and keys. It also prepends dugite's `bin` so a bare `git` resolves to the same binary the shell command uses.

   It **deletes every inherited `GIT_*` it does not own**, rather than overriding a fixed list. The agent controls the shell environment, and `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` alone sets any config key with no argv involved at all; `GIT_DIR`, `GIT_EXTERNAL_DIFF`, `GIT_INDEX_FILE`, and `GIT_ALTERNATE_OBJECT_DIRECTORIES` each reach a capability the argv checks exist to deny. The config triple is owned rather than deleted, which comes to the same thing: `GIT_CONFIG_COUNT` is pinned at `1` and slot 0 is spoken for, so a `KEY_1` the agent exported names nothing and its `KEY_0` loses to ours. What it keeps or sets:

   - `GIT_ALLOW_PROTOCOL=http:https` is the load-bearing control. When that variable is set it is the _only_ transport check git makes, so no `-c protocol.*.allow` can widen it. Excluding `ssh` keeps the user's keys and ssh-agent unreachable, excluding `ext` closes remote-helper command execution (`ext::sh -c ...`), and excluding `file` stops the agent cloning repositories from elsewhere on the host.
   - `GIT_CONFIG_GLOBAL=""` skips `~/.gitconfig` and the XDG config, which would otherwise hand git the user's identity, credential helpers, and `url.insteadOf` rewrites. `GIT_CONFIG_NOSYSTEM=1` covers `/etc/gitconfig` on macOS and Linux, where dugite's bundled system config is just an `include` of it; Windows keeps dugite's minGit system config because it carries the TLS/CA settings.
   - `GIT_TERMINAL_PROMPT=0` with `GIT_ASKPASS`/`SSH_ASKPASS` set to `""` rather than unset. Git reads `GIT_ASKPASS` first and only falls through to `core.askPass` and `SSH_ASKPASS` when it is absent, so `""` both blocks an inherited helper and runs nothing. Without it, `GIT_TERMINAL_PROMPT=0` would suppress the terminal prompt only for a GUI one to answer it.
   - `GIT_EDITOR`/`GIT_SEQUENCE_EDITOR` set to `false`, which outrank `core.editor`/`sequence.editor` and so hold even against a repo config the agent wrote. `GIT_ATTR_NOSYSTEM=1` keeps a system gitattributes from naming a diff/merge driver.
   - Commits are authored and committed as `GIT_AGENT_NAME`/`GIT_AGENT_EMAIL`, so history never attributes agent work to the user.
   - `GIT_CONFIG_COUNT=1` with slot 0 holding `core.longpaths=true`, so a bare `git` reaches Windows files through the Unicode `\\?\` APIs instead of the 260-character `MAX_PATH` ones. See `docs/findings/windows-long-paths.md` for why the task prefix makes that mandatory and what it does not cover.

   The `git` shell command adds three things an env var cannot express. **Forced config**, prepended as `-c` to every invocation: command-line config outranks every config file, so `credential.helper=` resets the helper list a `git config credential.helper store` would otherwise build (reaching `~/.git-credentials`, the keychain, or the credential manager dugite ships on `GIT_EXEC_PATH`), and `core.longpaths=true` holds even for a clone of a repository that ships the key set to `false`. **Config-key rejection** over both `-c`/`--config-env` (each accepted by git in attached _and_ space-separated form) and `git config <key> <value>`, which writes the same keys into the repo for every later invocation — needed because forced config cannot pre-empt an arbitrary `alias.<anything>`. **Path containment** for `-C`/`--git-dir`/`--work-tree`/`--file`/`--template` values and for leading-`..` positionals (`git init ../../x`), which must stay inside the chat's work folder or a folder it reaches. The containment fold matters: git resolves each non-absolute `-C` relative to the preceding one, so `-C .. -C .. -C ..` climbs three levels while three independent per-value checks each see one harmless `..`.

   **Folders the chat reaches** get no special route: git is handed real paths (`-C <repo>`, `--git-dir=<repo>/.git`, or a `cd` into the folder), and the OS profile above is what holds the files it touches. Before a command that writes, the shell command asks the rules for a write at its working directory and at each absolute path argument (`ruleRefusal`), and where they refuse, git may only read there: `READ_SUBCOMMANDS` and the listing forms of `branch`, `tag`, `remote`, `stash` and `config`, with `--no-optional-locks` forced so `status` and `diff` stop refreshing the index. Where the rules allow a write, git gets the whole command line, since committing in a folder the person granted is what they granted it for. See `docs/decisions/2026-09-11-git-reaches-attached-folders.md` for what was weighed and the pointer-file reach it leaves open.

   The net capability is public clone/fetch over http(s) plus local history and commits, in the chat's work folder and in the folders it reaches. Private repositories and pushing need credentials and are therefore unavailable; see `docs/decisions/2026-07-21-git-without-user-credentials.md` before wiring any up. Two consequences of the protocol allowlist worth knowing: cloning one task-local repo into another (`git clone work/a work/b`) fails with `transport 'file' not allowed`, since that is the same transport a `file:///Users/...` URL would use and path containment does not inspect URLs; and there is no editor, so a commit without `-m`/`-F` fails rather than hanging (`GIT_EDITOR=false`). `collapseProgress` keeps only the last state of git's carriage-return progress redraws, which otherwise arrive as a single ~20 KB line that line-based truncation cannot trim.

   **What this does not claim.** The argv layer applies to the `git` shell command only; a script that runs `git` itself gets the environment but not the argv policy. Since that script could equally read `~/.git-credentials` directly, the argv layer is defense in depth against the easy path, not a boundary; on macOS and Linux `~/.git-credentials` is closed to every native command by the OS profile until the person allows it on its card. Likewise, a repo's own `.git/hooks` are writable through the file tools and run on `git commit`; `core.hooksPath` being on the denylist does not change that, and it is capability-equivalent to the `node` baseline.

   **Python (`uv`).** Same trust level as the `node`/`pnpm` hatches, not a new boundary. The bundled `uv` binary (`src/lib/uv.ts`; vendored into `apps/studio/resources/uv/` by `apps/studio/scripts/download-uv.ts`) runs `python`/`pip` against the `.venv` nearest the shell's folder, looked for up to the work folder's root, or the one at that root for a command run outside it (`nearestVenv`). With none near, `python` runs the managed interpreter itself, with the standard library alone and the person's user site-packages off (`PYTHONNOUSERSITE`), and `pip` or `uv pip` makes the venv at the work folder's root first (`venv.ts`); a venv whose base Python is gone is made again wherever it is. A script in a skill's folder (the runtime folder's `skills/`, a Node skill's built copy, the workspace's skills) runs in that skill's environment instead: one relocatable virtualenv per `uv.lock`, in the runtime folder's `environments/`, which the app builds on the skill's first load or script, held to the asking chat's reach with only the folder being built opened to it, and builds again once its base Python is gone. Every package in it is checked against the hash its `uv.lock` records (`uv export` with hashes, `uv pip install --require-hashes`), an sdist as much as a wheel. A skill the app ships is built from uv's cache in the runtime folder's `build/caches/`, which no chat reaches (`uvBuildSubprocessEnv`), so nothing a chat put in its own cache ends up in what every chat runs; the workspace's own skills, which any chat can change, are built from the chats' cache as their own installs are, into environments named apart (a shipped skill's is `shipped-<hash>`), so one never stands in for a shipped skill's however the two lock. Anything else run where no `.venv` is near runs in the environment of the skill loaded last, and `uv run --project <skill>` runs in the skill's own (`UV_PROJECT_ENVIRONMENT`, with `UV_NO_SYNC`, since no chat may change it). The two are layered, so the skill's packages and what `pip install` put in the nearest `.venv` are both found (`skillPythonToRun`): a skill's script, and `uv run --project <skill>`, get that `.venv`'s site-packages after the skill environment's own, and anything else run in a `.venv` gets the site-packages of the skill loaded last after the `.venv`'s, so the skill's pinned versions win in its scripts and the agent's own installs win in its code. The layer is a `sitecustomize` the app writes to a folder of its own in `environments/`, put first on `PYTHONPATH`, with `INSTRUMENT_EXTRA_SITE_PACKAGES` naming the folder it adds (`pythonLayerEnv`): `site` imports it after adding the interpreter's own site-packages, and `site.addsitedir` appends the folder after them and runs its `.pth` files, where a `PYTHONPATH` entry would go ahead of them. It takes its own folder off `sys.path` again, then runs the `sitecustomize` it stands in front of where there is one (none of the managed Python, the environments the app builds and a `.venv` `uv venv` makes ships one, but a Python elsewhere on the computer or a package may), adds nothing in a Python of another version, and reaches every Python the script starts, which inherits both variables. `uvSubprocessEnv()` pins a chat's uv to the runtime folder under `app.getPath("userData")` (`UV_CACHE_DIR` and `UV_TOOL_DIR` in its `caches/`, `UV_PYTHON_INSTALL_DIR` in its `python/`) so its caches and managed Pythons stay out of the person's home folder, ignores host config (`UV_NO_CONFIG=1`), and only uses a managed CPython (`UV_PYTHON_PREFERENCE=only-managed`), pinned to 3.12 (`MANAGED_PYTHON_VERSION`) because the newest CPython runs ahead of the scientific/ML wheel ecosystem and uv's resolver silently backtracks to ancient, unbuildable deps on it. The app installs that Python itself, outside any chat's reach and from the build folders' cache, before a chat's first `uv` command or virtualenv (`ensureManagedPython`), since no chat may write the folder it lands in. A connected app's local Python server, which runs outside every chat's sandbox from the environment `uv tool run` keeps in its cache, uses the same cache. A chat's uv runs with `UV_PYTHON_DOWNLOADS=never`, so asking for another version fails, with a line saying only 3.12 is available. Model and font caches go to the person's own (`modelCachesEnvFor`): on macOS and Linux `~/.cache`, which the app-files place opens, where Hugging Face and Whisper look with nothing set and `MPLCONFIGDIR` and `U2NET_HOME` point matplotlib and rembg, whose own folders (`~/.matplotlib`, `~/.u2net`) are in the home folder no program may change; on Windows, which opens none of the person's caches and gives a held program a `LOCALAPPDATA` removed when it exits, `HF_HOME`, `U2NET_HOME`, `MPLCONFIGDIR` and `XDG_CACHE_HOME` point into the runtime folder's `caches/`. `uv self update` is blocked; everything else passes through. The overlay is also merged into the other hatches' env so a node script can shell out to `python`/`uv`. Every chat's `python` also starts with a set of data and document packages (pandas, numpy, matplotlib, openpyxl, pypdf, pdfplumber, pypdfium2, Pillow, python-docx, python-pptx, reportlab, beautifulsoup4), kept current on each machine rather than pinned in a release (`src/lib/python-base.ts`). The repo ships only a spec, `PYTHON_BASE_SPEC`: each package held below its next major version (`pandas>=3,<4`), so a refresh never changes an API the models know, and a new major arrives only when a release raises a ceiling. The app resolves the spec itself with `uv pip compile`, for this platform's wheels alone (`--no-build`), held to releases a week old by the same `UV_EXCLUDE_NEWER` a chat's `pip` gets, which mirrors pnpm's `minimumReleaseAge`. The resolved versions name a set's folder under uv's data dir (`python-base/<hash>/`), and `state.json` beside them records which set chats use and when the spec was last checked. At launch (`ensurePythonBase`) the app installs a set when there is none for this spec, and otherwise every `python`, `pip` or `uv` command starts a check in the background once the last one is a week old (`refreshPythonBaseIfDue`, run on main, behind a lock file so one process on the machine checks at a time); the command never waits on it. A check that resolves the same versions only records the time. One that resolves others installs them into a new folder beside the current set, outside any chat's reach and from a cache of their own, imports a module from every package with the managed Python under the native sandbox, and only then renames the folder into place and points `state.json` at it. Any failure (offline, a resolve, install or import that fails) leaves the current set in place, is logged, and waits a week like a check that passed; with no set at all, the next command tries again after a few minutes. A chat's virtualenv reaches the set through a `.pth` file each command rewrites to name the current one, so a chat moves to a new set on its next command while a script already running keeps the one it started with. The set a switch replaced stays until the next switch or the next launch, which removes every set but the current one, so the disk holds at most one set beside the current (about 255 MB apparent each, most of it cloned or linked from uv's cache). Chats sit the base behind what `pip` installed there, and `pip` never writes into it; a package that depends on one of them installs its own copy into the virtualenv, since uv does not see them. The agent is told about them in the context message only once they are installed. A `.venv` of the person's own, or one `uv run` uses in their project, never gets the `.pth`.

   **pnpm.** The bundled pnpm runs as Electron's Node with its store and caches in the runtime folder, the person's `~/.npmrc` read for its registry, proxy and sign-in settings (the sandbox keeps it from changes; the install step outside the sandbox and the app's builds read their own empty one instead), and its settings for every install the agent makes as `pnpm_config_*` variables (`nodeToolsEnvFor` in `tool-isolation-env.ts`): a release younger than a week is not installed (`minimumReleaseAge`, refusing a version within it), a dependency's install script nobody allowed is skipped with a warning (`strictDepBuilds` off; the bash tool then says to run `pnpm approve-builds <name>` where it was installed), and `pnpm run`/`exec` start no install of their own (`verifyDepsBeforeRun` off), so a project with nothing installed says so and the agent runs `pnpm install`. `-g`/`--global` is stripped with a note: the global folders are pinned to the app's caches, which no PATH names, so a global install would leave a command nothing finds. A project's own `pnpm-workspace.yaml` can still change them for that project. The work folder is no package of its own: `pnpm add` in a folder with no `package.json` makes one there, and in a folder under one adds to that one, as pnpm does anywhere; on macOS and Linux the folders above the work folder are closed to it, so its search for one stops there. An install from the npm registry (`add`, `install`, `remove`, `update`) runs in two steps on every platform (`pnpm-outside.ts`), since MXC refuses a program it holds the links an install makes. The app's own pnpm installs with no sandbox, with install scripts and pnpmfiles off, a `packageManager` or `devEngines` naming another pnpm ignored, and every package's own dependencies held to the registry (`blockExoticSubdeps`), from a store, caches and settings in the runtime folder's `install/`, which chats only read (`nodeInstallEnvFor`); its environment is built from the app's own, never the shell's. Then `pnpm rebuild --pending` runs the install scripts that step skipped, held by the sandbox like any command, reading that store frozen, and a script nobody allowed is reported as pnpm reports it. Only a command naming registry packages, with options from a closed list, goes outside, into a project the rules let the chat write, whose `package.json`, lockfile and `pnpm-workspace.yaml` name registry packages and build approvals alone, with no `.npmrc`, pnpmfile or workspace above it and no link out of its `node_modules`, and only while pnpm and the executable running it are out of the chat's reach to change. Anything else installs inside the sandbox as every pnpm command did, which works where the sandbox allows links. Where MXC holds commands, `npx`, `pnpx` and `pnx` (`pnpm dlx`) take the same step (`dlx-outside.ts`), since dlx links the cache it installs into: the packages install outside into a folder of the runtime caches' `dlx/`, one per set of packages and kept for a day as dlx keeps its cache, and their install scripts and the package's program then run inside. Only dlx's own `--package`/`-p` is read; any other option, or a package that is not the registry's, runs as `pnpm dlx`. A skill with Node dependencies runs from a copy the app builds in the runtime folder's `environments/`, one per version of the skill, with its production packages installed beside its scripts as its lockfile has them (`--frozen-lockfile`), where Node finds them. A skill the app ships is built with its own store, caches and config in the runtime folder's `build/` (`nodeBuildEnvFor`), which no chat reaches, so a setting a chat writes in `config/` (a registry, a `globalPnpmfile`) or a package it changes in the store never reaches that build; the workspace's own skills are built with the chats' as their own installs are, into copies named apart; a script of the agent's own goes in the work folder, with what it imports added there.

## Soft layer

The agent system prompt in `src/agents/instrument.ts` tells the model it reaches the person's files at their real paths, that the home folder is open to look through, and that changing anything in it or opening a place kept closed until asked needs the person's yes, asked for with `ask_permission`, which ends the turn. It also asks the LLM to behave (refuse malicious code, work in the chat's folder, etc.). It is not a security boundary.
