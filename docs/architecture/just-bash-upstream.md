# just-bash: what we consume, what we work around, what we are waiting on

`just-bash` is the sandbox every agent `bash` call runs in, so its gaps do not surface as stack traces. They surface as an agent giving a confident wrong answer, or writing a prompt-shaped workaround into its own reasoning. That makes the accounting below worth keeping in one place: which build we consume, what we have patched or told the agent to avoid because of it, and what is open upstream.

The failure mode this page exists to prevent is a workaround outliving the bug. Anything added to the registers below needs a removal trigger recorded next to it. See also [agent-sandbox.md](agent-sandbox.md) for what the sandbox contains, and [bash-sandbox-mounts-and-native-binaries.md](bash-sandbox-mounts-and-native-binaries.md) for how the folders a chat reaches are mounted.

## What we consume

We are on the published npm package, not a fork.

- `just-bash@^3.6.0` from npm, declared in `packages/workspace/package.json`.
- One local patch file, carrying sixteen changes: to `find`, to `stat`, to `MountableFs`'s copy across mounts, to the `python3` worker, a `stdinConnected` flag on the command context, to `ls`, to awk's `printf`, to `sort -h`, to how `python3` treats a worker that dies, to `rmdir` on `ReadWriteFs`, to `pathlib`'s glob in the `python3` worker, `find`'s `-newermt` and `-mmin`, to how `awk`, `sed`, `jq`, and `yq` report an execution limit, to how stdin becomes bytes in `sha256sum`, `gzip`, `base64`, `tar`, and `split`, the message a builtin prints for a failed read, and a hook that hands a command name the shell does not know to the embedder, built from source by `scripts/rebuild-just-bash-patch.ts`; see below. Three of them (the `python3` worker, worker exit, and `pathlib` glob parts) change only just-bash's `python3` runtime, which the agent's shell does not register: `python` and `node` are native commands ([decision record](../decisions/2026-10-12-python-and-node-run-native.md)). They are inert and go at the next rebuild of the patch.
- `run` 2.1.3, a dependency of just-bash rather than ours: the QuickJS-ng runtime behind just-bash's `js-exec` (#394), which the agent's shell does not register either. It strips TypeScript with Node's `module.stripTypeScriptTypes`, falling back to `typescript`, its optional peer, only on a Node without it. Electron's Node has it, so the packaged app leaves `typescript` out (`apps/studio/electron-builder.ts`).

`minimumReleaseAge` in `pnpm-workspace.yaml` holds installs to releases at least seven days old, so the newest published version is routinely not the newest installable one. `minimumReleaseAgeExclude` carries the document-viewer libraries deliberately pinned to exact versions, `agent-browser`, which we do float onto fresh releases, exact versions of one oRPC security release, and an exact just-bash version taken a few days early once its patch was rebuilt and verified against it. An exact-version entry is the way past the gate for a release we have checked and want before the week is out; it goes inert once the version ages past the cutoff. A bare package name is reserved for what we deliberately float.

Upstream cuts releases through changesets and merges a great deal between them, so **a fix being on upstream `main` does not mean we have it**. Check the published version, not the branch, before assuming a workaround can go.

## Moving to a fork build

Mostly unnecessary now. What a fork build was for, carrying our changes as source rather than as edits to minified output, is what `scripts/rebuild-just-bash-patch.ts` does inside the pnpm patch: it builds the release tag with every carried change applied and keeps the result as the patch. A fork build would add only a published artifact of our own, which buys nothing while the patch applies, and would cost the release-age gate and upstream's own publishing checks.

Adopt one only if the patch stops being able to express a change, for instance one that adds a new module the published package does not have; the script stops with a message when that happens.

## Fix upstream, or replace the command

Two ways to change what a just-bash command does, and they are for different problems.

**Fix it upstream and carry the fix** when the defect is in just-bash's own model: a quadratic accumulator, a wrong parse, a leaked rejection. just-bash runs in browsers, in plain Node, and over any `IFileSystem`, in-memory ones included, so a fix that works there is a fix every embedder gets, and carrying it until the release lands costs a manifest entry.

**Replace the command with a custom one** when the better implementation needs what only an embedder running in Node or Electron has: a real binary, a worker thread, or the host disk behind our mounts. That is not something upstream can take, because it cannot assume any of them. `rg` is the real ripgrep binary in a subprocess, `git` is dugite's git with our argv policy, and `du` (`shell-commands/du.ts`) walks the real directories behind the mounts in a worker thread, so a walk over a large folder costs the main thread nothing where the builtin's costs it everything. A replacement resolves paths through the workspace layout with the same containment as the others, and hands anything it does not implement back to the builtin through `ctx.origCommand`, so it never makes a working command stop working.

The replacements are where the performance headroom is. A builtin is interpreted TypeScript on the thread that paints the window; a subprocess or worker is not.

The patch is generated rather than edited. `patches/just-bash-sources/sources.json` names the release tag and every carried part: an upstream pull request pinned to a commit, or a local diff under the same directory where a pull request has to be adapted to the version we install (`cross-mount-copy-3.6.0.diff` and `stdin-connected-3.6.0.diff` are #422 and #448 merged onto a tag that moved under them, and `stdin-bytes-3.6.0.diff` is #573 reshaped to keep 3.6.0's module graph) or where we depart from upstream on purpose (`ls-plain-listing-3.6.0.diff`). A part may name pull requests and a diff together; the diff applies after them. `pnpm scripts:rebuild-just-bash-patch` then:

1. checks out the tag in a cache outside the repository and installs it;
2. builds it unchanged and stops unless the bundle and the shipped declarations are byte-for-byte the published package, which is what makes a rebuilt file a faithful stand-in for a published one;
3. applies every part in order, stopping on the first that does not apply;
4. builds again, and with `--test` runs just-bash's own tests for the directories the parts touch, after the build because the `python3` tests load the worker bundle it writes;
5. pairs each rebuilt bundle file with the published file it replaces, by walking both builds' import lists from the files whose content-hashed names did not change; a part that adds or removes a module outright stops the run rather than guess;
6. writes the files whose content differs, under their published names, into `pnpm patch --ignore-existing` and commits it, which moves the patch hash in `pnpm-lock.yaml`.

`--dry-run` reports the files without writing. On a development machine some of just-bash's tests fail for reasons of their own: `tar`'s xz cases without `node-liblzma`'s native build, and a few timing-sensitive `python3` queue cases and comparison suites that pass on a rerun. Two runs give a byte-identical patch. The rebuilt `index.js` is most of the patch's size: once a change touches the interpreter, the minifier renames identifiers through the whole file, so most of its lines differ from the published ones. `dist/bundle/browser.js` and `dist/bundle/index.cjs` are left out (`skip` in the manifest); Studio loads the ESM entry.

To move to a new version: point the manifest at its tag, drop the parts it already contains, refresh the pins, and run the script. A local diff that no longer applies has to be ported again against the new tag's source. While the new version is inside `minimumReleaseAge`, `pnpm install` refuses a lockfile that resolves it. Work on the upgrade with `pnpm_config_minimum_release_age=0` in the environment of that shell alone; to land it before the version ages in, add the exact version to `minimumReleaseAgeExclude`.

Earlier parts are gone. `patches/just-bash@3.2.0.patch` normalized the namespace of the dynamic `import("undici")` so the pinned connection owner could read `Agent` off it; without that every `curl` failed as `DNS pinning unavailable for private IP enforcement`. Upstream #339 is the same fix and shipped in 3.3.0. `create-bash-env-network.test.ts` is the guard that would catch a regression. The 3.4.1 patch carried five pieces 3.6.0 made unnecessary: #414 (`find` reports an unreadable directory and goes on), #423 (the `python3` program name, which 3.6.0 pins as #444), #390's entry charging in `ls`, and two fixes to the old `js-exec` worker that `run` replaced, one installing the module loader for scripts so a dynamic `import()` loads (decided in [decisions/2026-10-06-carry-the-script-dynamic-import-patch.md](../decisions/2026-10-06-carry-the-script-dynamic-import-patch.md)), the other stopping the bridge when the worker dies. The `find` cases stay as their guards.

Text we put in front of the model, or commands we withhold from it, because of an upstream gap. Each of these is a liability once the gap closes: the model keeps being told to avoid something that works.

`which` is in that table because it is withheld, not because it is pending. Ours (`shell-commands/which.ts`) answers from the registered command set, so it knows the custom shims (`python`, `agent-browser`, `ffmpeg`) that a filesystem-based `which` cannot see, and then from the computer's PATH, where the programs the shell runs by name are; it is registered as a custom command, which shadows the built-in whether or not the name is withheld. It belongs with the permanent adaptations rather than the workarounds: the `npm` stub pointing at `pnpm` is a product choice about which package manager tasks use, and the `<system_info>` line telling the agent its shell is GNU coreutils rather than BSD is a description of what just-bash is.

### Not yet offered: an external command resolver

The external commands part is ours and has no pull request yet. The text to open one with, against `main`:

> **interpreter: let the embedder resolve a command the shell does not know.** Adds an optional `resolveExternalCommand(name, { cwd, env })` to `BashOptions`, returning `{ command, path }` or undefined. The interpreter asks it for a name containing `/` before reading that file as a script, and for a bare name after builtins, functions, the shell's PATH and the registry have all missed, so nothing that resolves today changes. `type` (with `-a`, `-p`, `-P`, `-t`), `command -v`/`-V` and `hash` ask it at the same points and report the path it returns, and a command remembered in the hash table under that path resolves through it again rather than through the filesystem. The resolver runs inside `DefenseInDepthBox.runTrustedAsync`, since it is host code that may read `process.env` or stat the host disk, and what it returns is registered the way a custom command is. The motivating embedder runs just-bash over the host's real directories and wants a program on the host's PATH to run as a real, separately sandboxed process under its own name, with `command -v` telling the truth about it; without a hook the choices are registering every name on PATH as a custom command before each call, or rewriting the AST. Tests: `src/interpreter/external-command-resolver.test.ts`.

## Known gaps with no fix in flight

Not workarounds, so they carry no removal trigger. They are here because each one is a way the sandbox can hand the agent a confident wrong answer, and knowing about them is cheaper than rediscovering them. Each was checked against 3.6.0.

- **`ln -s` does not work.** Symlink creation is off in the shell's filesystem (`allowSymlinks`), deliberately, so `ln -s a.txt b.link` exits 1 with `ln: failed to create symbolic link 'b.link': Operation not permitted`. On 3.4.1 the same refusal read as a hard link on a directory; #391 fixed the message in 3.6.0.
- **Symlink support depends on who is asking.** The shell's filesystem refuses to create one, so `cp -R` of a `node_modules` tree inside the chat's folder refuses the whole tree up front with `EACCES: permission denied, cp '<link>' contains a symlink`, nothing copied. A real subprocess writes to the host directory directly and is not subject to that, so a Python script can create thousands of symlinks in the same folder where `cp -R` just failed. Nothing in the sandbox surfaces the difference.
- **A copy from one mount into another stopped at the first symlink.** Upstream's `MountableFs` copies a tree across mounts entry by entry and asks the destination to create each link, which every mount we build refuses with `EPERM: operation not permitted, symlink '<dest>'`: everything after the link was left uncopied, and the errno was the one the attached-folders prompt reserved for a macOS denial of the folder. That is the shape of every `cp -R` of a home-directory folder or a checked-out repository. Fixed upstream as #422 and carried locally meanwhile (see Local patches above): the copy finishes around every link and the command exits 1 with `cp: cannot copy '<folder>/Docs': copied all but 2 entries: <folder>/Docs/link.txt: EPERM: operation not permitted, symlink '/work/copy/link.txt'; ...`, every other file in place. The prompt's EPERM rule was narrowed to reads and listings at the same time, so the errno the destination still reports no longer matches it. This bullet goes with the patch.
- **`find -type l` and `cp -L` do not exist.** `find`'s type is `"f" | "d"` upstream, and `cp` has no dereference flag. Together they make a symlinked tree awkward to inspect or flatten, which is how the `cp -R` failure above usually gets discovered.
- **A custom command cannot tell an empty pipe from no pipe.** The command context carries `stdin` as bytes and nothing about where they came from, so `false | rg PATTERN` and a bare `rg PATTERN` arrive identically. Our `rg` is the real binary, which reads stdin when fd 0 is a pipe and walks the working directory otherwise, and the shim had to pick one from the bytes: it picked the walk, so a browser read that failed upstream of `rg` came back as 118 KB of the chat folder's own skill files presented as page text, twice in one production session. Patched locally as the `stdinConnected` part above; the same `stdin ? input : "ignore"` choice in the `ffmpeg`, `ffprobe`, `node`, `python`, and `uv` shims is harmless, since for a reader an empty pipe and `/dev/null` are the same EOF. Upstream's own `rg` had the same bug, reported and fixed in #401 before ours was opened; see the table above for how the two relate.
- **Pipelines are not streaming.** Each stage runs to completion and its whole stdout is buffered as a string, so `tar -cf - big | tar -xf -` trips `total output size exceeded` against `maxOutputSize` even though nothing was headed for the agent. The message names `executionLimits.maxOutputSize`, which reads as "your output is too large" rather than "an intermediate did not fit". The same design means a downstream stage can never end its producer: `rg -l pattern <home folder> | head -200` runs the search to the end of the tree, since `head` does not exist until `rg` has exited, and a promoted call streams every line of it into the live view and the process log regardless of the `head`. A bounded search is unbounded here, and the fix is an interpreter change (streaming stages with backpressure), not a command fix.
- **The error sanitizer hides the paths the agent works at.** `sanitizeErrorMessage` (`fs/sanitize-error` in the package, bundled into the script workers' chunks) is a regex that replaces any path starting `/Users`, `/home`, `/private`, `/var`, `/opt`, `/Library`, `/System`, `/usr`, `/etc`, `/tmp`, `/nix` or `/snap`, and any `C:\` path, with `<path>`; its host-error variant also takes `file://` addresses and more roots. It was written for an embedder whose filesystem is virtual and whose host layout must not leak. The agent here works at real paths, so an error that crosses it names `<path>` and the agent cannot tell which file a rule refused: a script worker (`sqlite3` is the one the shell registers) reports `EACCES: permission denied, ... '<path>' -- <path> is closed in Settings › Permissions`, with the reason intact and the file gone. The main-thread builtins print the path as it is. The workaround is the one in the table above: the shell collects the rules' refusals as they happen and appends them to stderr with the path spelled out, outside the sanitizer's reach. Errors that do not come from a rule (a missing file inside a worker) still arrive sanitized. What would let it go is an option to turn the sanitizer off for a filesystem whose paths are the agent's own. Reproduced on 3.6.0.
- **Three text tools print GNU's answer in another shape.** `uniq -c` pads its count to four columns where GNU pads to seven; `sort` collates non-ASCII lines (`naïve`, `日本`) in an order that is neither GNU's `C` nor its `en_US.UTF-8`; and `jq`'s `@csv` quotes a string only when it holds a comma, quote, or newline, where jq quotes every string (deliberately, by the comment beside it). A script comparing output byte for byte, or a CSV consumer that expects quoted text, sees the difference.
- **A parse error fails the whole script.** An unsupported construct anywhere means no statement runs, and the message locates the offending column without naming the construct. Every command before it is silently skipped.
- **`awk` cannot lex a `/` inside a bracket expression.** `awk '{if (n ~ /^[^/]*\.md$/) print}'` exits on `awk: Expected RPAREN, got RBRACKET`, because the lexer ends the regex literal at the `/` inside `[^/]` rather than at the closing delimiter. gawk accepts it, and `[^/]` is the ordinary way to write "one path segment", so this lands on a shape the model reaches for by default. `IGNORECASE` is unsupported too, which matters less only because it usually fails behind this. The cost is not the parse error itself but where it falls: `awk` is normally the last stage of a pipeline, so the whole search runs first and the error arrives after the expensive part, with nothing to show for it. Escaping as `[^\/]` parses. Reproduced on 3.6.0.
- **`date` and `ls -l` can disagree about a file's time.** Upstream, `date` defaults to UTC when `$TZ` is unset while `ls`'s formatter uses host-local components, so a correctly stored UTC instant can display as the previous day. Our env seeds `TZ` from the host zone (`create-bash-env.ts`), so the two agree here; the gap belongs to any embedder that leaves `TZ` unset. Found while fixing `touch`; reported on #364 rather than fixed, because the fix belongs in `ls` and would move every `ls -l` timestamp in the suite.
- **`sqlite3` dot commands are a parse error.** Already covered as a prompt workaround above; noted here too because it is the one gap upstream has declined rather than deferred.
- **We ship our own `mktemp`** (`shell-commands/mktemp.ts`) and withhold the one 3.6.0 added (#377, not ours; our #392 was closed in its favor) through `BROKEN_COMMANDS`. The idiom the model knows for "somewhere safe to put a scratch file" is the one place the sandbox refuses, so upstream's default of `$TMPDIR`, then `/tmp`, fails here unless `TMPDIR` points into a folder the chat reaches. Ours names files under the chat's `.tmp`, the directory native commands already get as `TMPDIR`. Retiring it means setting `TMPDIR` to the chat's `.tmp` in the bash env, and checking that every mount it can point into implements `createExclusive`: `MountableFs` passes the call through, and a backend without it fails the command with `ENOSYS` rather than falling back. Every shell, the chat's and each task's, gets ours. `create-bash-env-mktemp.test.ts` is the guard.
- **A handful of other coreutils are missing** with no equivalent: `zip`/`unzip`, `dd`, `xxd`, `realpath`, `shuf`, `openssl`, `rsync` (`yes` arrived in 3.6.0, finite since pipelines do not stream). Each appeared once in the production record, in a task probing the sandbox rather than doing work, and `od`, `strings`, `head -c`, `seq`, and the `zip` skill cover the ground between them. Listed so the next reader can weigh a request against the whole set rather than adding them one at a time.

## Checking whether a release has caught up

```bash
npm view just-bash version                       # what latest actually is
npm view just-bash time --json                   # when each version published, against minimumReleaseAge
pnpm why just-bash                               # what we resolve to
```

When the published version moves, walk the registers above and delete every row whose trigger has fired, including the prompt text, then drop those parts from `patches/just-bash-sources/sources.json` and rebuild the patch against the new tag. Removing a stale line from the `sqlite3` description matters as much as dropping a patch: a model told a working command is broken will route around it for as long as the sentence survives.

Verify against the installed build rather than the changelog. `packages/workspace/scripts/run-bash.ts` boots the same sandbox the agent gets, so a claim about behavior is one command away:

```bash
pnpm --filter @instrument-org/workspace run --silent script:run-bash -- "<command>"
```
