# In-app browser

Each task can hold a browser the **agent drives over CDP** and the **user drives with mouse and keyboard** — the same guest, not two browsers. This doc maps where that guest actually lives, who owns its lifetime, and how the two drivers reach it, because the pieces are split across the renderer, the Electron main process, and the workspace server, and none of them is the obvious place to start reading.

For why the agent gets a managed `agent-browser` wrapper rather than the upstream CLI, see the [decision record](../decisions/2026-07-10-managed-agent-browser-wrapper.md); for the browser profile, [workspace-browser-profile](../decisions/2026-07-13-workspace-browser-profile.md).

## The guest is a renderer-owned `<webview>`, not a main-process view

This is the fact that makes everything else make sense, and it is not what you would guess from `apps/studio/src/electron-main/browser-view/`.

The guest is a `<webview>` element appended to `document.body` in the **renderer**, managed by the pool in [`client/lib/browser-pool.ts`](../../apps/studio/src/client/lib/browser-pool.ts). The main process owns only _which targets should exist_ and streams that desired set over the `browser.targets` RPC ([`electron-main/rpc/routes/browser.ts`](../../apps/studio/src/electron-main/rpc/routes/browser.ts)); the pool reconciles to it, mounting on add and disposing on remove.

Each guest stays parented to `document.body` for its whole life so that React reconciliation, or a host subtree being hidden, can never unmount it. Unmounting would drop its compositor surface, which breaks capture and input.

## Two visibility modes, and why it is never truly hidden

- **paint-host** — laid out at the guest's logical size but visually hidden (`opacity: 0.001`). Chromium still paints it on screen, so `capturePage()` and CDP input keep working while nothing is showing it. The size is whatever the agent last asked for, else the bounds the panel last showed it at, else 1280×800 — capped in every case at what the window can rasterize (see the policy split below).
- **visible** — positioned over a host slot (the task page's browser panel) and scaled to fit, with input enabled.

Capture requires the guest to stay composited into the window, which is why "hidden" is a near-zero opacity rather than `display: none`. A host shows its guest only while its own surface is on screen (a task's panel while its tab is foreground) and parks it otherwise; hosts on screen together each show their own, the way a draft window's page stands over the page in the pane behind it. Two hosts can also want the same page at once (a chat inline in the pane and grown in a window over it): the pool keeps every host's claim and stands the guest in the frontmost one, the newer on a tie, passing it to the next claimant when that host lets go, so a host beneath re-measuring never pulls the page out from under the window drawing it. **Hiding or closing the panel never disposes a guest** — only the main process's desired set does that.

A shown guest is an element in the renderer's DOM, so the window's own layers stack over it by `z-index` like over any other element: `showOverSlot` takes the layer the host stands on (the pane's page at zero, a draft window's page above the draft), and a menu, a popover, or a floating window drawn above that layer covers the page rather than being painted over by it. Covering it with the renderer's own content does not disturb capture, since the guest's surface is composited on its own. That was not so before the guest moved into the renderer: a main-process view sits above everything the renderer draws, and the reflex of hiding the page under any overlay dates from then.

[`use-browser-slot.ts`](../../apps/studio/src/client/hooks/use-browser-slot.ts) measures the slot and drives show/park; [`use-browser-targets.ts`](../../apps/studio/src/client/hooks/use-browser-targets.ts) exposes which targets have actually attached.

## Attach lifecycle

`createTarget` in [`manager.ts`](../../apps/studio/src/electron-main/browser-view/manager.ts) records an entry, then waits for the renderer to mount the guest and Electron to fire `did-attach-webview`. Target ids accepted in `will-attach-webview` are drained through a FIFO, and each entry carries a generation bumped per create so the renderer pool can diff a recreate of a just-destroyed id against the old one.

Attachment resolves a one-shot signal created with the entry ([`entry.ts`](../../apps/studio/src/electron-main/browser-view/entry.ts)); teardown rejects it. That is what stops a `createTarget` racing a teardown from hanging until its own timeout. Destruction notifies listeners for _any_ reason — explicit close, detach, renderer crash, or a handshake that timed out before the guest attached.

## How the agent reaches it

```
agent bash tool
  `agent-browser ...` (managed wrapper: lib/shell-commands/agent-browser.ts)
      |  CDP over ws
  workspace server CDP bridge (logic/server/routes/cdp-sockets.ts routes by path)
      |  ws://127.0.0.1:<port>/…/devtools/task/<taskId>      a chat's task: every tab it holds (cdp-task-bridge.ts)
      |  ws://127.0.0.1:<port>/…/devtools/page/<targetId>    one page: the chat's on-screen tab, or a task no chat owns (cdp-bridge.ts)
  main process dispatch-command.ts  ->  guest webContents.debugger
```

The `…` in each path is a secret drawn once per launch ([`cdp-bridge-path.ts`](../../packages/workspace/src/logic/server/cdp-bridge-path.ts)) and handed to agent-browser only inside the provider plugin's argv, since the bridge listens on loopback where any local process can reach it and task and target ids are guessable. An upgrade with a wrong or missing secret, or with any `Origin` header, is refused with a 403: browsers always send `Origin` on a WebSocket and agent-browser's client never does. The bridge serves no HTTP discovery (`/json`); agent-browser connects to the `ws://` URL the plugin returns as is.

**A task working for a chat holds tabs of that chat.** Its record's `browserTabs` lists them, each marked handed (by the conversation, with `task new --tab` or `task tab --add`) or opened by the task. Every one is an ordinary tab of the chat in the window's strip, added behind whatever the user has up and never selected on the agent's account. The task endpoint answers agent-browser's `Target.*` domain over exactly those tabs, each known by the window's id for it: `createTarget` asks the window for a background tab and holds it (at most eight), `closeTarget` closes a tab the task opened and only lets go of a handed one, `activateTarget` and `Page.bringToFront` change nothing in the window, and a tab closed by the user or handed over mid-run reaches the agent as `targetDestroyed` / `targetCreated`. Each attached tab is its own `openTargetSession`, the same per-page wiring the page endpoint uses, so the local-file gate, the held navigate and the teardown below hold per tab. A held tab whose guest has not come back since a launch is asked back through the window before the task is told it closed. The page endpoint still pins a connection to one page and refuses `tab`, `window` and `--new-tab` there.

The conversation arranges the tabs with its `tab` command (`open`, `replace`, `close`, `show`), which the window answers on the `window.tab` / `window.tabDone` pair; the same channel carries a task's request for a background tab.

The agent never has to load the `agent-browser` skill before driving the browser: the bash tool attaches the app's copy of it to the result of the first `agent-browser` command in a session ([`browser-skill-delivery.ts`](../../packages/workspace/src/lib/browser-skill-delivery.ts)). Whether it is already there is read from the history the model is actually sent, so a context rollover that dropped the earlier delivery, or a new session, gets it again with the next command, and a `load_skill` of it counts as a delivery.

A bash call whose last page-changing `agent-browser` command (a navigation, `click`, `press`, `select`, `check`, a tab switch) is not followed by a read of the page (`snapshot`, `screenshot`, `get text`, `eval`, `read`) ends with the page as `snapshot -i --delta` sees it ([`agent-browser-follow-up.ts`](../../packages/workspace/src/lib/shell-commands/agent-browser-follow-up.ts)), which saves the model the step it would otherwise spend asking for it. It waits for `domcontentloaded` first, since a click returns before the page it navigated to has loaded, and attaches nothing when the snapshot has no controls in it. The CLI keeps the delta baseline per tab and resets it on a URL change, so a navigation brings the whole page (cut at a character budget) and an action on the same page brings only what changed, a single line when nothing did. Only the task's own browser gets this; an external browser, a browser-free `read <url>`, and `--help` do not.

The wrapper rejects upstream flags and subcommands that would select another connection or persistence model, and rewrites screenshot/download paths into the task's `tmp/` (see [agent-sandbox.md](agent-sandbox.md) for the argv policy). These quirks live in [`dispatch-command.ts`](../../apps/studio/src/electron-main/browser-view/dispatch-command.ts):

- **Screenshots bypass the debugger.** A viewport `Page.captureScreenshot` is served from `webContents.capturePage`; an element clip still goes through the debugger.
- **A covered window is made to draw.** A guest draws only when the Studio window hosting it draws, and a window covered by another app's window or minimized does not. A page the guest navigates to in that state gets a new render widget that never presents a frame, so on their own neither capture path gets one (`capturePage` times out or fails with `UnknownVizError`, the debugger's screenshot never answers) and input is never acknowledged. A page that painted before the window was covered keeps capturing, but input still needs new frames. While a screenshot, a screencast frame or an `Input.*` command is pending, the gateway repeatedly asks the Studio window itself for a one-pixel `stayHidden` capture ([`embedder-draw.ts`](../../apps/studio/src/electron-main/browser-view/embedder-draw.ts)), which makes it draw without ever marking the window's renderer visible. A screenshot that still gets no frame fails with a message naming the covered window as the likely cause and pointing at text reads.
- **Clicks wait for the layout to settle.** agent-browser scrolls an element into view, measures it, and presses the measured point, while pages reflow a frame or two after a scroll. The gateway answers `DOM.scrollIntoViewIfNeeded` only once the element's box holds still, re-runs agent-browser's own scroll-and-measure script (selector and `find` clicks) until two runs agree, and before a press repeats the last measurement, refusing a press whose element has moved instead of letting it land elsewhere and report success ([agent-clicks-land-where-the-element-was](../findings/agent-clicks-land-where-the-element-was.md)).
- **Input needs a rendering page.** A guest in a window covered by another app's can render no frames while still reporting itself visible, and a press sent to it is never acknowledged. Every `Input.*` command first waits up to 150ms for one animation frame; when none comes it asks again while the window is made to draw, and is refused with the reason only when that fails too. The probe can pass while no frame reaches the screen, so every `Input.*` command also runs with the window drawing.
- **Every agent press is logged.** One `agent press` line per `mousePressed`: the point, the element under it and the nearest clickable ancestor (`target=none` means plain text), the guest's `visibilityState`, the host window's state (`focused`, `unfocused`, `minimized`, `hidden`), whether the tab is `shown` or `parked`, and how long the ack took. A click that did nothing can be told apart from one that hit the wrong element or one on a page nobody could see.
- **`Browser.getWindowForTarget` is answered locally.** Electron's debugger does not implement the `Browser` domain, and agent-browser probes it to discover window dimensions, so the gateway reports the guest's current effective surface — falling back to the 1280×800 default only before the renderer has reported a size. A fixed answer would go stale the first time an agent set a viewport or the pool clamped to the raster budget.

## Policy split: the panel may do things the agent may not

`Emulation.setDeviceMetricsOverride` reaches two different mechanisms depending on who asks. The panel's "View as" menu gets a real CDP override through [`device-emulation.ts`](../../apps/studio/src/electron-main/browser-view/device-emulation.ts), carrying a `scale` the panel computes from the guest's live measured bounds so the surface always shrinks to fit what is on screen. An agent-browser caller cannot know that size and so cannot supply a safe `scale`; `dispatch-command.ts` therefore reads its request as a size for the guest **element** and hands it to the renderer pool instead of overriding anything. The guest's layout viewport follows its element size exactly, so there is never a second, larger layout for the compositor to fall short of — which is what corrupted both earlier attempts at honoring the command as a real override ([in-app-browser-device-emulation](../findings/in-app-browser-device-emulation.md)).

An agent-set size applies while the guest is parked and yields to a panel showing it, since the panel's bounds are what the user is looking at; it takes over again on the next park. Sizes beyond what the window can rasterize are **refused with the maximum** rather than clamped, because a clamped guest still reports the size it was asked for and its captures would disagree with it — see [browser-guest-raster-cap](../findings/browser-guest-raster-cap.md) for the 1.3x budget and how it was measured.

Popups follow a shape policy in [`window-open-policy.ts`](../../apps/studio/src/electron-main/browser-view/window-open-policy.ts): real `window.open` popups to http(s) are **allowed** (denying them returns null and hangs "Continue with Google" style sign-in flows), while `target=_blank` links and tab-opens report `foreground-tab`/`background-tab` and get no window. Opens are additionally denied while agent CDP activity is driving the guest, so automation cannot spawn a window the user never asked for. A denied tab-open does not simply vanish. While a person rather than an agent drives the guest, it becomes a tab of the window's own (`newTabOpenOf`, published as `browser.open-in-new-tab` and opened by `useOpeners`): in front for `_blank`, behind for a middle- or Cmd-click, to the web or, from a page on the computer, to another file on it. Under the agent guard the guest navigates there itself, because a denial lands before Chromium mints a WebContents, so the alternative is a click with no outcome and no signal ([blank-target-links-are-dead-clicks](../findings/blank-target-links-are-dead-clicks.md)); the guard withholds a window rather than a navigation. The guest's context menu ([`guest-interactions.ts`](../../apps/studio/src/electron-main/browser-view/guest-interactions.ts)) offers "Open Link", "Open Link in New Tab", and "Open Link in Default Browser"; the same module injects a per-document script mapping the mouse thumb buttons to `history.go()`, the second path besides the chord registry below by which user input reaches a guest that may not hold focus. On macOS the guest's preload ([`page-editor-guest/preload.ts`](../../apps/studio/src/page-editor-guest/preload.ts)) takes the thumb buttons first and sends them to the window (`page-thumb`), where the surface showing the page walks its tab the way its row's arrows do (`onPageThumb` and `stepPage` in `browser-pool.ts`, the rule in `tab-steps.ts`): the page's own history, then the tab's earlier views, then the window tab's history; a page no surface claims steps its own history. The menu's Back and Forward take the same way in (`browser.step-page`), and so do the task panel's arrows. Every step of a guest's own history goes through `goGuest`, which marks it so the navigation it makes does not drop what the tab had ahead of the page. The blank page every guest is born on is removed from its history once it reaches a real one (`dropBlankStart`), so back from a page's first entry is never a step onto an empty page. Turning a page's own `window.open` into a tab the agent can drive is still open: [agent-browser-multiple-tabs](../plans/completed/agent-browser-multiple-tabs.md) leaves popups to a plan of their own.

Downloads split the same way in [`downloads.ts`](../../apps/studio/src/electron-main/browser-view/downloads.ts). Every guest shares the one workspace browser session, so its single `will-download` listener attributes each download to the guest that started it. A guest the agent authorized through `Browser.setDownloadBehavior` (what agent-browser's `download` command sends) saves under the GUID that command waits for, and its completion is synthesized back as `Page.downloadProgress`. Any other download is the person's own click: a `<webview>` shows nothing of its own for one, so it lands where a download from any other browser would, their Downloads folder, under its own name, suffixed rather than overwritten, with no chooser. That folder is proved writable first, by writing and removing a file, because macOS asks once before an app may touch Downloads and remembers a refusal; the workspace's own `downloads/` stands in when it takes no file, and the download is canceled when nothing does. Either way the window hosting the guest gets a `browser.download-finished` event to say so ([`browser-download-notices.ts`](../../apps/studio/src/client/lib/browser-download-notices.ts)). Only a download from a guest no entry owns is canceled outright.

## A file on the computer has one address, for the person and the agent

An HTML file the person opens (from This Mac, a reply's card, the omnibar, or the chat's `tab open`) is shown in a guest of the app window at its `file://` address, which is what their own browser would do with the file: relative links resolve, and the tab row shows the file's place on the computer rather than the address. The file's text is a step away ("View source" in the page's menu opens it in the file viewer as code). The tab strip names the tab by the page's own title, or the filename when it has none. The file is watched while its tab is open (`files.live.info`, a stat on an interval by host path), and the guest reloads when it is written, so an agent's edit shows the way it would in a viewer of the file.

The Finder's tiles, rows and preview column show such a file as its page too, as a picture: [`rendered-pictures.ts`](../../apps/studio/src/electron-main/lib/rendered-pictures.ts) loads the file in a window nobody sees and photographs it, served on the file channel's `?thumbnail=` and kept on disk by the file's mtime ([`file-thumbnails.ts`](../../apps/studio/src/electron-main/lib/file-thumbnails.ts)); Markdown and code are typeset there the same way. A picture rather than a frame in the renderer because the person's file channel must never load a page as a document (a page can read its own address, token and all) and a `file://` frame in the app's own session would read the whole disk; the hidden window runs in a session of its own under the same local-page rule as the guests, with the network limited to the hosts the page skill draws from and no input, popups, navigation of its own, or sound. Quick Look shows the page live, in a guest like the tab's.

The agent opens a file at that same address. `agent-browser open work/report.html` (or `/mnt/Docs/page.html`, or `file:///task/work/report.html`) is rewritten by [`agent-browser-file-url.ts`](../../packages/workspace/src/lib/shell-commands/agent-browser-file-url.ts) to the file's real `file://` URL before the browser sees it, and everything the browser prints back is spelled in the agent's own paths again by [`local-page-address.ts`](../../packages/workspace/src/lib/local-page-address.ts), so `get url` answers `file:///task/work/report.html` and the host path never reaches the model. What the agent checks is therefore the page the person will see: the same bytes, the same address, the same guest, the same folder rule below. There is no server in between. An Electron guest gives a `file://` page what a stock Chromium withholds from one (module scripts, `fetch` and XHR of the files beside it, workers), so a page behaves there the way it would over http; the one difference that remains is that every `file://` page shares one origin, and so one `localStorage`. The eval harness, which has no window and lets the CLI start a stock Chromium, passes `--allow-file-access` to close that gap.

A page in Edit keeps that address too. The page editor ([`page-editor/sessions.ts`](../../apps/studio/src/electron-main/page-editor/sessions.ts)) loads the file's stamped copy at the file's own address with one parameter added, `?instrument-edit=<nonce>`, and a `file` protocol handler on the guest session answers exactly that address with the copy and passes every other `file://` request through to disk. Every guest shares the session and a request does not say which guest made it, so the nonce is what picks the copy. The parameter is taken out of everything that shows an address: the tab row, Copy URL, the way out to another browser, and what the agent reads back. The copy's history entries are removed when Edit ends, and an Edit address whose session has ended reads the file from disk.

`file://`'s root is the whole computer, so four rules keep a page from being a way to read the disk:

- **The agent opens only what its own tools can read.** The rewrite refuses a `file:` argument that names nothing in the task's layout, and the CDP bridge ([`cdp-bridge.ts`](../../packages/workspace/src/logic/server/routes/cdp-bridge.ts)) checks every `Page.navigate` or `Target.createTarget` to a `file://` URL against the same layout: under a mount, outside a mount's private directory, and not through a symlink that leaves the mount. `task new --tab` and `task tab` still refuse a tab whose page is a file, since a task reaches a file through its folders and never through a browser standing on one. The note the conversation gets for such a tab says which file is open and how the agent reaches it when a granted folder covers it, with no tab id to hand over.
- **A tab showing any other file is closed to the agent.** A page can still take its tab to another file (a link, a script setting `location`), and the person can open one in a tab the agent drives. The bridge tracks the main frame's address, and while it is a file the agent could not have opened it refuses every command but leaving the page or switching a domain's events, and withholds the events that carry the page's content (screencast frames, console, DOM). It starts closed on a new connection and opens only once it has read the task's layout and the tab's current address.
- **A local page reads only its own folder.** The guest has the network, so an agent-written page could otherwise read any file and send it anywhere. [`local-file-policy.ts`](../../apps/studio/src/electron-main/browser-view/local-file-policy.ts) cancels every `file://` subresource request (image, script, style, fetch, frame) that is not under the requesting page's folder, by name and by where the name really leads, so a symlink beside the page reaches nothing past it, and refuses the task's private directory anywhere. A main-frame navigation to another file is left alone by this rule; the rule above decides whether the agent may look at it. That holds in the guest only: a window a page opened (a sign-in popup) never loads a file, since its opener keeps a handle to it and every `file://` document shares one origin, so a local page could otherwise send its popup to `file:///etc/hosts` and read it.
- **A local page saves only its own folder's files.** A download never passes through the request filter, so `<a download href="file:///…">` would otherwise copy any file into a downloads folder the agent reads. `downloads.ts` cancels a `file://` download that is not under the page's folder, and answers agent-browser's `download` with a cancellation at once rather than letting it wait out its timeout.

## Ads and trackers are blocked by default

The guest blocks ads and trackers the way Brave does out of the box, through Ghostery's filter engine (`@ghostery/adblocker`) over EasyList, EasyPrivacy, Peter Lowe's list, and uBlock Origin's lists. [`content-blocking.ts`](../../apps/studio/src/electron-main/browser-view/content-blocking.ts) owns it; "Block ads" in a page's menu turns it off for the workspace, and the page reloads under the new choice.

- **One request listener, shared.** Electron keeps a single `onBeforeRequest` listener per session, and the library's own Electron wrapper registers its own, which would silently replace the local-file policy above. So the wrapper is not used: the file policy's listener hears every request and hands each non-`file:` one to `blockedRequestResponse`.
- **Requests and elements both.** Network rules cancel what a page loads; the engine's preload, registered on the guest session, asks for each page's hiding styles and scriptlets over IPC. Ads a search engine serves from its own origin, which no request rule can tell from results, are hidden by the second half.
- **A document is never blocked**, only what it loads, so every navigation the person or the agent makes lands.
- **The lists come from where each is published**, fetched at launch when the engine on disk (`content-blocking-engine.bin` under userData) is missing or a week old, with uBlock Origin's `!#include` lines followed. Not from the engine's own mirror of them in Ghostery's repository, which moves only when that repository's bot lands a commit and leaves out uBlock Origin's newer yearly lists. The scriptlet resources do still come from that repository, since they are built from uBlock Origin's source rather than published as a list. A failed fetch keeps the engine already loaded; with none on disk, pages load unblocked until a later launch fetches one.

## Focus

`webContents.isFocused()` is unreliable for `<webview>` guests — it can stay stuck `true` after focus moves to a plain host-page element. The manager therefore trusts renderer-reported DOM focus (`setGuestFocus` / `setHostFocus`) and uses it to route keyboard back/forward, reload, and zoom to the focused guest instead of the tab or the whole window. Window zoom is CSS-only (see [responsive-layout.md](responsive-layout.md)) and never reaches the guest's webContents, so guest zoom is a separate path.

Focus is also load-bearing for agent input, which is what makes this more than bookkeeping. A guest is an inner WebContents of the renderer, so the two share one focus tree, and Chromium delivers keyboard input to whichever widget holds focus rather than to the target whose debugger carried the command. A guest that does not hold focus cannot be typed into at all: the keystrokes go to Studio's own window. `dispatch-command.ts` therefore gates `Input.dispatchKeyEvent`, `Input.insertText`, and `Input.imeSetComposition` on the guest document reporting focus, and reclaims it first when it does not, refusing only if the guest never takes it. Reclaiming has to go through the renderer (`browser.focus-guest` → the pool's `focusGuest`), because DOM focus on the `<webview>` element is the only thing that moves keyboard focus across the process boundary: `webContents.focus()` on the guest does not, and neither does a page-level `focus()` inside it. The guest's own `activeElement` survives losing and regaining focus, so this lands the keys on whatever the agent last clicked. Mouse and scroll are routed by hit-testing and need no such check.

The reclaim exists because the agent's commands are separate tool calls seconds apart while host focus is handed back after a much shorter lull, so a guest the agent clicked has nearly always lost focus again by the time the keystrokes for it arrive. Refusing instead of reclaiming makes ordinary form entry impossible unless the agent happens to chain its click and its typing into a single shell command. See [cdp-keyboard-input-follows-window-focus](../findings/cdp-keyboard-input-follows-window-focus.md).

macOS Command chords are their own silent failure under CDP: macOS resolves them through the application menu, which an injected key event never reaches, so Chromium's editing layer takes the command from the event's own `commands` field instead. [`mac-editing-commands.ts`](../../apps/studio/src/electron-main/browser-view/mac-editing-commands.ts) attaches the right editing command per chord — without it, `press Meta+A` reports success and selects nothing. The clipboard chords (Meta+C/X/V) are deliberately absent, since routing them through this trusted path would hand a page the user's clipboard.

[`focus-guard.ts`](../../apps/studio/src/electron-main/browser-view/focus-guard.ts) keeps the user's caret through agent activity, and splits two questions that look alike. `isAgentDrivenCommand` marks any command as the agent driving the guest, which is what attributes a side effect such as a `window.open` to automation. `bouncesGuestFocus` is the narrower set whose focus transfer is refused on the user's behalf: navigations and explicit focus calls, whose pull on focus is incidental to what was asked for. Input is deliberately excluded from the second, since rejecting the focus a CDP click grants is what sends the agent's next keystroke into the app. Focus taken by agent input is handed back once the target has been quiet for the settle tail, so a click-then-type burst reads as one stretch of work instead of a fight over the caret.

## Which browser a chord means

Focus is not the only claim on a chord, because a guest can be on screen without holding keyboard focus — the common case, since clicking the chat or the URL bar hands focus back to the host. Cmd+F and Cmd+R therefore route by what the user is *looking at*: the browser panel on screen registers itself in [`foreground-browser-registry.ts`](../../apps/studio/src/client/lib/foreground-browser-registry.ts) while its guest is live, its tab is foreground, and no overlay covers it, and the window's command stream offers both chords to that panel. A focused `<webview>` swallows renderer keydowns, so these chords can only arrive as native accelerators through the main process — which is what the registry exists to bridge.

Cmd+R has no app-wide meaning at all: a claimed chord reloads the guest and an unclaimed one does nothing, and the app window's View menu leaves out the reload roles that would otherwise bind it to the window. Reloading the renderer destroys every guest with it — the `<webview>` elements go with the document, main reaps their entries, each task's browser comes back at `about:blank`, and the lifecycle machine closes the task's `agent-browser` sessions — which is more than anyone pressing Cmd+R is asking for. That reload is reachable on `reloadApp` (Cmd+Shift+R), whose Developer group binds only in developer mode, and on the button an app crash puts on screen. See [app-reload-destroys-the-task-browser](../findings/app-reload-destroys-the-task-browser.md).

## Lifetime

[`task-browser.ts`](../../packages/workspace/src/machines/task-browser.ts) supervises a task's browser as an XState machine with `Observed` / `Retained` / `Unobserved` / `GracePeriod` / `Stopping` / `Stopped` states. Which state it sits in is decided by the leases viewers hold, not by any event: `acquirePresence` / `releasePresence` only move counts, and eventless transitions on each live state route from there.

The renderer takes those leases through `browser.live.presence` in the workspace RPC, where subscribing *is* the hold and aborting releases it. There are two levels, and the difference between them is the whole design:

| Lease | Held while | Clock when it is the highest lease |
| --- | --- | --- |
| `visible` | the task page is on screen | none — `Observed` never reaps |
| `retained` | the task page is mounted at all | `RETAINED_TIMEOUT_MS` (8 hours) |
| none | — | `USER_PRESENCE_TIMEOUT_MS` (5 minutes), or `AGENT_IDLE_TIMEOUT_MS` (1 hour) from the last CDP heartbeat |

A task page the user turned away from is not one they abandoned, so backgrounding it costs the browser nothing for a working day; closing it drops the short clock on the browser within minutes. The browser panel holds both leases and gates `visible` on [`use-task-page-visible.ts`](../../apps/studio/src/client/hooks/use-task-page-visible.ts), which is the single place that knows the app currently draws one task per foreground tab. Nothing below that hook — not the machine, not the RPC — names tabs, so a shell that keeps pages alive some other way changes only the hook.

A reap is unobservable after the fact: the panel builds a new tab the moment it remounts, so a model that was driving a page finds a plausible-looking browser that is not the one it left. Teardown therefore records `closedAt` on the session's browser state ([`browser-state.ts`](../../packages/workspace/src/lib/browser-state.ts)), [`create-browser-status-part.ts`](../../packages/workspace/src/lib/create-browser-status-part.ts) reports it on the next user message and clears it, and `browser.open` puts a freshly built tab back on `lastUrl` — so the user gets their page back and the model is told it is a fresh load whose page state and snapshot refs are gone.

A page tab of the window's own comes back the same way. The panel showing it opens it with the address the tab remembers as `restoreUrl`, which `browser.open` uses only for a guest that comes up blank and only when its session recorded no page of its own; a session an agent drove comes back at the page it recorded. That one open is how a page returns after a launch, after its site tab is reopened, after a reap, and in a draft's band.

Sessions are torn down through `agent-browser-cleanup.ts`; see [agent-browser-orphaned-daemons](../findings/agent-browser-orphaned-daemons.md) and [agent-browser-ref-map-idle-ttl](../findings/agent-browser-ref-map-idle-ttl.md) for the failure modes that shaped it.
