# Windows

A person can have any number of app windows open on one workspace. They are full windows of the same app, each with a strip of tabs across its bar, and everything behind them (the workspace machine, the chats, the agents, the RPC routes) is one process they all talk to. Each window is its own `BrowserWindow` with its own renderer, Jotai store and React Query cache. For why they are separate renderers rather than one renderer drawing into several native windows, and why a chat can be open in two of them, see the [decision](../decisions/2026-11-03-windows-are-separate-renderers.md).

## Which window is which

[`windows/app-window.ts`](../../apps/studio/src/electron-main/windows/app-window.ts) keeps every open window by the id it keeps its state under: `app` for the first a workspace ever had, a fresh one for the rest. `getAppWindow()` is the window last in front, which is what the rest of the main process means by "the window"; `getAppWindows()` is all of them, front to back. A window's page learns nothing of its own id: main names a web contents as it makes it (`app-window-ids.ts`), and answers whatever that web contents asks with that window's own things.

## What belongs to a window, and what they share

| What | Where | Who sees it |
| --- | --- | --- |
| The strip of tabs, the drafts and chats floating over it, whether the inbox is out, the chat and folder Chat and Files in the rail go back to | `window` kept file, `window/windows/<id>.json` | That window alone |
| Each chat's, draft's and site's tabs and which is up | `layout` kept file, one key per group (`window-tabs.v10/<group>`) | Every window, live |
| How things are laid out (widths, views, zoom) | `view` kept file | Every window, live |
| Size and place, which windows are open and in what order, which can come back | `window/window-state.json` | Main |

A group is a chat, a draft or a site, which is the same thing whichever window shows it, so its tabs are kept by the group and not by the window. A window writes only the groups it changed (`keptMembersAtom`), because a write of the whole list from one window would undo what another wrote a moment before. Anything that lets go of a group has to remember that other windows share it: a window drops a site's group only when it held that group itself and no tab in another window stands on it, closed windows that can come back included (`siteGroupsInOtherWindows`), and the sweep of empty drafts at startup keeps those floating in any window.

## Asking one window

Almost everything main publishes for the windows is read by all of them (`liveRead` routes re-read for themselves), and that is right for state. A request to do something is not: `window.command` names a web contents, published through `commandWindow`, and the route hands each window only what names it. A chord goes to the window it was pressed in (`bindAppWindowChords`), and a menu row to the focused one.

What something outside the app asks for goes to the window that already has it (`appWindowShowing`, read from what each window keeps): a notification or a link to a chat brings that window and that tab forward, and otherwise it opens in a new tab of the window in front.

What an agent asks of a chat's tabs must be answered exactly once, or a page it opens would open per window, so each ask names one window as it goes out (`appWindowForChat`): of the windows whose page can hear it, the one showing the chat, else the one in front. A blank page an agent makes for itself goes to the same window. The workspace package asks through `WorkspaceConfig.windowForChat`, which a host with one window leaves out.

## Moving a tab

`moveTabOut` ([`move-tab.ts`](../../apps/studio/src/client/components/window/move-tab.ts)) hands a tab, history included, to main (`window.moveTab`), and takes it out of the strip only once another window has it. Main either writes it into the kept state of a window it then opens, which reads it as it loads, or sends it to the window as `receiveTab`, refusing a window whose page is not listening yet so a tab is never lost on the way. A window left with no tabs closes with nothing to come back to (`closeEmptiedWindow`). Move to New Window, Move to Window and Merge All Windows all come through here.

Tearing a tab off ([`tab-drag.ts`](../../apps/studio/src/electron-main/windows/tab-drag.ts), `useTabCarry` in `app-tab-strip.tsx`) moves nothing between renderers until the release, and usually not then, so going back to the row or Escape undoes all of it. The renderer keeps the drag and decides when the tab has left its row by where the pointer is heading as well as where it is (`tab-pull.ts`): a steep pull comes off about 10px past the row, and a sweep along the row gets more room. It captures the pointer as the drag starts, because a page runs in a process of its own and otherwise takes a pointer that crosses it, the release included. Main keeps one phase for the drag (`carryPhase`): on its row, free of every strip, or docked in another window's. Everything the drag shows is an effect of going into or out of a phase, or of following the pointer within one. Main reads the cursor itself, so the window's motion cannot feed back into the positions it is placed by.

The window that was pressed goes with the pointer, renderer and all, so the tab is simply left alone: its page, the words typed into it, its selection, scrolling and keyboard are never touched, because none of them move. The other tabs and the floats stay where they were in a spare window (`keepSpareReady`, `takeSpareWindow`): an ordinary app window kept booted and hidden, on none of the window lists, given them through the kept state the way a window coming back from a launch is, and standing beneath at the old bounds. Nothing holds a picture of anything: what is seen beneath is that window, on screen and drawn from the start of the drag, Linux aside, so that the pressed window is free to move the moment the tab leaves its row. Until then it is told it is beneath (`kind: "beneath"`), so a chat up in it does not count as read. Until the release the pressed window keeps every tab and draws only what `window.tab-carry` tells its strip to (`tabsInView`): the tab alone, or the tab among the tabs of the window it is held over. On the release it lets the others go (`keepOnlyTab`) and the spare window is adopted (`adoptSpareWindow`) as a window like any other, or goes back to being hidden if nothing changed. A window wholly covered by an opaque one counts as out of sight on macOS and stops drawing, so the pressed window is a shade short of opaque while it covers one that has to go on drawing. The tab that comes up beneath takes its page in the same step (`neighborPages`), and hands it back if the tab returns to the row, unless a person has used it, in which case it waits for the release.

The tab goes to the spare window instead, and the pressed window stays put, where that loses less or there is no choice (`whatGoes`): the tabs staying behind have a page a person has used and this tab has none (`hasUsedPage`, `isPageUsed`), the window is full screen, or the session cannot place a window. Out of a full-screen window the spare floats in that window's Space while the tab is held, unable to go full screen itself, since macOS would otherwise switch Spaces mid-drag, and on the release it goes full screen as the window it came from stands. A maximized window goes with the pointer like any other, at its own size, and the window left behind fills the work area in its place. On Linux only the pressed window ever goes with the pointer: a window of ours under the pointer takes the press's release, so the pressed window never hears the press end, and a window there has no opacity to keep it out of sight until it is wanted (one given an opacity stays a few percent see-through, so the drag gives it none). A tab going to the spare window stays showing in its strip through the drag and opens at the pointer on the release. A window manager there also keeps a window a program moves on screen, so a window following the pointer stops at the screen's edge. A Wayland session goes further, telling a window nothing of where it is and letting it place no window, so even the pressed window stays put, and Move to Window is the way into another window's strip. GNOME takes a window shown without focus to want attention, and says it "is ready", unless the window is off the taskbar, which the spare stays until it is adopted. X11 forgets that when a window is hidden, so on Linux a spare is shown only as the tab leaves its row, and one that has been shown is not used again.

Main answers which strip the point is over (`carryDestination`), since only it can see every window. Windows are tested front to back from the order they were last focused, because Electron cannot read the OS's stacking order, and a window covering a strip takes the release. Over another window's strip the carried window stands exactly over that one and shows both windows' tabs with the held one at the pointer, without loading any of them, and says where the tab stands (`placeTabDrag`), which is where it lands. Let go there, whichever side has less to lose is the one that reopens (`landsBy`): the carried window stays and takes on the other's tabs, which close that window, unless that window has a used page and the tab has none, in which case the tab goes to it the way a menu's move does, and the target is raised and the carried window closes only once the target has drawn the tab. With used pages on both sides the tab in hand wins, and the other page reloads when it is next looked at. A window's only tab leaves nothing behind and needs no spare window. The press that starts a drag has to reach the page, so app windows set `acceptFirstMouse`: without it the first press on a window behind another only brings it forward, and over the bar it drags the window. An instance kept off screen never shows a window and starts no spare until a drag asks for one, so a drag driven over CDP exercises the same path.

## A page is in one window

A page tab belongs to a group every window can see, but its guest is a `<webview>` in one renderer, and Electron cannot move one between renderers. So a page is in the window that showed it last. [`in-app-browser.md`](in-app-browser.md#a-page-is-in-one-window-at-a-time) has what that does to a guest.

## Coming back

A launch brings back every window that was open, each where it was with its tabs, the one last in front on top (`restoreAppWindows`). A quit leaves those records alone, so closing the app is what keeps them. Closing a window while the app runs moves it to what can come back: File › Reopen Closed Window, or Shift+Cmd+T once no closed tab is left to reopen. The last ten are kept; past that a window's file and place go. With every window closed on macOS, the Dock icon brings back the one closed last.

Closing a window quits the app only where it is the last one on Windows or Linux (`quitsWithLastWindow`), and asks about running work only then. While setup is up, only the window it draws over is open; the rest come back as it goes down, and New Window does nothing until then.
