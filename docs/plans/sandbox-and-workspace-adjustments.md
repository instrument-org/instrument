# Sandbox and workspace adjustments

Status: done. Landed. The agreed changes from the Windows sandbox (MXC) validation, each with what was decided and how it was built.

## Decided, built

1. **Work folders move to `~/.instrument/work/<workspace>/<chat>/` on every OS.** Built; every chat may use every work folder. What an agent makes for the person lives in the home folder, readable and recognizable (chat folders keep their date-and-title names; the workspace level is a readable name). Everything internal stays in the app's data folder (sign-ins, browser profiles, `workspace.db`, runtime). A chat opens only its own folder: sibling chats and other workspaces are closed by name. Fixes git and Windows PowerShell 5.1 under MXC, which refuse to work below a folder denied by name (`AppData`). Needs a migration from the current `work/` in the machine folder.
2. **Closed folders above an open one are list-only on Windows.** Built. Under MXC a folder denied by name breaks git and PowerShell 5.1 for anything open below it (a granted `Documents\Taxes` while `Documents` asks); a list-only folder does not. Programs can then see file and folder names there, never contents. Say so in the always-open places caveat on the Permissions screen.
   - Measured: a list-only folder shows names, sizes and dates across its whole subtree until a folder denied by name below it. In the app's shape that already lists `AppData\Roaming` and `AppData\Local`, including `Recent` (recently opened document names). Deny by name, below them, the folders that reveal the person's activity or hold sign-ins and that no chat needs.
   - Matching on other OSes, measured: macOS can list closed folders without reading files (`file-read-data` limited to directories, plus metadata), but its listing call always carries sizes and dates, so "names only" is not possible there; Linux can only show placeholders with fake sizes, or needs a new Landlock helper that leaks extended attributes and cannot keep a nested closed folder closed. No escape to contents or writes was found on any of the three. Whatever ships lists only folders set to ask, never sign-in places or folders set to never. The shell's own `ls` and globbing would change to match. Decided: Mac and Windows, as part of item 7.
   - Seatbelt trap: a rule naming one operation (`file-read-data`) beats a `file-read*` rule whatever the order; last-match-wins holds only between rules of equal specificity.
3. **Picking the Instrument folder feels like Obsidian**: hard refusals only where the app would break (its own data and install folders, `~/.instrument`, inside or around another workspace); everything else warns, and for the home folder or Documents, Desktop and Downloads themselves the warning offers a new `Instrument` folder inside as its main action. Earlier shape: the workspace folder check hard-refuses only a few places: the home folder, `~/.instrument`, the app's own data and install folders, and a folder inside or around another workspace. The rest (system folders, a disk's top, `Library`/`AppData`/`~/.config`) become a warning the person can go past. Drop the "a folder on a different disk from its parent" test. Built. Still hard-refused by the move alone: Documents, Desktop and Downloads themselves, sign-in folders, temporary folders.
4. **Product commands move under one `instrument` command** (`instrument chat`, `instrument app`, `instrument mail`, ...), since commands now fall through to real programs and `mail` and `chat` already hide real ones. Prompts, tool descriptions, tests and the skills repo change together; the registry pin moves with them. Built.
5. **`/tmp` behaves the way it does in Git Bash on Windows**: the shell's `/tmp` is the folder programs get as `%TEMP%`, held and unheld, rather than a new `C:\tmp`. The agent's Windows notes say a script should use the temp folder its language gives it. Built.
6. **pnpm's install step runs outside the sandbox** with scripts off, for registry package names only; package scripts run inside afterward. One path on every OS. Built.

## Permissions cleanup

Carried over from the permissions cleanup track, so there is one list with one owner.

7. **App files are look, don't touch** (`~/Library`, dotfolders, `AppData`): programs see names, sizes and dates there; opening or changing a file asks for that one app's folder ("Let Instrument use "Code"?"). Sign-in and startup places stay closed and unlisted. Linux shows nothing there, since bubblewrap cannot show names without contents. The shell's own `ls` and globbing match. Built. `~/Library/Containers` and `Group Containers` stay unlisted, since macOS may ask the person before a program looks into another app's container.
8. **Stop closing `~/Library/Caches`** (`toolCaches` in `native-sandbox/host.ts`). Not by adding it to `toolCaches`: those open at rank 3 in the Seatbelt and bubblewrap profiles, deeper than the App files rule on `~/Library`, so a person setting App files to Not allowed would be overruled. Make it a rule beside App files that follows the person's level, with browser caches (`Caches/Google/Chrome`, `com.apple.Safari` and the like, which hold cached pages) closed by name with the other sign-in places. Built, with the updaters' download caches closed as the app's own data.
9. **Drop the dangerous-names list in allowed folders and the Linux walk** (`walk.ts`, the walk stamps in `mxc.ts`). Built; `AppData\Local\Packages` is no longer opened either, since a held program's TEMP is the person's own.
10. **Honor `~/.npmrc` (decided: read-only, in the sandboxed path) and drop per-tool cache variables** (`MPLCONFIGDIR`, `HF_HOME`, `U2NET_HOME`, `XDG_CACHE_HOME`). The install that runs outside the sandbox (item 6) keeps its own config and store, because any config it reads can redirect the registry or load a pnpmfile, and pnpm hardlinks store files into projects, so a store a chat can write would reach the person's own `node_modules`. The sandboxed path may read `~/.npmrc` read-only. Dropping the cache variables follows item 8. Built; model caches stay in `~/.cache`.
11. **List the always-open places at the bottom of Settings › Permissions**, including the Windows entries (`AppData\Local\Programs` read-only) and item 2's caveat that names are visible in list-only folders. The places the agent can always reach because the product needs them: the chat's own work folder, the work folders under `~/.instrument`, tool caches. Built.

## Decided, not doing

- App-provided `clipboard` and `open` commands. The app already opens files in their own programs, and a clipboard write the person may miss is stateful in a way that rarely helps.
- A native helper for the Windows ssh-agent pipe. Key files in `~/.ssh` work.

## Folded in

- When the person picks a refused place such as the home folder, offer `<that folder>/Instrument` instead, show the path, and say whether it already has things in it or already holds a workspace. Built as item 3's folder inside. See [choose-where-instrument-keeps-files.md](choose-where-instrument-keeps-files.md) and [instrument-folder.md](instrument-folder.md).
- Turn MXC on by default: built, after a preview passed real chats on the test PC. `tasklist` runs outside the container, read-only, so the agent sees every process (`tasklist.exe` by that spelling still runs held). The start cost (about 150 ms per held program against 90 ms measured earlier) is still unexplained; [windows-sandbox-mxc.md](windows-sandbox-mxc.md) tracks it.
