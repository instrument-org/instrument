# Agent sandbox

`instrument` is an Electron desktop app where users chat with an AI agent that operates inside a per-task folder. The agent is **not** in a VM, container, or OS sandbox. It runs as ordinary code in the Studio main process on the user's machine. "Sandboxing" here means a layered set of _userland_ constraints, picked so the user never has to approve individual tool calls.

For why this userland approach was chosen over OS-level isolation, see the [decision record](../decisions/2026-07-15-userland-agent-sandbox.md).

## Tools and where they live

The main agent (`packages/workspace/src/agents/main.ts`) gets a fixed set of tools from `packages/workspace/src/tools/`: `EditFile`, `ReadFile`, `WriteFile`, `Glob`, `Grep`, `BashTool`, `WebSearch`, `GenerateImage`, `LoadSkill`. Each tool's `execute` runs as host Node.js code; sandboxing is implemented _inside_ each tool, not by the runtime.

## The virtual filesystem layout

`packages/workspace/src/lib/workspace-fs-layout.ts` defines what the agent can see, shared by the file tools, the bash sandbox, and the native-binary path bridge: the task dir mounts **writable at `/task`** (the working directory), the workspace's own `skills/` dir mounts **writable at `/skills`**, user-attached folders mount **read-only under `/mnt/<name>`**, and everything else is an empty read-only base (writes outside the mounts fail EROFS). See `docs/architecture/bash-sandbox-mounts-and-native-binaries.md` for the design constraints and known quirks.

`/skills` is created rather than skipped when the directory is absent, so the agent never writes to a mount the prompt advertises but that does not exist. It is writable on purpose: authoring a skill is a user-facing feature, and a skill saved there is immediately loadable by `LoadSkill`. See the [decision record](../decisions/2026-07-20-skills-as-a-mount-not-a-tool.md). Like `/mnt`, it sits outside the task root, so the native-binary path bridge quarantines it: python/ffmpeg/scripts cannot reach it, and running a skill's script means loading the skill and running the copy under `work/skills/<source>/<name>/`. The source segment (`instrument`, `claude`, and so on) records provenance rather than another skill hierarchy, prevents namesakes from merging, and is included in every path `LoadSkill` returns.

## Containment layers (strongest -> weakest)

1. **Path-constrained file tools** (`ReadFile`/`WriteFile`/`EditFile`/`Glob`/`Grep`): paths resolve through the workspace layout (`src/lib/resolve-agent-path.ts`) — task-relative or `/task/...` into the task, `/mnt/...` into attached folders (reads only, with symlink containment); anything else is rejected. Write tools refuse read-only mounts.
2. **just-bash builtins** (`BashTool` via `src/lib/create-bash-env.ts`): a TypeScript bash interpreter running against the mounted virtual FS built from the same layout. Standard unix commands (`cat`, `sed`, `awk`, `jq`, etc.) are reimplemented in TS and only see the virtual FS. Also blocks JS escape vectors and prototype pollution. See `reference/just-bash/THREAT_MODEL.md`.
3. **`agent-browser` flag/subcommand policy** (`src/lib/shell-commands/agent-browser.ts`): the harness owns daemon session identity and config/plugin-registry discovery (`--session`, `--config`, `--namespace`, `AGENT_BROWSER_PLUGINS`, plus a managed empty `--config` so the agent-writable task dir's `agent-browser.json` is never discovered) and blocks meta subcommands (`auth`, `plugin`, `state`, etc.). By default invocations route to the Instrument task browser through a `browser.provider` plugin (`src/lib/agent-browser-plugin.ts`, `AGENT_BROWSER_PROVIDER=instrument`); connection-targeting flags (`--cdp`, `--auto-connect`, `--provider`, `--profile`, `--state`) pass through and route the invocation to a sibling `-ext` daemon session against an external browser. Screenshot/download paths are rewritten into the task dir. Page-level behavior inside Chromium is currently unrestricted, and external-browser invocations act on real browsers (including the user's running Chrome) with no additional gate beyond skill guidance.
4. **Real-binary escape hatches** — `pnpm`, `tsx`, `ffmpeg`, `git`, `uv`/`python`/`python3`/`pip`, custom commands in `src/lib/shell-commands/`, and `curl`. These shell out to the real `node`/binary via `execa`. Once running, they have the host user's full FS, network, `process.env`, and `child_process` access. just-bash's containment does not extend here. Their **argv paths** are bridged through `resolveNativeHostPath`: `/task/...` maps to the real task dir; every other virtual path (notably `/mnt` mounts, whose host paths must never reach a writable subprocess) quarantines to a nonexistent path inside the task dir. **Inline program text** gets the same treatment (`bridgeInlineCodePaths`): quoted `/task/...` string literals in `-e`/`-c` code and heredoc programs are rewritten to cwd-relative paths, and quoted `/mnt/...` literals fail fast with copy-first guidance. **Script files on disk** are scanned but never rewritten (`scanScriptFileForVirtualPaths`): the entry file a `node`/`tsx`/`python` invocation runs is checked for the same quoted `/task/...`, `/task/.instrument/...`, and `/mnt/...` literals and fails fast with guidance instead of the confusing host error they otherwise produce (a `/task/...` literal dies with "Read-only file system: '/task'"). Files are reported, not rewritten, because a script is the agent's own artifact — silently diverging what runs from what it wrote is worse than an up-front error; it is best-effort guidance, not a boundary. Subprocess **stdin** crosses as raw bytes (`subprocessStdin`) — handing just-bash's latin1-packed stream string to `execa` would UTF-8 re-encode every non-ASCII byte. The subprocess **temp dir** (`TEMP`/`TMP`/`TMPDIR`, set in `resolveCommandContext`) points at a task-local `work/tmp`, so `tempfile`/`os.tmpdir()`/`mktemp` land inside the task instead of the host temp dir. `curl` is enabled with `dangerouslyAllowFullInternetAccess: true`.

   **Git.** Same trust level as the other hatches. Two pieces: `src/lib/git.ts` holds the environment that isolates git, and `src/lib/shell-commands/git.ts` is the `git` shell command's argv policy on top of it. Both use the git distribution dugite ships, located via dugite's `setupEnvironment()` (which also supplies `GIT_EXEC_PATH`, templates, and the CA bundle). It must be listed in electron-builder's `asarUnpack`, since a binary inside the asar cannot execute.

   `gitSubprocessEnv()` is merged into `resolveCommandContext` **and** `execaNodeForTask`, so it reaches every task subprocess rather than only the shell command. That is deliberate: `<userData>/bin` (where `setupBinDirectory` puts a `git` symlink for the user's apps) and `/usr/bin` both hold a `git` that a script can invoke by bare name, so isolation anchored to one command shim would leave those uncovered — and stripping those directories from `PATH` would make it worse, since the fallback is a host git that reads the user's real config and keys. It also prepends dugite's `bin` so a bare `git` resolves to the same binary the shell command uses.

   It **deletes every inherited `GIT_*` it does not own**, rather than overriding a fixed list. The agent controls the shell environment, and `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` alone sets any config key with no argv involved at all; `GIT_DIR`, `GIT_EXTERNAL_DIFF`, `GIT_INDEX_FILE`, and `GIT_ALTERNATE_OBJECT_DIRECTORIES` each reach a capability the argv checks exist to deny. The config triple is owned rather than deleted, which comes to the same thing: `GIT_CONFIG_COUNT` is pinned at `1` and slot 0 is spoken for, so a `KEY_1` the agent exported names nothing and its `KEY_0` loses to ours. What it keeps or sets:

   - `GIT_ALLOW_PROTOCOL=http:https` is the load-bearing control. When that variable is set it is the _only_ transport check git makes, so no `-c protocol.*.allow` can widen it. Excluding `ssh` keeps the user's keys and ssh-agent unreachable, excluding `ext` closes remote-helper command execution (`ext::sh -c ...`), and excluding `file` stops the agent cloning repositories from elsewhere on the host.
   - `GIT_CONFIG_GLOBAL=""` skips `~/.gitconfig` and the XDG config — `resolveCommandContext` restores the real `HOME`, so git would otherwise inherit the user's identity, credential helpers, and `url.insteadOf` rewrites. `GIT_CONFIG_NOSYSTEM=1` covers `/etc/gitconfig` on macOS and Linux, where dugite's bundled system config is just an `include` of it; Windows keeps dugite's minGit system config because it carries the TLS/CA settings.
   - `GIT_TERMINAL_PROMPT=0` with `GIT_ASKPASS`/`SSH_ASKPASS` set to `""` rather than unset. Git reads `GIT_ASKPASS` first and only falls through to `core.askPass` and `SSH_ASKPASS` when it is absent, so `""` both blocks an inherited helper and runs nothing. Without it, `GIT_TERMINAL_PROMPT=0` would suppress the terminal prompt only for a GUI one to answer it.
   - `GIT_EDITOR`/`GIT_SEQUENCE_EDITOR` set to `false`, which outrank `core.editor`/`sequence.editor` and so hold even against a repo config the agent wrote. `GIT_ATTR_NOSYSTEM=1` keeps a system gitattributes from naming a diff/merge driver.
   - Commits are authored and committed as `GIT_AGENT_NAME`/`GIT_AGENT_EMAIL`, so history never attributes agent work to the user.
   - `GIT_CONFIG_COUNT=1` with slot 0 holding `core.longpaths=true`, so a bare `git` reaches Windows files through the Unicode `\\?\` APIs instead of the 260-character `MAX_PATH` ones. See `docs/findings/windows-long-paths.md` for why the task prefix makes that mandatory and what it does not cover.

   The `git` shell command adds three things an env var cannot express. **Forced config**, prepended as `-c` to every invocation: command-line config outranks every config file, so `credential.helper=` resets the helper list a `git config credential.helper store` would otherwise build (reaching `~/.git-credentials`, the keychain, or the credential manager dugite ships on `GIT_EXEC_PATH`), and `core.longpaths=true` holds even for a clone of a repository that ships the key set to `false`. **Config-key rejection** over both `-c`/`--config-env` (each accepted by git in attached _and_ space-separated form) and `git config <key> <value>`, which writes the same keys into the repo for every later invocation — needed because forced config cannot pre-empt an arbitrary `alias.<anything>`. **Path containment** for `-C`/`--git-dir`/`--work-tree`/`--file`/`--template` values and for leading-`..` positionals (`git init ../../x`). The containment fold matters: git resolves each non-absolute `-C` relative to the preceding one, so `-C .. -C .. -C ..` climbs three levels while three independent per-value checks each see one harmless `..`.

   The net capability is public clone/fetch over http(s) plus local history and commits. Private repositories and pushing need credentials and are therefore unavailable; see `docs/decisions/2026-07-21-git-without-user-credentials.md` before wiring any up. Two consequences of the protocol allowlist worth knowing: cloning one task-local repo into another (`git clone work/a work/b`) fails with `transport 'file' not allowed`, since that is the same transport a `file:///Users/...` URL would use and path containment does not inspect URLs; and there is no editor, so a commit without `-m`/`-F` fails rather than hanging (`GIT_EDITOR=false`). `collapseProgress` keeps only the last state of git's carriage-return progress redraws, which otherwise arrive as a single ~20 KB line that line-based truncation cannot trim.

   **What this does not claim.** The argv layer applies to the `git` shell command only; a script that runs `git` itself gets the environment but not the argv policy. Since that script could equally read `~/.git-credentials` directly — `HOME` is the user's real home for every hatch — the argv layer is defense in depth against the easy path, not a boundary. Likewise, a repo's own `.git/hooks` are writable through the file tools and run on `git commit`; `core.hooksPath` being on the denylist does not change that, and it is capability-equivalent to the `node`/`tsx` baseline.

   **Python (`uv`).** Same trust level as the `node`/`pnpm` hatches, not a new boundary. The bundled `uv` binary (`src/lib/uv.ts`; vendored into `apps/studio/resources/uv/` by `apps/studio/scripts/download-uv.ts`) runs `python`/`python3`/`pip` against a per-task virtualenv at `work/.venv`. `uvSubprocessEnv()` pins uv to isolated dirs under `app.getPath("userData")` (`UV_CACHE_DIR`/`UV_PYTHON_INSTALL_DIR`/`UV_TOOL_DIR`) so just-bash's `HOME=/` never sends it writing to the host home, ignores host config (`UV_NO_CONFIG=1`), and only uses a managed CPython (`UV_PYTHON_PREFERENCE=only-managed`, downloaded on first use). `uv self update` is blocked; everything else passes through. The overlay is also merged into the other hatches' env so a tsx/node script can shell out to `python`/`uv`.

## Soft layer

The agent system prompt in `src/agents/main.ts` asks the LLM to behave (refuse malicious code, stay within the task folder, etc.). It is not a security boundary.
