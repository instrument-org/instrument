# Agent sandbox

`instrument` is an Electron desktop app where users chat with an AI agent that works inside the chat's work folder and can start background tasks, each a session of the same chat working in the same folder. The agent runs as ordinary code in the Studio main process on the user's machine, in no VM or container. What holds it to the person's wishes is one set of rules, Settings › Permissions, applied at every layer: in the process for the shell's own commands and the file tools, and by the operating system for the programs it starts, through Seatbelt on macOS and bubblewrap on Linux. Where the system offers no such wrapper (Windows, an AppImage, a host process already sandboxed), the programs it starts follow the rules only as far as Instrument can read their command lines, and Settings says so.

For why the first version was userland only, see the [decision record](../decisions/2026-07-15-userland-agent-sandbox.md). For why the agent now works at real paths and what that replaced, see [the decision](../decisions/2026-10-11-the-agent-works-at-real-paths.md).

## Tools and where they live

The one agent (`packages/workspace/src/agents/instrument.ts`), which runs a chat and each of its tasks, gets a fixed set of tools from `packages/workspace/src/tools/`: `EditFile`, `ReadFile`, `WriteFile`, `BashTool`, `WebSearch`, `WebFetch`, `GenerateImage`, `LoadSkill`, plus `Choose` and `ConnectApp` for asking the user. There is no tool for asking for a folder: running into one the rules keep closed raises the card itself (`raiseAsk` in `permissions/asks.ts`). File discovery and search are not tools: they live in the shell, on the real `rg` binary (see the [decision record](../decisions/2026-07-28-real-ripgrep-in-the-sandbox.md)). Each tool's `execute` runs as host Node.js code; the rules are applied _inside_ each tool, not by the runtime.

What differs between a chat and a task is the shell, not the tools. A chat's shell adds the `task`, `chat`, `memory`, and `tab` commands and reaches the workspace's `.instrument/apps/` folder; a task's has none of those (`create-bash-env.ts`), and the task's own turn tells it that no question, folder request, or app card reaches the user from there.

## What decides reach

The rules live in `packages/workspace/src/lib/permissions/`. Every layer below asks the same question of a host path: may the agent read it, may it change it.

- **The rules** (`rules.ts`) are a list of `{ path, level, source }`. A level is Allowed, Ask first or Not allowed, which are the three a person sets, or `readOnly` (readable, never changeable), which the app sets for its own folders. `reachOf` finds the deepest rule holding a path, by the path the rule names or where that path really is, and that rule decides; at an equal depth the rule closing the app's own data outranks every other, the app's own rules outrank a chat's grant, which outranks a folder rule, which outranks a built-in place, and a rule naming one hidden entry of a folder outranks the rule for all of them (`ruleRank`, which both native profiles order by too). A path no rule holds is readable and asks before it changes, and so is a path in the home folder whose deepest rule is an allow above the home, since the native profiles close the home to changes beneath every rule above it. "Use folders without asking" turns every Ask first into a yes but the sign-in folders' (below), which hold sign-ins rather than work; nothing turns a Not allowed into anything else. Matching is without case on macOS and Windows, and a path on the Mac's Data volume (`/System/Volumes/Data/Users/...`, joined to `/` by firmlinks that `realpath` leaves alone) is matched as the rest of the system spells it (`withoutDataVolume`); Seatbelt matches the path the kernel resolved, so it needs no such step.
- **Built-in places** (`places.ts`) are the folders every computer starts in: the output folder (always allowed), Desktop, Documents, Downloads, iCloud Drive and other drives, other apps' files (`~/Library` and the home folder's hidden entries on macOS, `~/AppData` on Windows, the home folder's hidden entries on Linux), and the passwords place. Each starts at Ask first except the output folder. The passwords place holds two lists: the folders where command-line tools keep sign-ins (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.azure`, `~/.config/gcloud`, `~/.kube`, `~/.docker/config.json`, `~/.netrc`, `~/.git-credentials`, `~/.config/gh`, `~/.config/op`, `~/.password-store`), which take the place's level and so ask first by default, and the places that hold every sign-in at once (the Keychain, cookies, browser profiles, 1Password's data), which stay Not allowed unless the place is set to Allowed. A sign-in folder is asked for whole, a file such as `~/.netrc` by itself, whatever path in it the agent ran into, and a grant of `~/.ssh` also passes the app's `SSH_AUTH_SOCK` to native commands and opens the ssh-agent's socket in the Seatbelt profile, which refuses connecting to it otherwise, and binds it back under bubblewrap, which otherwise covers it. The person changes a place, adds a rule for a folder of their own, and flips the switch above in Settings › Permissions (`rpc/routes/permissions.ts`, stored in `permissions.json` in the workspace's machine folder, since its paths are this computer's).
- **A chat's grants** are Allowed rules that win at an equal depth (`chat-rules.ts`). A grant comes from a folder sent with a message or from an allow on the card the agent raises by running into a folder (`rpc/routes/permissions.ts`); "Always allow" on the card also writes a folder rule, so every chat has it. A chat also holds, without a grant, its topics' folders.
- **The app's own folders** are rules too, ranked above everything the person sets (`layoutRules` in `workspace-fs-layout.ts`). The app's own data is closed (`appData` rules, Not allowed): this computer's folder (`WorkspaceConfig.machineDir`, Electron's userData: the app's Chromium profile, the registry of workspaces, the runtime folder, each workspace's machine folder with its keys, browser profiles, folder rules and work folders) and the workspace's `.instrument/`. The workspace's folder around that is the person's: once they picked it, it is the output folder, and it follows their rules and the output folder's like any folder. A folder holding this computer's folder whole (the home folder) mounts read-only as a whole, and one inside the app's own data too (`effectiveFolderAccess`); a folder holding only a workspace's `.instrument/` carries its grant. Inside the app's own data only the app's own rules open anything: the chat's own work folder (`work/<id>/` in the workspace's machine folder), Allowed; in its record folder (`.instrument/chats/<id>/`) `attachments/`, `readOnly`, and `handoff-notes.md`, Allowed; the skills (read-only for what the app ships and what other agents left, Allowed for the workspace's own `.instrument/skills/`); for a chat the `.instrument/apps/` folder; the runtime folder's `caches/` and `config/`, Allowed; and its `python/`, `skills/`, `environments/`, `preload/` and `bin/`, `readOnly`. Its `build/` stays closed: what the app builds or loads from it every chat then runs, so no chat may write it, and only a build the app runs for a chat reaches it (below). Everything else there, its own `chat.db` and `settings.json`, other chats' records and work folders, `workspace.json`, `preferences.json`, the keys and the browser data, is refused plainly, with no card and a note saying it is the app's own data and that the chat's work folder and what the person sent stay open (what the person sent sits inside that data, and a note that only closes the way in talks the agent out of reading it): a person's rule inside it is dropped (`layoutRules`), one on a folder holding it (a card's yes to `~/Library/Application Support` or the home folder, Settings allowing `/`, folders used without asking) is outranked by the deeper rule that closes it, and a card for something beside it never names a folder that holds it (`folderToAskFor` names the folder below it, and `ruleRefusal` raises none where that cannot be done, `holdsAppData`). The folders above an open one answer a `cd` and a `stat` but are not listed. The same rules reach the Seatbelt and bubblewrap profiles, so a program the agent starts is refused there too. A chat's records are not in the folder it works in, so a program the agent starts there finds no record of the chat beside its files.
- **What the agent is told** when a rule stops it is spelled out with the path: a Not allowed place says it is closed in Settings and not to look for another way in; an Ask first place raises a card for the folder (`folderToAskFor`: one level below the place, so the person sees a folder they made rather than all of Documents) and tells the agent it is waiting on the person; a read-only folder says to copy out what it needs. One function, `ruleRefusal` (`permissions/rules-fs.ts`), says all of this and raises the card, for the shell's own commands, the file tools, the commands that check their operands, a path outside every folder the shell reaches, and a native command the system stopped, so a path is asked for the same way whichever of them met it. The person's answer wakes the agent, and once they allow the folder every session of the chat reaches it.

## The layout

`packages/workspace/src/lib/workspace-fs-layout.ts` builds what a chat's shell reaches, shared by the file tools, the shell, `rg`, `du`, `git`, and the agent's browser. Every folder is at its real path on the disk, spelled as the shell spells it (`shellPath`): the same on macOS and Linux, and `/c/Users/sam` for `C:\Users\sam` on Windows, as Git Bash does, converted back at the edge (`hostPathOf`). Paths shown to the person stay in the host's form.

- **The chat's work folder** is the shell's working directory and the file tools' base for a relative path, for the chat and for every task it starts alike (`workDir` in `lib/work-dir.ts`, `work/<id>/` in the workspace's machine folder). It is made by the chat's first command, and again, empty, by a later one once it was removed, which the app does when the chat and its tasks come to rest with nothing in it (`reapWorkDir`: no session of the chat running and nothing it left running in the background, and only a `.DS_Store` counts as nothing). It is always allowed, and nothing is scaffolded into it. A relative path under `attachments/` the work folder does not hold is read where the person's files are, in the record folder. The shell names the folders the agent works with (`FOLDER_VARIABLES`): `INSTRUMENT_WORK` this folder, `INSTRUMENT_ATTACHMENTS` the record folder's `attachments/` (none for the window), `INSTRUMENT_OUTPUT` the output folder, and `INSTRUMENT_SKILL_DIR` the folder of the skill the session loaded last (`lastLoadedSkillDir`), which every native command gets too, in the host's spelling (`resolveCommandContext`).
- **The chat's record folder** (`.instrument/chats/<id>/`, `layout.record`), for its `attachments/`, which the agent reads, and its `handoff-notes.md`, which it writes. Everything else in it is refused. The window, which keeps no such records, has none in its layout.
- **The folders the chat reaches** (`folderReach` in `lib/chat/folder-reach.ts`): the home folder and the output folder always, the folders granted in the chat, the folders of the topics it is filed under, and the folders Settings › Permissions allows everywhere, the folders of a place of work set to Allowed among them (Desktop, Documents, Downloads, iCloud Drive, the drives). The home folder is reachable so the agent can look around and then ask for the right folder; the built-in places in it ask before the agent reads them, and changing anything outside a grant asks first.
- **The skill sources**, each at its own directory. The two bundled sources share the prepared copy of the skills in the runtime folder's `skills/`, since the app bundle is signed and replaced wholesale by the updater. Only the workspace's own `.instrument/skills/` is writable, created when missing, and wrapped in `skillWriteTrackingFs` so edits to a skill are attributed. `load_skill` copies nothing: it names the folder the skill is read and its scripts run from, and the app builds the dependencies of what it ships and of the workspace's own skills in the runtime folder's `environments/`, read-only to every chat (`skill-environments.ts`; Python and pnpm below). See the [decision record](../decisions/2026-07-20-skills-as-a-mount-not-a-tool.md).
- **The workspace's `.instrument/apps/` folder**, writable, for a chat only; a task reaches its apps through the `app` command.
- **The system's temp folders** (`/tmp`, `/var/tmp`, and `os.tmpdir()`, at both their spelled and real paths), writable, each held by a system allow rule so the native profiles open them as well; a deeper rule (a workspace or a planted home inside one) still decides there.
- **`/dev`**, a small in-memory stub (`null`, `zero`, `stdin`, `stdout`, `stderr` as plain writable files, rebuilt per call) so `cmd > /dev/null` resolves instead of dying with EROFS.
- **Everything else** is a read-only base (`read-only-base-fs.ts`) that reads the disk where the rules allow reading (the system's own folders and anything no rule holds; empty on Windows), held to the rules at a path and where it really leads, and walked against the home folder's budget. A write outside the folders (`/opt/x`) fails with EROFS and says where files can go, instead of succeeding and evaporating when the call ends.

A folder inside one already reached is reached through the outer mount, because just-bash's `MountableFs` refuses a mount inside another (`mountRoots`). In practice the home folder holds nearly everything: the chat's work folder, the workspace, the skills, `apps/`, and a grant under home all sit inside it, so one read-write mount of the home folder serves them and the rules say what in it is open. A read-only mount (`OverlayFs`) is used for a read-only source only when no writable one sits inside it. The writable mounts are `ReadWriteFs`, because `OverlayFs` copies on write into memory and the filesystem is rebuilt per bash call, so a `mv` into a folder would report success and leave the person's files alone. [bash-sandbox-mounts-and-native-binaries.md](bash-sandbox-mounts-and-native-binaries.md) has the mount design and its quirks.

## Containment layers (strongest -> weakest)

1. **Path-constrained file tools** (`ReadFile`/`WriteFile`/`EditFile`/`GenerateImage`): a relative path resolves inside the chat's work folder (an `attachments/` one it does not hold, in the record folder), and an absolute one through the layout (`src/lib/resolve-agent-path.ts`) to the mount that owns it, read where a migration moved it when it is gone from where it was (`remapMovedPath`). Both are asked of `classifyHostPath`, the one answer every consumer holding a host path takes: the mount it is reached through and whether a symlink takes it out of the mount. A path in a folder the chat reaches is then held to the person's rules, the chat's grants and the app's own rules (`ruleRefusal`, shared with the shell; the app's own data is refused as such, never reported missing), a write to a read-only skill source is refused, and a path in no folder the chat reaches is rejected.
2. **just-bash builtins** (`BashTool` via `src/lib/create-bash-env.ts`): a TypeScript bash interpreter running against the mounted filesystem built from the layout. Standard unix commands (`cat`, `sed`, `awk`, `jq`, etc.) are reimplemented in TS and see only that filesystem. Each mount is wrapped in `rulesFs` (`permissions/rules-fs.ts`), which asks the rules before every read, write, listing, copy and move: a refused path throws `EACCES` naming the path and the reason. A builtin reports any failed read as a missing file, so `create-bash-env.ts` collects the refusals during a call and appends them to the call's stderr, with the path spelled out ([just-bash-upstream.md](just-bash-upstream.md) says why). The home folder's listings run against a smaller traversal budget than the chat's own folder. `du` is the exception that does not go through the interpreter's walk: `shell-commands/du.ts` resolves each operand through the same layout, refuses one the rules keep from the agent and a symlink out of its mount, and walks the real directories in a worker thread, because the builtin's walk over a large folder runs on the main thread and spends the whole traversal budget without answering. It does not ask the rules for what it measures. Anything it does not implement falls through to the builtin. The interpreter also blocks JS escape vectors and prototype pollution; see just-bash's own `THREAT_MODEL.md`, reachable through the `just-bash` agent reference. The network commands (`curl` among them) are just-bash builtins too, not host binaries, and they fetch through just-bash's own `network` config: every address is open, the internet and the local network alike, loopback included, with the body capped at the sandbox's byte limit. `WebFetch` and app requests reach the same addresses. Instrument's own workspace server is on loopback too and guards itself: its model proxy and CDP bridge each require a per-launch secret the sandbox never holds ([decision record](../decisions/2026-10-10-the-workspace-server-guards-itself.md)). The shell's own `PATH` names no folder it mounts, so a binary in the home folder cannot shadow a command registered under the same name.
3. **`agent-browser` flag/subcommand policy** (`src/lib/shell-commands/agent-browser.ts`): the harness owns daemon session identity and config/plugin-registry discovery (`--session`, `--config`, `--namespace`, `AGENT_BROWSER_PLUGINS`, plus a managed empty `--config` so the agent-writable chat folder's `agent-browser.json` is never discovered) and blocks meta subcommands (`auth`, `plugin`, `state`, etc.). By default invocations route to the in-app browser through a `browser.provider` plugin (`src/lib/agent-browser-plugin.ts`, `AGENT_BROWSER_PROVIDER=instrument`). Connection-targeting flags (`--cdp`, `--auto-connect`, `--provider`, `--profile`, `--state`, `--executable-path`) and the `profiles` subcommand are refused: the in-app browser is the only browser, since a Chrome the person is using exposes no debugging port to reach their live sessions. Screenshots land in the chat's `screenshots/` and downloads in its `downloads/`, both in its work folder. An `upload` operand must exist in the shell's filesystem and is passed on in the host's spelling, which Chromium requires. A page the agent opens by a file path is loaded at its real `file://` address, and the CDP bridge checks every navigation to a `file://` address against the chat's layout (see [in-app-browser.md](in-app-browser.md)). Page-level behavior inside Chromium is currently unrestricted, and page content the CLI returns arrives as the CLI prints it, with no boundary markers ([decision record](../decisions/2026-10-09-outside-content-arrives-last-and-unmarked.md)).
4. **Native commands**: `pnpm`, `node`, `ffmpeg`, `git`, `uv`/`python`/`pip`, `rg`, `osascript` (macOS only), and the other custom commands in `src/lib/shell-commands/`. These shell out to the real binary through `execShim` or `execaNodeForChat`, with their arguments exactly as the agent typed them (on Windows an absolute path in the shell's spelling becomes the host's, `hostPathArgs`) and the shell's current directory, which starts as the chat's work folder, as the working directory. Once running they have the host user's network, `process.env` and `child_process`; what holds their files is the operating system, from the same rules. The agent's two script runtimes are among them: `python` (alias `python3`) is the interpreter of the `.venv` nearest the shell's folder, or the managed Python's own where none is near, and `node` is Electron run as Node, so a script has whatever was installed and is held to the same profile as any other binary ([decision record](../decisions/2026-10-12-python-and-node-run-native.md)). A `node` script also gets a `tools` global for calling a connected app's tools as values: `node.ts` passes `--import` with a preload (`node-tools-preload.ts`, written by the app into the runtime folder's `preload/`, which every native command reads and none changes, so no chat can change what another chat's `node` loads) and spawns the script with an IPC channel, and each call goes over that channel to the `node` command, which answers it through the shell's `invokeTool`, the same checks `app call` makes. No port or token is added to the sandbox, and only the process `node` started has the channel.

   **Programs on the PATH.** A name no builtin and no command of ours answers runs the program by that name on the computer's PATH (`shell-commands/path-program.ts`), searched first match first for a regular file this user may execute, or on Windows for the name with each PATHEXT extension in turn. The PATH is the one a native command runs with: the app's own, which holds its bin folder, with the virtualenv nearest the shell's folder, where there is one, and the bundled uv ahead of it. just-bash asks for the program only once its own lookup misses, through the `resolveExternalCommand` option our patch adds ([just-bash-upstream.md](just-bash-upstream.md)), so a builtin, a function, or one of our commands keeps its name, and a program of the same name is reached only by its path. A name with a `/` runs natively when it names a script with a `#!` line or a Mach-O, ELF or PE binary; an executable file with neither is a shell script, and just-bash runs it as a shell would. The program runs through `execShim` like every native command, with the environment allowlist, the shell's directory, stdin, cancellation and background streaming, under Seatbelt or bubblewrap; a `.bat` or `.cmd` goes through `cmd.exe`. `command -v`, `type` and `hash` answer from the same lookup, and `which` (ours) asks `command -v`, so each names what will run: a program by its path, one of our commands by the program it runs (`python3` by the interpreter it runs in the work folder, `git` by the bundled git; `COMMAND_PROGRAMS` in `create-bash-env.ts`), and a just-bash builtin or a command of ours with no program of its own as a shell builtin (`file is a shell builtin`, `command -v file` prints `file`), through the `registeredCommandPath` option the same patch adds. A name found nowhere is `command not found` with status 127. On a Mac without Apple's Command Line Tools, a developer tool stub (`make`, `cc`, `/usr/bin/python3`, `xcrun`) runs like any program and fails, since the profile keeps it from asking for the installer, and `execShim` adds a line saying the person installs the tools. There is no list of programs and no card per program: the folder rules hold a program the way they hold `python`. A command we wrap with checks of its own (`git`'s argv policy, `osascript`'s app check, `agent-browser`'s flags) has them only under its bare name; the same binary run by its path gets the folder rules and the environment, as it would from a script. See the [decision record](../decisions/2026-10-12-programs-on-path-run-natively.md).

   **macOS: Seatbelt.** Every spawn runs under `/usr/bin/sandbox-exec` with a profile `seatbeltProfile` builds from the rules (`src/lib/native-sandbox.ts`). It allows everything by default, so system directories, devices and services stay where a binary expects them, and then, ordered shallow to deep because the last matching rule wins, denies changes anywhere in the home folder and lets each rule open or close its folder: a folder allowed inside a place that asks is open, and one closed inside it is closed again, the same answer `reachOf` gives. A path is written in both spellings where a symlink lies on the way. Opened regardless of the rules (`nativeReachFor` in `permissions/chat-rules.ts`, `toolCaches`): the chat's work folder, the apps folder for a chat, and the runtime folder's `caches/` and `config/` for reading and changing; the skills, the runtime folder's `bin/` (with the folders its links lead to), and its `python/`, `environments/` and `preload/` (the managed Pythons, the skill environments and the `node` preload), which no chat may change since every other chat runs them, for reading; and `~/Library/Caches` for both. The runtime folder's `build/` is opened to one command alone, a build the app runs for the chat (`buildFolders` in `run-uv.ts` and `run-pnpm.ts`): its `caches/` for reading and changing, its `config/` for reading. The app's own pnpm, uv and node-gyp keep their stores, caches and config in the app's folders rather than the person's, so nothing else in the home folder is opened for them. A name that runs code when its folder is used (`.git/hooks`, `.gitconfig`, `.vscode`) stays closed to changes everywhere but the app's own folders, and Apple Events and opening apps are denied (see `osascript` below), as is the launchd service the `/usr/bin` developer tool stubs ask to show the Command Line Tools installer, so no command can raise that dialog however it clears its environment ([finding](../findings/macos-command-line-tools-dialog.md)). The profile binds every process the command starts, a `python` script's own `subprocess` included. It is built from the person's rules, the chat's reach and the app's own rules, the closed app data among them; a chat's records are not in the folder it opens either, so nothing has to be masked there ([finding](../findings/private-dir-masking-is-not-a-boundary.md)). Measured at about 6 ms a spawn.

   **Linux: bubblewrap.** The same rules become `bwrap` arguments (`bwrapArgs`): the whole system as it is, the home folder read-only, then each rule's folder bound back from shallow to deep, read-write, read-only, or replaced by an empty folder or an empty file when it is closed. A closed folder that a folder opens inside can only be passed through: it holds what opens in it, with the folders on the way there searchable and no more, and nothing else, so a program naming anything else there finds it missing, and the note below says why. Nothing a closed folder holds is listed to build the arguments: bubblewrap refuses more than 9,000 of them, and a stand-in per entry would reach that once a workspace holds about a thousand chats. The login session's runtime folder (`XDG_RUNTIME_DIR`, `/run/user/<uid>`) is an empty one: it holds the session bus, through which `systemd-run --user` would start a command outside the sandbox, and the ssh and gpg agents' sockets, which sign with keys the rules may keep closed. The ssh-agent's socket is bound back once the rules reach `~/.ssh`, and one elsewhere (`/tmp/ssh-…`) is covered until then. A socket in the abstract namespace has no path, so this does not reach one; blocking `socket(AF_UNIX)` with seccomp, as some sandboxes do, would take a helper the app does not ship and would break programs that talk to their own children over a socket. The home folder's hidden entries have no pattern form, so they are listed and closed by name. A folder the person allowed by name before it existed (the card a refused `git init ~/newproj` raises) is made before it is bound, where the folder holding it is there. Names that run code have no pattern form either, so each folder bound read-write for the person (not the app's own folders) is searched, breadth first, three folders down and at most 10,000 entries, skipping `node_modules`, without following links and stopping at any folder another rule decides (`namesThatRunCode`, `WALK_LIMITS`). Each name already there is bound read-only, and so is each repository's `hooks` folder, or an empty read-only one where a repository has none, which leaves an empty `hooks` folder behind as `git init` would. Each `.git`, and every folder between a found name and the allowed folder, is bound onto itself: a mount point cannot be renamed or removed, so a command can neither move `.git` aside and write hooks into it, nor swap the repository's folder for a copy with hooks planted. A name that is not there yet stays open to being made (`.envrc`, `.vscode`, `.mcp.json`, each of which its own tool asks the person to trust before running), as does a repository the same command makes; the next command finds and binds them. On an Apple-silicon Mac the search takes about 9 ms a command over a folder of 4,000 files, and its cap holds a larger one to about 13 ms. The command runs in its own process namespace (`--unshare-pid`), so what it leaves running dies with it when the app quits, and behind a `bash -p` step that closes every descriptor it inherited but its standard streams and Node's IPC channel: on Linux a spawned program inherits whatever the app holds open without close-on-exec (Chromium's databases and sockets, the debug port), and an open descriptor reaches past every closed folder. macOS needs no such step, since libuv spawns there with every descriptor closed on exec. `bwrapAvailable` probes once; Ubuntu closes user namespaces to unprivileged programs, and the `.deb` installs an AppArmor profile for the app that opens them for it and what it starts, while an AppImage installs none and runs unwrapped.

   **`agent-browser`** is spawned directly rather than through `execShim`, so neither profile holds it; its flag and subcommand policy (layer 3) is what does.

   **Elsewhere**, and wherever Seatbelt does not nest (the host process is itself sandboxed), native commands run unwrapped. Only an answer from the system is kept: a probe that times out or cannot start is logged and run again by the next command, and the command it was for is refused (`NativeSandboxUnavailableError`) rather than run unwrapped. Settings › Permissions reads `enforced` from the same probes and says plainly that the list is followed as closely as Instrument can there. The one command-line check is `git`'s, below.

   **When the system stops a command.** A command that fails with a refusal naming a path the rules keep from it gets a line appended to its stderr (`refusedPathIn`, `refusalNote`): a closed place says so and tells the agent to bring it to the person, an Ask first place names the folder to request and says to run the command again after the card. A command that exits 0 caught its refusal itself (a script printing the error it handled), so it gets the line only for a path in the app's own data that its stderr names, and never a card. Under bubblewrap a name in a closed folder that something opens inside is missing, and the home folder is read-only, so there the same refusal can read as a missing file or a read-only disk, capitalized or not (Node and Go write `no such file or directory`), and the note is found from the path the message names; a missing file in the app's own data gets it whatever the exit code. A path the message says was a folder being made (`mkdir`'s wording) is asked for as that folder, even directly in the home folder, as is the folder `git init` or `git clone` is given; a file directly in the home folder raises no card, since none opens the home folder whole.

   **What a hatch prints** reaches the agent through `filterShellOutput`, which redacts credentials (a token in a URL's userinfo, git's `password=` and `username=` lines) and, on Windows, turns backslashes into slashes. Paths are not rewritten: what a tool prints is the path it was given. Subprocess **stdin** crosses as raw bytes (`subprocessStdin`), because handing just-bash's latin1-packed stream string to `execa` would UTF-8 re-encode every non-ASCII byte. The subprocess **temp dir** (`TEMP`/`TMP`/`TMPDIR`) is the system's, as the shell exports it, respelled for the host in `resolveCommandContext` with the folder variables (`INSTRUMENT_WORK`, `INSTRUMENT_ATTACHMENTS`, `INSTRUMENT_OUTPUT`).

   **The user's other apps** are reached through Apple Events, and only through `osascript`. The Seatbelt profile denies sending Apple Events and opening apps, so a command could not have another app do what the profile keeps from it. `osascript` (`shell-commands/osascript.ts`) reads the apps its script tells, holds each to the app rules in Settings › Permissions (an app that asks raises a card, as a folder does), refuses a script that has an app run code outside it (`runsCodeOutside`), and runs unwrapped only when every app it tells is allowed; a script that tells none runs inside the profile. The app claims `com.apple.security.automation.apple-events` and names a reason in `NSAppleEventsUsageDescription`, and macOS asks the user once per app it controls.

   **macOS privacy prompts** for anything a native command does (Screen Recording for `screencapture`, Camera, Contacts) name Instrument, not the program. The program is the app's own child, started through `sandbox-exec`, which applies the profile and then runs it in place, and macOS holds the app that started a process responsible for its privacy requests. A permission the person grants is Instrument's, for everything it runs, and the agent is told to name the setting for Instrument itself.

   **Stored secrets.** Studio's stores encrypt with Electron's `safeStorage`, whose key on Windows (DPAPI) and Linux (libsecret) any process running as the same user can use, so these hatches can decrypt the session, provider keys, and app credentials on those platforms; only the macOS keychain's per-app ACL keeps the key from them.

   **Git.** Same trust level as the other hatches. Two pieces: `src/lib/git.ts` holds the environment that isolates git, and `src/lib/shell-commands/git.ts` is the `git` shell command's argv policy on top of it. Both use the git distribution dugite ships, located via dugite's `resolveGitBinary()`, with `setupEnvironment()` supplying `GIT_EXEC_PATH`, templates, and the CA bundle. It must be listed in electron-builder's `asarUnpack`, since a binary inside the asar cannot execute.

   `gitSubprocessEnv()` is merged into `resolveCommandContext` **and** `execaNodeForChat`, so it reaches every task subprocess rather than only the shell command. That is deliberate: `<userData>/runtime/bin` (where `setupBinDirectory` puts a `git` symlink for the user's apps) and `/usr/bin` both hold a `git` that a script can invoke by bare name, so isolation anchored to one command shim would leave those uncovered — and stripping those directories from `PATH` would make it worse, since the fallback is a host git that reads the user's real config and keys. It also prepends dugite's `bin` so a bare `git` resolves to the same binary the shell command uses.

   It **deletes every inherited `GIT_*` it does not own**, rather than overriding a fixed list. The agent controls the shell environment, and `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` alone sets any config key with no argv involved at all; `GIT_DIR`, `GIT_EXTERNAL_DIFF`, `GIT_INDEX_FILE`, and `GIT_ALTERNATE_OBJECT_DIRECTORIES` each reach a capability the argv checks exist to deny. The config triple is owned rather than deleted, which comes to the same thing: `GIT_CONFIG_COUNT` is pinned at `1` and slot 0 is spoken for, so a `KEY_1` the agent exported names nothing and its `KEY_0` loses to ours. What it keeps or sets:

   - `GIT_ALLOW_PROTOCOL=http:https` is the load-bearing control. When that variable is set it is the _only_ transport check git makes, so no `-c protocol.*.allow` can widen it. Excluding `ssh` keeps the user's keys and ssh-agent unreachable, excluding `ext` closes remote-helper command execution (`ext::sh -c ...`), and excluding `file` stops the agent cloning repositories from elsewhere on the host.
   - `GIT_CONFIG_GLOBAL=""` skips `~/.gitconfig` and the XDG config, which would otherwise hand git the user's identity, credential helpers, and `url.insteadOf` rewrites. `GIT_CONFIG_NOSYSTEM=1` covers `/etc/gitconfig` on macOS and Linux, where dugite's bundled system config is just an `include` of it; Windows keeps dugite's minGit system config because it carries the TLS/CA settings.
   - `GIT_TERMINAL_PROMPT=0` with `GIT_ASKPASS`/`SSH_ASKPASS` set to `""` rather than unset. Git reads `GIT_ASKPASS` first and only falls through to `core.askPass` and `SSH_ASKPASS` when it is absent, so `""` both blocks an inherited helper and runs nothing. Without it, `GIT_TERMINAL_PROMPT=0` would suppress the terminal prompt only for a GUI one to answer it.
   - `GIT_EDITOR`/`GIT_SEQUENCE_EDITOR` set to `false`, which outrank `core.editor`/`sequence.editor` and so hold even against a repo config the agent wrote. `GIT_ATTR_NOSYSTEM=1` keeps a system gitattributes from naming a diff/merge driver.
   - Commits are authored and committed as `GIT_AGENT_NAME`/`GIT_AGENT_EMAIL`, so history never attributes agent work to the user.
   - `GIT_CONFIG_COUNT=1` with slot 0 holding `core.longpaths=true`, so a bare `git` reaches Windows files through the Unicode `\\?\` APIs instead of the 260-character `MAX_PATH` ones. See `docs/findings/windows-long-paths.md` for why the task prefix makes that mandatory and what it does not cover.

   The `git` shell command adds three things an env var cannot express. **Forced config**, prepended as `-c` to every invocation: command-line config outranks every config file, so `credential.helper=` resets the helper list a `git config credential.helper store` would otherwise build (reaching `~/.git-credentials`, the keychain, or the credential manager dugite ships on `GIT_EXEC_PATH`), and `core.longpaths=true` holds even for a clone of a repository that ships the key set to `false`. **Config-key rejection** over both `-c`/`--config-env` (each accepted by git in attached _and_ space-separated form) and `git config <key> <value>`, which writes the same keys into the repo for every later invocation — needed because forced config cannot pre-empt an arbitrary `alias.<anything>`. **Path containment** for `-C`/`--git-dir`/`--work-tree`/`--file`/`--template` values and for leading-`..` positionals (`git init ../../x`), which must stay inside the chat's work folder or a folder it reaches. The containment fold matters: git resolves each non-absolute `-C` relative to the preceding one, so `-C .. -C .. -C ..` climbs three levels while three independent per-value checks each see one harmless `..`.

   **Folders the chat reaches** get no special route: git is handed real paths (`-C <repo>`, `--git-dir=<repo>/.git`, or a `cd` into the folder), and the OS profile above is what holds the files it touches. Before a command that writes, the shell command asks the rules for a write at its working directory and at each absolute path argument (`ruleRefusal`), and where they refuse, git may only read there: `READ_SUBCOMMANDS` and the listing forms of `branch`, `tag`, `remote`, `stash` and `config`, with `--no-optional-locks` forced so `status` and `diff` stop refreshing the index. Where the rules allow a write, git gets the whole command line, since committing in a folder the person granted is what they granted it for. See `docs/decisions/2026-09-11-git-reaches-attached-folders.md` for what was weighed and the pointer-file reach it leaves open.

   The net capability is public clone/fetch over http(s) plus local history and commits, in the chat's work folder and in the folders it reaches. Private repositories and pushing need credentials and are therefore unavailable; see `docs/decisions/2026-07-21-git-without-user-credentials.md` before wiring any up. Two consequences of the protocol allowlist worth knowing: cloning one task-local repo into another (`git clone work/a work/b`) fails with `transport 'file' not allowed`, since that is the same transport a `file:///Users/...` URL would use and path containment does not inspect URLs; and there is no editor, so a commit without `-m`/`-F` fails rather than hanging (`GIT_EDITOR=false`). `collapseProgress` keeps only the last state of git's carriage-return progress redraws, which otherwise arrive as a single ~20 KB line that line-based truncation cannot trim.

   **What this does not claim.** The argv layer applies to the `git` shell command only; a script that runs `git` itself gets the environment but not the argv policy. Since that script could equally read `~/.git-credentials` directly, the argv layer is defense in depth against the easy path, not a boundary; on macOS and Linux `~/.git-credentials` is closed to every native command by the OS profile until the person allows it on its card. Likewise, a repo's own `.git/hooks` are writable through the file tools and run on `git commit`; `core.hooksPath` being on the denylist does not change that, and it is capability-equivalent to the `node` baseline.

   **Python (`uv`).** Same trust level as the `node`/`pnpm` hatches, not a new boundary. The bundled `uv` binary (`src/lib/uv.ts`; vendored into `apps/studio/resources/uv/` by `apps/studio/scripts/download-uv.ts`) runs `python`/`pip` against the `.venv` nearest the shell's folder, looked for up to the work folder's root, or the one at that root for a command run outside it (`nearestVenv`). With none near, `python` runs the managed interpreter itself, with the standard library alone and the person's user site-packages off (`PYTHONNOUSERSITE`), and `pip` or `uv pip` makes the venv at the work folder's root first (`venv.ts`); a venv whose base Python is gone is made again wherever it is. A script in a skill's folder (the runtime folder's `skills/`, a Node skill's built copy, the workspace's skills) runs in that skill's environment instead: one relocatable virtualenv per `uv.lock`, in the runtime folder's `environments/`, which the app builds on the skill's first load or script, held to the asking chat's reach with only the folder being built opened to it, and builds again once its base Python is gone. Every package in it is checked against the hash its `uv.lock` records (`uv export` with hashes, `uv pip install --require-hashes`), an sdist as much as a wheel. A skill the app ships is built from uv's cache in the runtime folder's `build/caches/`, which no chat reaches (`uvBuildSubprocessEnv`), so nothing a chat put in its own cache ends up in what every chat runs; the workspace's own skills, which any chat can change, are built from the chats' cache as their own installs are, into environments named apart (a shipped skill's is `shipped-<hash>`), so one never stands in for a shipped skill's however the two lock. Anything else run where no `.venv` is near runs in the environment of the skill loaded last, and `uv run --project <skill>` runs in the skill's own (`UV_PROJECT_ENVIRONMENT`, with `UV_NO_SYNC`, since no chat may change it). The two are layered, so the skill's packages and what `pip install` put in the nearest `.venv` are both found (`skillPythonToRun`): a skill's script, and `uv run --project <skill>`, get that `.venv`'s site-packages after the skill environment's own, and anything else run in a `.venv` gets the site-packages of the skill loaded last after the `.venv`'s, so the skill's pinned versions win in its scripts and the agent's own installs win in its code. The layer is a `sitecustomize` the app writes to a folder of its own in `environments/`, put first on `PYTHONPATH`, with `INSTRUMENT_EXTRA_SITE_PACKAGES` naming the folder it adds (`pythonLayerEnv`): `site` imports it after adding the interpreter's own site-packages, and `site.addsitedir` appends the folder after them and runs its `.pth` files, where a `PYTHONPATH` entry would go ahead of them. It takes its own folder off `sys.path` again, then runs the `sitecustomize` it stands in front of where there is one (none of the managed Python, the environments the app builds and a `.venv` `uv venv` makes ships one, but a Python elsewhere on the computer or a package may), adds nothing in a Python of another version, and reaches every Python the script starts, which inherits both variables. `uvSubprocessEnv()` pins a chat's uv to the runtime folder under `app.getPath("userData")` (`UV_CACHE_DIR` and `UV_TOOL_DIR` in its `caches/`, `UV_PYTHON_INSTALL_DIR` in its `python/`) so its caches and managed Pythons stay out of the person's home folder, ignores host config (`UV_NO_CONFIG=1`), and only uses a managed CPython (`UV_PYTHON_PREFERENCE=only-managed`), pinned to 3.12 (`MANAGED_PYTHON_VERSION`) because the newest CPython runs ahead of the scientific/ML wheel ecosystem and uv's resolver silently backtracks to ancient, unbuildable deps on it. The app installs that Python itself, outside any chat's reach and from the build folders' cache, before a chat's first `uv` command or virtualenv (`ensureManagedPython`), since no chat may write the folder it lands in. A connected app's local Python server, which runs outside every chat's sandbox from the environment `uv tool run` keeps in its cache, uses the same cache. A chat's uv runs with `UV_PYTHON_DOWNLOADS=never`, so asking for another version fails, with a line saying only 3.12 is available. The same overlay points `HF_HOME`/`U2NET_HOME`/`XDG_CACHE_HOME` into the runtime folder's `caches/`, so model downloads stay out of the host home. `uv self update` is blocked; everything else passes through. The overlay is also merged into the other hatches' env so a node script can shell out to `python`/`uv`.

   **pnpm.** The bundled pnpm runs as Electron's Node with its store, caches and config in the runtime folder, and its settings for every install the agent makes as `pnpm_config_*` variables (`nodeToolsEnvFor` in `tool-isolation-env.ts`): a release younger than a week is not installed (`minimumReleaseAge`, refusing a version within it), a dependency's install script nobody allowed is skipped with a warning (`strictDepBuilds` off; the bash tool then says to run `pnpm approve-builds <name>` where it was installed), and `pnpm run`/`exec` start no install of their own (`verifyDepsBeforeRun` off). A project's own `pnpm-workspace.yaml` can still change them for that project. The work folder is no package of its own: `pnpm add` in a folder with no `package.json` makes one there, and in a folder under one adds to that one, as pnpm does anywhere; on macOS and Linux the folders above the work folder are closed to it, so its search for one stops there. A skill with Node dependencies runs from a copy the app builds in the runtime folder's `environments/`, one per version of the skill, with its production packages installed beside its scripts as its lockfile has them (`--frozen-lockfile`), where Node finds them. A skill the app ships is built with its own store, caches and config in the runtime folder's `build/` (`nodeBuildEnvFor`), which no chat reaches, so a setting a chat writes in `config/` (a registry, a `globalPnpmfile`) or a package it changes in the store never reaches that build; the workspace's own skills are built with the chats' as their own installs are, into copies named apart; a script of the agent's own goes in the work folder, with what it imports added there.

## Soft layer

The agent system prompt in `src/agents/instrument.ts` tells the model it reaches the person's files at their real paths, that the home folder is open to look through, and that changing anything in it or opening a place kept closed until asked shows the person a card on its own. It also asks the LLM to behave (refuse malicious code, work in the chat's folder, etc.). It is not a security boundary.
