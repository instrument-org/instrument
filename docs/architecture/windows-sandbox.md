# The sandbox on Windows

What holds the agent to Settings › Permissions on Windows, what MXC adds when it is on, and what it still leaves open.

## What holds everywhere

The agent's own tools follow the Permissions rules on every platform: the shell's builtins (`cat`, `ls`, `cp`, and the rest) and the file tools check each path against the rules before they touch it, refuse what is Not allowed, and ask before a folder marked Ask first. `rg` is the real ripgrep binary, which nothing sandboxes on Windows without MXC: the paths it is given are checked against the rules and its walk leaves the app's own data out, but it reads what the person can. The shell spells a Windows path the POSIX way, `D:\Photos` as `/d/Photos`, and converts it back at the edge for native commands and for anything shown to the person.

## Native programs

A native program the agent runs (`python`, `node`, `uv`, `pnpm`, `git`, `ffmpeg`, uutils, anything on the PATH) is held by the operating system on macOS (Seatbelt) and Linux (bubblewrap), from the same rules. On Windows that is Microsoft's MXC (`@microsoft/mxc-sdk`), wherever the app ships its launcher and the canary below passed on that machine; `INSTRUMENT_MXC=0` in the app's environment turns it off. Otherwise native programs run with the person's own access, so a script can read or change any file the person can, and Settings › Permissions says so in plain words, with a link to this page.

### How MXC holds a program

`wrapNativeCommand` (`lib/native-sandbox/index.ts`) returns MXC's launcher, `wxc-exec.exe`, which Studio ships alone in `resources/mxc/` (`apps/studio/scripts/download-mxc.ts`, pinned by hash; it is signed by Microsoft and needs nothing else from the package). `launchNative` then builds the request once the working folder and environment are known, since the container inherits neither from the launcher, and every caller spawns through it.

The request asks for MXC's process container (Tier 1) and nothing else: no fallback that would add entries to the ACLs of the person's folders. UI stays on, since anything importing USER32 (node, Electron run as node) fails to start without it; the clipboard and input injection stay closed. The network is open, as it is to native commands everywhere. A held program runs at low integrity, with the administrators group deny-only.

The disk is three lists, deny by default, where the deepest entry holding a path decides, as `reachOf` and the Seatbelt profile decide (`mxcFilesystemPolicy`, `lib/native-sandbox/mxc.ts`): the system drive readable, the home folder readable, each rule's folder opened or closed, the reach's own folders (the chat's work folder, the runtime's caches, the skills), the app's install folder readable, and the sandbox's own folder closed so no program can forge the canary's verdict. A folder closed above an open entry is named in `enumeratePaths` rather than denied by name, so a program can `lstat` its way down to what it may read (Node's realpath looks at every folder on the way), and git and Windows PowerShell 5.1 work in the open folder: a folder denied by name anywhere above the working folder makes `git init`, `git status` and `git commit` fail (`failed to stat '<pad>C:/Users/x/<denied>': Permission denied`) and PowerShell 5.1 start in `C:\`. MXC lets a program list an enumerated folder and stat every name in it (size, dates) all the way down, until a folder denied by name; it refuses reading, changing, renaming or linking anything there. So a folder that asks first with a granted folder inside it (`Documents` around a granted `Documents\Taxes`) shows its names to a program the agent runs, never what is in them. `AppData`, the app-files place, is enumerated while it asks first whatever opens below it: a program sees the names, sizes and dates in it and opens nothing, and opening a file there raises a card for that one app's folder, the first below `Roaming`, `Local`, `LocalLow` or `Local\Packages` (`AppData\Roaming\Discord`). The app's own data is listed only on the way to a folder programs work in (the work folders in `~/.instrument/work`, the runtime's caches), and each folder in it off that way is denied by name, so its keys, profiles and records show nothing. A folder set to Not allowed is treated the same way: `AppData` set to Not allowed is listed only on the way to `Local\Programs` and the app's install, with every folder off that way denied by name, so the names in `AppData` and `AppData\Local` show and nothing below them. The places in `AppData` whose names say what the person has been doing (recent files and jump lists, Office's recent files, PowerShell's history, the web cache and history, the activity history) and Windows' own sign-in stores (`Credentials`, `Protect`, `Vault`) are denied by name too, with the browsers' profiles (`placePaths`). A closed folder with nothing open below it stays denied by name, and a denied folder inside another denied one is left out: the deny above closes it already. The policy is built once per set of rules and reused while what it read on disk is unchanged.

The canary (`mxc-canary.ts`) decides whether MXC holds on this machine, not a Windows build number: one real run of the app's `node` through the same generator and launcher must read a granted file, turn an open file back into its drive-letter path ([microsoft/mxc#1464](https://github.com/microsoft/mxc/issues/1464), fixed in a Windows update rather than in MXC), and be refused a folder the rules close. Its verdict is kept per Windows build and per launcher, so an update probes again. A canary that fails leaves commands unwrapped with the notice; one that gives no answer is tried again, and the command it was for is refused rather than run unwrapped.

### What the container changes, and what the app does about it

- **Node's look for a package.json.** Node looks for a package.json in every folder above a script and fails outright when the sandbox refuses the read of one, where a missing file would do; under MXC every folder above the work folder and a granted folder is closed. The preload every `node` the agent runs imports (`node-preload.ts`) reads past that refusal, only once Node has hit it: `module.registerHooks` resolve and load hooks (the load hook for the script `node <script>` starts, which the preload sends through the ES module loader with no format), and the CommonJS loader's `.js` handler, which reads the module type before any hook runs, all carry on as Node does with no package.json. A Node another program starts has no preload; its command is told that a package.json beside the script ends the look.
- **`instrument` in a script.** Node's IPC handle does not reach a held program, so a `node` script's `instrument` global and a `python` script's `import instrument` reach the command that started them over loopback TCP with a per-process token, on every platform. The token reaches a held program in its environment, since no handle reaches it through the launcher; the request carrying it goes to the launcher in a file in the sandbox's own folder, removed once the script connects, rather than on the launcher's command line, which any process can read.
- **Folders under `AppData` programs keep for themselves.** `AppData\Local\Programs`, where per-user installs go (Python from python.org, VS Code), is readable to every chat; the rest of `AppData` is listed and asks first to open a file, `AppData\Local\Packages` included, which holds packaged apps' data and sign-ins (Teams, Mail, a desktop app's own web profile). Windows still starts a held program with `LOCALAPPDATA` in a container profile of its own under `Packages`, which the container may write without any rule, and TEMP and TMP back at `%TEMP%`.
- **Links an install makes.** A held program may not make a symlink or a junction, and pnpm's `node_modules` is junctions on Windows. An install from the npm registry runs its install step outside the container and the install scripts it skipped inside, the same on every platform ([agent-sandbox.md](agent-sandbox.md), pnpm). An install that has to stay inside (a `file:` or git dependency, a workspace, a pnpmfile) cannot make its links there.
- **`uvx`** runs the app's own uv as `uv tool run`, with the managed Python, rather than whatever `uvx` is on the PATH.

### What it leaves open

- **The ssh-agent.** OpenSSH's agent listens on a named pipe that admits authenticated users, and a held program is not admitted, so `ssh` in a chat allowed `~/.ssh` finds no agent. A pipe the app relays through would need a DACL that admits `ALL APPLICATION PACKAGES` as well as Everyone, which Node cannot set: its `readableAll`/`writableAll` add Everyone alone, and a held program is still refused (`EPERM`); `icacls` cannot change a pipe's DACL.
- **What goes through a broker.** A held program runs at low integrity, so what Windows serves through another process is refused or comes back empty: the clipboard (also with `ui.clipboard: "all"` in the request), opening a file or link in its default app (`start` does nothing for a file and waits until killed for a link; `Start-Process` is refused), WMI and CIM (`Get-CimInstance`, `Get-Printer`, `Get-Volume`, `systeminfo`), other processes (`Get-Process` sees only the command's own; `tasklist` runs outside, [agent-sandbox.md](agent-sandbox.md)), ICMP (`ping`), the credential store (`cmdkey /list` shows none), writes under `HKCU` (`reg add`, `setx`) and new scheduled tasks. The measurements are in the [plan](../plans/windows-sandbox-mxc.md).
- **Each start costs time.** A held program starts about 150 ms later than an unwrapped one in an installed build, and a pipeline pays that once per stage. The measurements are in the [plan](../plans/windows-sandbox-mxc.md).
