# Workspace package

Core AI agents, workflow logic, RPC, and tools.

## Structure

- **RPC**: Router in `src/rpc/index.ts`. Handlers in `src/rpc/routes/`. Base and `toORPCError` in `src/rpc/base.ts`. Exposed to Studio as `workspaceRouter` via `@instrument-org/workspace/electron`.
- **Streaming**: every `eventIterator` procedure goes under `live.*` (snapshot on subscribe, then updates) or `events.*` (fires only on change), and nothing else does. A `live.*` mirror of a non-live procedure shares its leaf name: `chats.info` / `chats.live.info`. A live view of records re-reads on `recordChanges` (`lib/record-changes.ts`), which the write layers publish; do not add a topic or a hand publish for a record write.
- **Tools**: `src/tools/`. Each is a capability (`defineCapability` in `lib/capabilities/define.ts`) with a `surfaces.tool`, made a model tool by `modelTool()` (`lib/capabilities/tool.ts`); register in `all.ts`. Its name, description and input schema are pinned by `tool-definitions.test.ts`, since they open the prefix a provider caches. Fallible logic returns a `Result`; map it to tool output, or throw for oRPC.
- **Result library**: the repo's standard is `typescript-result` (the `typescript-result` skill), as in `packages/ai-gateway`. Code here that composes with functions still returning neverthrow's `Result` (`ChatReads`, `ChatWrites`, the shell commands, tools) stays on neverthrow rather than converting at every call; a module with no such neighbors uses `typescript-result`.
- **Agents**: one agent, `instrument` (`src/agents/instrument.ts`, wired by `create-agent.ts`, its tools picked from `TOOLS`), runs every chat and task session. In a chat it does quick work itself with every tool, and `instrument task new` (`src/lib/shell-commands/task/fork.ts`) forks it into a task: a session in the chat's own records (`src/lib/chat/children.ts`) whose parent is the chat's, which reads the chat's messages up to where it forked as its own history rather than a copy (`src/lib/records/fold.ts`, read through `ChatReads`), works in the chat's folder, and wakes the chat when it finishes (`src/lib/chat/wake.ts`). The `instrument task` command (`src/lib/shell-commands/task/command.ts`, one module per subcommand on `defineSubcommands`) is `new`, `send`, `stop`, `list`, and `log`, and takes a task by its handle in the chat (`t1`). A user message mid-turn joins the running turn at its next step (`src/lib/chat/mid-turn.ts`), every tool call carries `activity` and `explanation`, and the first step of a turn the user typed is sent with a never-stored note (`src/lib/turn-note.ts`).
- **Workspace server**: loopback Hono app in `src/logic/server/index.ts`: the CDP bridge `agent-browser` drives a guest through, and the AI gateway mounted at `AI_GATEWAY_API_PATH`. It serves no files: a page on this computer opens at its `file://` address for the person and the agent alike, and the person's viewers read files through Studio's own `instrument://computer-<token>` channel.
- **Schemas**: `src/schemas/`. Use for RPC/tool I/O where applicable.
- **Machines**: XState in `src/machines/`. `WorkspaceActorRef` is the main-process handle; RPC context gets `workspaceRef` and `workspaceConfig`.
- **Skills**: `src/lib/skills.ts` discovers them across the bundled set, the registry, co-installed agent homes, and the workspace's own `Skills/` folder at its top level, deduping symlinks by canonical directory and copies by package fingerprint. `skill-catalog.ts` renders the budgeted catalog, which `available-skills-context.ts` puts in the session's context message (`LoadSkill`'s description is static, so installing a skill never rewrites a tool definition); `validate-skill.ts` holds the rules the runtime enforces. Each skill source is reachable at its real directory, and only the workspace's own (`getWorkspaceSkillsDir`) is writable (see `docs/architecture/agent-sandbox.md`). `load_skill` reads a skill where it is and names its folder, which the shell calls `INSTRUMENT_SKILL_DIR`; the app builds a skill's Python and Node dependencies in the runtime folder's `environments/` (`skill-environments.ts`), and `python` picks a skill's environment by where the script is.
- **Records**: a chat is the only record, and `src/lib/record-folders.ts` is the one answer to where its record folder is (`chatDir`, under the config's `chatsDir`: its logs and settings files, `state.<device>.json`, `attachments/`, `handoff-notes.md`, named in `chat-dir-utils.ts`), and the chat's own session is read from those logs (`chatSessionIn`). Its work is apart from it, on this computer (`workDir`). `resolveChat(id)` says whether an id is a chat's, never an id's shape; `chatDir` throws `NotFound` for one that is not. Everything that names a record takes a `ChatId` (`schemas/chat-id.ts`), and a task is named by its session in the chat's records; the chat's session id is internal to its records (`chats.session` reads it, and `chats.ofSession` turns a session from an older address back into its chat). JSON files on disk are written only through `src/lib/json-record-file.ts`.
- **Paths**: the agent works at real host paths. `shellPath` and `hostPathOf` (`src/lib/workspace-fs-layout.ts`) translate between a host path and the shell's spelling of it (the same on macOS and Linux, `/c/Users/...` on Windows). The shell starts in the chat's work folder (`workDir`, `src/lib/work-dir.ts`: `<id>/` under the config's `workFoldersDir`, the workspace's folder in `~/.instrument/work/`), made by the chat's first command and removed when the chat comes to rest with nothing in it, or at the next start if the app quit first (`src/lib/chat/work-dir-reap.ts`); the chat's tasks share it, and permission rules (`src/lib/permissions/`) decide what the agent may read and write. The file tools take a path as the shell does and read and write through its filesystem (`src/lib/tool-fs.ts`). A migration that moves a folder writes the paths it moved into the files holding them, once (`src/lib/rewrite-stored-paths.ts`): the ones this package opens, and every store the app registered with `registerStoredPaths` (none outside the app), so no caller names them; so a stored path says where its folder is rather than being looked up on every read; the person's views read an earlier build's `/tasks/<task>/...` in the work folder's `tasks/` (`resolve-workspace-file-path.ts`).

## Context messages

- `session-context` message (system prompt + `agent.getMessages`) is the session's baseline: written once when the session first needs model input, then reused byte for byte, so the request prefix a provider cache is keyed on does not move. `lib/session-baseline.ts` holds the whole rule. A task sends its own baseline once it has one, else the one it inherited.
- It is written again only when the session's window rolls over past it (the rollover rewrites the front anyway, and it is how a release's new prompt reaches a chat that began on an older one) or when it is marked older than `SESSION_CONTEXT_VERSION`. Bump that constant only when a change to what `getMessages` writes has to reach chats before their next rollover. A stored prompt that differs from `systemPrompt()` is never a reason on its own: an app update and a chat moving to another computer both look like that.
- The system prompt is the same on every computer: it names folders by the shell's variables (`FOLDER_VARIABLES`), never by path, and says nothing true of only one platform. What is true of one computer (the OS, the time zone, where each variable's folder is, the platform's shell guidance) goes in the context message, which records it as `environment` on its metadata.
- So every `getMessages`-derived value (system date, computer, folder list, skill catalog, task layout) is a startup snapshot for the life of the session. A fact that must reach the model later is an **append-only correction**: a persisted `data-*` part rendered onto a user turn (`folder-changes.ts`, `create-browser-status-part.ts`, `date-change.ts`, `environment.ts`), never an edit to an earlier message. Corrections must be deterministic to render from what is stored, so no live reads or timers during model-message conversion.
- Every `data-*` part declares a `CADENCE`. A standing picture (`state`: topic, workspace instructions, what was on screen, a task's tabs) is stored whole on every message whose writer could read it, an empty picture included once the session's history has had something in it (`goesUnsaid`), and `stateNotes` (`lib/state-notes.ts`) alone decides what of it the model hears; Studio's developer cards read through the same function. A writer that writes only a change is `diff`: what the session was last told is read from its own history, the baseline's metadata and the notes since (`lib/last-told.ts`), never kept beside it, so a note and the record of its telling are one write.
- Derive standing values from current state so a value read at baseline time is not pinned to a snapshot that later parts already superseded.
- A correction recorded on an assistant message (`data-maxSteps`, `data-setupChanges`) is carried forward in `SessionMessage.toModelMessages` to the next user turn, since injection only runs for user messages.

## Evals

`pnpm eval` runs the real agent loop against real models (`evals/`, cases in `evals/cases/`). `--model` is required, start on Workers AI, and name the models you ran. The `workspace-evals` skill has the rest; the `validate-changes` skill says whether an eval is the right check at all.

A commit that adds, drops, or reverses a rule for how an agent behaves (its prompt in `src/agents/`, or text a command prints for the model to act on) names the eval case covering that rule in a `Tested:` trailer, with the models it ran on, and adds a case under `evals/cases/` when none covers it. Rewording that keeps the rule is exempt, and so is a change no run could tell apart; say which in the commit. A rule tuned to one transcript and reversed for the next is how prompt churn happens, and a case pinning the behavior is what shows the next reversal what it would undo. Prefer a command refusal to a prompt rule wherever a command can enforce it: refusals hold where prose drifts.

## Seeded workspaces

`scripts/seed-workspace.ts` builds a throwaway app workspace from a committed
description in `fixtures/workspaces/` at the **repo root** (this package's own
`fixtures/` is something else), for `ELECTRON_USER_DATA_DIR` and
`INSTRUMENT_DATA_HOME`.
`scripts/record-fixture-session.ts` captures a real chat (with every task in it, each a session in its records) or a lone 1.x task folder into one.

```bash
pnpm workspace:seed --list                                # from the repo root
pnpm workspace:seed --out <dir> --fixture documents [--fresh]
pnpm --filter @instrument-org/workspace script:record-fixture-session <chat-dir> --fixture <name> --chat <key> [--task-key <handle>=<key>]...
pnpm --filter @instrument-org/workspace script:record-fixture-session <task-dir> --fixture <name> --task <key>
```

The seeder writes a chat through `placeChat` and `ChatWrites`, and settles
work folders with `claimWorkFolders`, never laying out `.instrument/chats/<id>/`
itself: a seeder that did would keep producing workspaces the app can no longer
read once storage changes. Studio's `seeded-workspaces.test.ts` guards that,
by running the launch steps over every fixture and reading it back through
the app's readers (`scripts/lib/fixture-workspaces.ts`).

The repo-root `fixtures/workspaces/README.md` covers what a fixture holds and how to add one.
