# Bash sandbox: mounts at real paths

The agent's shell and the programs it starts see one namespace: the disk's own paths. This page covers how the shell's filesystem is built from the folders a chat reaches, why a folder inside another is reached through the outer one, how native commands receive paths, and the just-bash quirks that follow. What decides whether a path may be read or changed is in [agent-sandbox.md](agent-sandbox.md); why the virtual `/task`, `/mnt`, `/skills` and `/apps` paths were removed is in [the decision](../decisions/2026-10-11-the-agent-works-at-real-paths.md).

## The layout

`packages/workspace/src/lib/workspace-fs-layout.ts` is the single source of truth for what the agent can see. Its consumers build from it and must never disagree: the just-bash filesystem, the dedicated file tools (`read_file`/`write_file`/`edit_file`/`generate_image`), the `rg`, `du` and `git` shell commands, and the agent browser's file addresses ([in-app-browser.md](in-app-browser.md#a-file-on-the-computer-has-one-address-for-the-person-and-the-agent)).

A layout holds mounts of one shape: a real directory (`hostRoot`), the path the shell names it by (`shellRoot`, `shellPath(hostRoot)`), and whether it is read-only. A chat's layout has:

- the **chat's work folder**, the shell's working directory, in the person's home folder (`~/.instrument/work/<workspace>/<id>/`). It is the chat's for its conversation and for every task it starts alike (`workDir` in `lib/work-dir.ts`), and holds nothing of the chat's records, so nothing in it is masked. The shell exports it as `INSTRUMENT_WORK`, beside `INSTRUMENT_OUTPUT` (the output folder), `INSTRUMENT_APPS` (the workspace's apps) and `INSTRUMENT_WORKSPACE_SKILLS` (its own skills), and native commands get them all in the host's spelling.
- the **chat's record folder** (`.instrument/chats/<id>/` in the workspace), where the rules open only `attachments/`, to read, and `handoff-notes.md`, to write. The window has none.
- the **folders the chat reaches** (`folderReach` in `lib/chat/folder-reach.ts`): the home folder and the output folder (`outputFolderPath` in `lib/chat/output-folder.ts`: the person's Instrument folder once they picked one, `~/Instrument` until then, or the older `~/Documents/Instrument` on an install that has one) always, every folder granted in the chat, the folders of the topic it is filed under, and the folders Settings › Permissions allows everywhere. They mount read and write; what may change in each is the rules' to say.
- one mount per **skill source**, at its own directory. The workspace's own `Skills/`, at its top level, is writable, created when missing, and wrapped in `setupTrackingFs` so skill edits are attributed; the bundled skills (the prepared copy) and those found in a co-installed agent's home are read-only.
- the workspace's **`Apps/` folder**, at its top level, writable, for a chat only; a task reaches its apps through `instrument app`.
- the **system's temp folders**, writable with no card, as any program expects: `/tmp`, `/var/tmp`, and this process's own temp folder (`os.tmpdir()`: `TMPDIR` on macOS, `%TEMP%` on Windows), each at its spelled and its real path (`tempFolders` in the workspace config replaces the list; the tests set none, since their fixtures live in the system's temp folder and stand for folders the agent does not reach). A system allow rule holds each, so the Seatbelt and bubblewrap profiles open them too, and a deeper rule still decides inside one: a workspace or a test's planted home under the temp folder keeps its own rules. An allow above the home folder opens nothing in it to change (`reachOf`), as the profiles close the home to changes beneath every rule above it. The shell exports the same folder as `TMPDIR`, `TMP` and `TEMP`, and native commands get it in the host's spelling, or whatever the agent exported instead.
- **`/dev`**, a small in-memory stub (`null`, `zero`, `stdin`, `stdout`, `stderr` as plain writable files, rebuilt per call) so `cmd > /dev/null` resolves instead of dying with EROFS and taking the whole call's output with it.
- Everything else is the **read-only base** (`read-only-base-fs.ts`): on macOS and Linux it reads the disk itself (an `OverlayFs` over `/`, wrapped in `rulesFs`) wherever the rules allow reading, as a native program can, so `cat /etc/hosts`, `file /usr/bin/env` and `ls -l /etc` work. A place that asks first asks (`/Volumes` raises its card), the app's own data is refused, and a path is held to the rules both as written and where it really leads, since this filesystem follows links (`followsLinks`; `reachOf` also matches each rule at its folder's real path). Its listings count against the home folder's walk budget, so `find /` stops at 20,000 entries rather than crawling the disk, and `du` of a folder outside every mount walks it natively. A write there fails with EROFS rather than landing in a per-call in-memory filesystem and evaporating when the call ends, and raises a card for the nearest folder on disk that holds it (`outsideFolderRefusal`; never the home folder whole or a disk root). A folder this account could not change whatever the person said (`/etc`, `/usr`; `accountCanWrite`, `access(2)` with `W_OK`) raises no card, and the agent reads that only an administrator can change it; native programs' refusals get the same answer (`refusalNote`). Windows skips the check, since `access` there sees only the read-only flag. Windows has no one root to read its drives from, so there the base is empty, and a read of a folder that exists outside every mount fails with EACCES and raises that card instead.

The shell's `PATH` is system folders it does not mount (`/usr/local/bin:/usr/bin:/bin`). Its own registered commands resolve by name ahead of any PATH (`registeredCommandPath`, [just-bash-upstream.md](just-bash-upstream.md)), a name they pass on runs the program the host's PATH names (`resolveExternalCommand`), and only then is the shell's PATH searched, for a script with no `#!` line; a program it finds there is still run natively. The host's PATH reaches native commands through `resolveCommandContext`.

A chat holds only the grants made in it on this computer (`grants: [{ path, grantedAt, source }]` under `chats` in the machine folder's `permissions.json`, `lib/chat/grants.ts`): a folder attached to a message (`"attached"`), or an allow on the card the agent raised by running into a folder (`"card"`). A grant is an Allowed rule in that chat alone; "Always allow" on the card also writes a folder rule. Every session of a chat, its tasks included, reaches the same folders at the same paths, because a task works in its chat's work folder and reads its chat's grants live. A path in a message, a wake note, or the conversation a task carries on from is therefore the same path on both sides, and nothing crosses between them that needs rewriting.

## A folder inside another is reached through the outer one

just-bash's `MountableFs` refuses a mount inside another, and the folders a chat reaches nest as a rule: the home folder holds the chat's work folder (in `~/.instrument`) and record folder (the workspace and its machine folder are inside it), the skills, `apps/`, and any grant under home. `mountRoots` therefore keeps only the outermost mounts, and the nested ones are reached through them. Consequences:

- What may be read or changed inside a mount is the rules', never the mount's: each mount's filesystem is wrapped in `rulesFs`, which asks `reachOf` for the path under it. The chat's work folder inside the home mount is open because a system rule allows it; the rest of this computer's folder and of the workspace is refused because a deeper rule closes it.
- A read-only source nested in nothing mounts through `OverlayFs` with `readOnly`. One that holds a writable mount (`holdsWritable`) mounts writable, because the writable one is reached through it. A writable mount uses `ReadWriteFs`, because `OverlayFs` is copy-on-write **into memory** and the filesystem is rebuilt per bash call: mounting a writable folder there would report every `mv` and `cp` as succeeding and leave the person's files untouched.
- The app's own folders are made when missing (the chat's work folder, the workspace's `Skills/` and `Apps/`). A folder of the person's that is gone stays gone and is skipped, rather than coming back empty.
- The home folder is walked against a traversal budget of its own, smaller than the sandbox's, so a listing of a large home folder cannot spend the whole call; the chat's work folder walks at the sandbox's budget wherever it sits, the home folder included (`WalkBudget`).
- The file tools and the other consumers of the layout do not collapse mounts. They take the deepest mount whose root holds the path, which is the same answer.

On Windows the shell spells a path as Git Bash does (`C:\Users\sam` is `/c/Users/sam`), converted at the edge in both directions (`shellPath`, `hostPathOf`); `MountableFs` mounts any absolute path, so `/c/...` needs no patch. Paths shown to the person stay in Windows form.

## Native commands get paths as typed

**Real subprocesses** (`python`, `node`, `ffmpeg`, `ffprobe`, `pnpm`, `uv`, `agent-browser`, `git`, `rg`, and any other program on the PATH, run by name through `shell-commands/path-program.ts`) do their own syscalls against the real kernel filesystem, and they are handed the arguments the agent wrote. Every script the agent runs is one of them: the shell has no in-process Python or JavaScript runtime. There is no translation of arguments, inline code or script files, no quarantine of paths, and no copy-first rule: `ffprobe ~/Movies/clip.mov` runs on the person's file where it lives. (`curl` is not among them: it is a just-bash network builtin and never touches the kernel filesystem.) What keeps such a program out of the places the rules close is the operating system, through a Seatbelt or bubblewrap profile built from the same rules; see [agent-sandbox.md](agent-sandbox.md). Only on Windows is anything rewritten: an absolute path in the shell's spelling becomes the host's (`hostPathArgs`), bare or as a `--flag=` value. What a command prints is not rewritten either; `filterShellOutput` redacts credentials and, on Windows, turns backslashes into slashes.

The commands that still look at paths themselves:

- **`rg`** resolves an argument that names a mount through `resolveReadOnlyHostPath`, so a path the rules keep from the agent or one out of its mount through a symlink is refused. It refuses every flag that lets ripgrep run another program (`--pre`, `--pre-glob`, `--hostname-bin`, `-z`). It shadows just-bash's own `rg` reimplementation, registered after the bundled commands so the real binary wins, being orders of magnitude faster on a large tree and free of the builtin's `(?i)` and root-level-glob bugs.
- **`du`** walks the real directories in a worker thread, with the same rule and symlink checks on what it is named.
- **`git`** runs on the folder it is in or is pointed at, and asks the rules for a write before any command that writes; see the Git section of [agent-sandbox.md](agent-sandbox.md) and [the decision record](../decisions/2026-09-11-git-reaches-attached-folders.md).
- **`agent-browser`** opens a file by its path at the file's real `file://` address ([in-app-browser.md](in-app-browser.md)).

Stdin crosses as bytes, not a string. just-bash packs stream data one byte per char (latin1); `subprocessStdin` converts that to a `Buffer` before it reaches `execa`, whose string `input` would UTF-8 re-encode it and mojibake every non-ASCII byte of a heredoc or piped binary.

## One answer for a host path

Every consumer that holds a host path asks `classifyHostPath(layout, hostPath, via?)` what it is to the agent: the mount it is reached through and its path there, and whether it leaves that mount through a symlink. It canonicalizes once (`host-path.ts`: realpath through missing segments, compared without case on macOS and Windows). The file tools, `resolveReadOnlyHostPath` (so `rg` and `du`), agent-browser file addresses, and the CDP bridge's file check all ask it. Whether the agent may read or change the path is the other question, and `reachOf` answers it.

## just-bash quirks we compensate for downstream

just-bash is the published npm package (`just-bash@^3.6.0` in `packages/workspace/package.json`) with one generated local patch, no fork build. A patch is carried only for a gap on the main path; anything else means landing a fix upstream and waiting for a release, which is why each one below is absorbed downstream instead. See [just-bash-upstream.md](just-bash-upstream.md) for the patch set, what we consume, and what is open upstream, and [the decision to carry no local patches](../decisions/2026-08-27-no-local-just-bash-patches.md), narrowed since, for why the rest are not patched. Known quirks:

- A **redirect into a path the filesystem refuses throws** (`echo x > <read-only skill source>/...`, or a path the rules close) instead of producing stderr + exit code. `tools/bash.ts` and `packages/workspace/scripts/run-bash.ts` convert the thrown error into a normal failed-command result.
- A **refusal reads as a missing file in a builtin**, and just-bash's error sanitizer replaces host paths in errors that come back from a script worker with `<path>`. The shell appends the rules' refusals to the call's stderr with the path spelled out; see [just-bash-upstream.md](just-bash-upstream.md).
- **`mv` out of a read-only source half-completes**: cross-mount `mv` is copy-then-rm, the copy lands in the destination, the `rm` fails with EROFS, an error is reported, and the source is preserved. Benign direction, confusing error.
- `MountableFs` synthesizes mount points for `ls /`, `stat`, etc.; its routing table is private, which is why `workspace-fs-layout.ts` mirrors the longest-prefix arithmetic instead of reusing it.

## Symlink policy differs by layer (intentionally)

- **just-bash mounts** refuse to traverse _any_ symlink, inside or out, and **the file tools** read and write through the same mounts, so they refuse the same links. The one link they follow is a folder the chat reaches that is itself a link inside another mount (`~/work` leading to `~/Documents/work`): it mounts where it leads, and its own name leads there (`linkedFs`), where the rules decide as they do at that path. Outside every mount, the read-only disk under the mounts follows a link, and the rules are asked of where it leads as well as of the path.
- **Native commands** follow symlinks as the operating system does, and the Seatbelt and bubblewrap profiles name a rule's path in both spellings where a link lies on the way.

## Testing without booting Studio

`pnpm --filter @instrument-org/workspace run --silent script:run-bash -- --attach <dir> "ls <dir>"` boots the exact runtime sandbox (see `.agents/skills/run-bash/SKILL.md`). The invariants are pinned by `workspace-fs-layout.test.ts` (mounts at real paths, the rules over a folder, EROFS, `classifyHostPath`), `permissions/rules.test.ts` and `permissions/rules-fs.test.ts` (the rules and the filesystem wrapper), `native-sandbox.test.ts` (the profiles), `app-data-rules.test.ts` (the app's own data, closed under every rule a person can set, in the rules, the shell, the file tools and both profiles), `tools/file-tools-shell.test.ts` (the file tools refused where `cat` and a redirect are, by name, through `..` and through a symlink), `resolve-workspace-file-path.test.ts` (the paths a chat kept, as the person's views read them back), `exec-shim.test.ts`, `filter-shell-output.test.ts` (the output filter), and `chat/folder-reach.test.ts` (which folders a chat reaches and in what order).
