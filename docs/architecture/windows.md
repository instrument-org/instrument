# Windows

A person can have any number of app windows open on one workspace. They are full windows of the same app, each with a strip of tabs across its bar, and everything behind them (the workspace machine, the chats, the agents, the RPC routes) is one process they all talk to. Each window is its own `BrowserWindow` with its own renderer, Jotai store and React Query cache. For why they are separate renderers rather than one renderer drawing into several native windows, and why a chat can be open in two of them, see the [decision](../decisions/2026-11-03-windows-are-separate-renderers.md).

## Which window is which

[`windows/app-window.ts`](../../apps/studio/src/electron-main/windows/app-window.ts) keeps every open window by the id it keeps its state under: `app` for the first a workspace ever had, a fresh one for the rest. `getAppWindow()` is the window last in front, which is what the rest of the main process means by "the window"; `getAppWindows()` is all of them, front to back. A window's page learns nothing of its own id: main names a web contents as it makes it (`app-window-ids.ts`), and answers whatever that web contents asks with that window's own things.

## What belongs to a window, and what they share

| What | Where | Who sees it |
| --- | --- | --- |
| The strip of tabs, the drafts and chats floating over it, whether the inbox is out, the chat and folder Chat and Files in the rail go back to | `window` kept file, `window/windows/<id>.json` | That window alone |
| Each chat's, draft's and site's tabs and which is up | `layout` kept file, one key per group (`window-tabs.v10/<group>`) | Every window, live |
| How things are laid out (widths, views, zoom) | `view` kept file | Every window, live |
| Size and place, which windows are open and in what order, which can come back | `window/window-state.json` | Main |

A group is a chat, a draft or a site, which is the same thing whichever window shows it, so its tabs are kept by the group and not by the window. A window writes only the groups it changed (`keptMembersAtom`), because a write of the whole list from one window would undo what another wrote a moment before. Anything that lets go of a group has to remember that other windows share it: a window drops a site's group only when it held that group itself and no tab in another window stands on it, closed windows that can come back included (`siteGroupsInOtherWindows`), and the sweep of empty drafts at startup keeps those floating in any window.

## Asking one window

Almost everything main publishes for the windows is read by all of them (`liveRead` routes re-read for themselves), and that is right for state. A request to do something is not: `window.command` names a web contents, published through `commandWindow`, and the route hands each window only what names it. A chord goes to the window it was pressed in (`bindAppWindowChords`), and a menu row to the focused one.

What something outside the app asks for goes to the window that already has it (`appWindowShowing`, read from what each window keeps): a notification or a link to a chat brings that window and that tab forward, and otherwise it opens in a new tab of the window in front.

What an agent asks of a chat's tabs must be answered exactly once, or a page it opens would open per window, so each ask names one window as it goes out (`appWindowForChat`): of the windows whose page can hear it, the one showing the chat, else the one in front. A blank page an agent makes for itself goes to the same window. The workspace package asks through `WorkspaceConfig.windowForChat`, which a host with one window leaves out.

## Moving a tab

A tab moves one way, whether a drag or a menu asks. A tab's menu moves it with one row, as a browser's does: Move Tab to New Window with no other window open, and Move Tab to Another Window, which lists New Window and the windows, with one. Either is a drag let go straight away (`moveTabNow` in [`tab-carry.ts`](../../apps/studio/src/electron-main/windows/tab-carry.ts)): the same phases, the same choice of what goes and who reopens, and the window takes the outcome the same way (`settleTabMove`). So a page keeps its state from a menu exactly as it does from a drag. The window stands a step off where it was, since there is no pointer to say where.

Merge All Windows and opening a link in a new window are the two that open a tab afresh: a merge has more than one tab to bring and only one window can keep its renderer, and a link has nothing to keep. A merge is main's alone (`mergeAllWindows`): it reads each window's tabs from what the window keeps and writes them into what the window in front keeps, refusing a front window whose page is not listening yet, which would miss them, hands over the pages those windows hold and their floats, and closes them with nothing to come back to (`closeEmptiedWindow`). A link opens through `window.openNew`, which writes the tab into the kept state of the window it then opens, which reads it as it loads.

Tearing a tab off ([`tab-carry.ts`](../../apps/studio/src/electron-main/windows/tab-carry.ts), with its pure rules in [`tab-carry-rules.ts`](../../apps/studio/src/electron-main/windows/tab-carry-rules.ts), and `useTabCarry` in the renderer) moves nothing, windows and pages alike, until the release, so going back to the row or Escape has nothing to undo. The renderer keeps the drag and decides when the tab has left its row by where the pointer is heading as well as where it is (`tab-pull.ts`): a steep pull comes off about 10px past the row, and a sweep along the row gets more room. Pages are out of the pointer's way for the drag (`data-tab-held`), because a page runs in a process of its own and otherwise takes a pointer that crosses it, the release included: pointer capture does not reliably hold it back, and a window that never hears the release stays on the pointer. Main keeps one phase for the drag (`CarryPhase`): on its row (`row`), free of every strip (`free`), or held in another window's (`docked`). Everything the drag does is an effect of going into or out of one, or of following the pointer within one, and main reads the cursor itself to follow it.

A tab in the hand is drawn at the pointer and placed by where its left edge is (`heldAt`, `onPlace`), the same way whether its strip is its own or another window's: the strip's own reorder measures from the press, and the row closing up and opening again moves a tab out from under those measures. Nothing else in the window answers to the pointer while it holds a tab, hovering included.

Off its row a tab leaves its strip as if it had gone: the strip closes up with its own motion (`carriedKey`), the tab beside it comes up, and a small picture of the whole window, as it stands, goes with the pointer (`openTabPicture` in [`tab-picture.ts`](../../apps/studio/src/electron-main/windows/tab-picture.ts)), a window of its own for the length of the drag that takes neither focus nor the pointer. All of that happens in the one renderer, with the tab still among its tabs, so back on the row or Escape it simply returns.

On the release whichever side has less to lose is the one that opens afresh (`whatGoes`), and what opens stands across the pointer with the pointer just under its bar, or as near that as keeps all of it on the screen (`boundsAtRelease`). By default that is the tab: it opens in a spare window (`keepSpareReady`, `takeSpareWindow`), an ordinary app window kept booted and hidden, on none of the window lists, given it through the kept state the way a window coming back from a launch is, and the window it came from stays as it is, with every page in it. A tab whose page has been used cannot do that, since a page cannot change renderers and keep what it holds (`isPageUsed`: a person's click, key or scroll, or an agent's input, where being sent to an address leaves nothing to lose). So the pressed window leaves with it, renderer and all, and the page, the words typed into it, its selection, scrolling and keyboard are never touched. The spare takes the other tabs and the floats in its place, as the window stood. It comes up over the pressed window first, and the pressed window is told what it holds from there out of sight (`kind: "reshaping"`, which also keeps its strip from animating) and goes to the pointer once it has drawn, so that neither window is seen changing. A window wholly covered by an opaque one counts as out of sight on macOS and stops drawing, so the spare is a shade short of opaque for those few frames. The picture grows from the pointer to fill where that window is coming up, wearing that window's tab bar (`growTo`), and goes once it is up. A tab pressed before all that is done stays on its row for that drag, since a window is still being told what it holds.

The spare is given what it will hold as the tab leaves its row, and until the release it is told it is beneath (`kind: "beneath"`), so a chat up in it does not count as read. Where a window can be kept unseen it is on screen at no opacity by then, so that it has drawn when it is wanted. The tab that comes up in the spare takes its page on the release (`neighborPages`). Any other page the spare shows it asks for only once it has been adopted (`adoptSpareWindow`, `canTake`), and a drag undone has moved nothing.

A full-screen window stays, and so does one in a session that cannot place a window: the tab goes to the spare whatever its page holds. Out of a full-screen window the picture and the spare float in that window's Space, unable to go full screen themselves, since macOS would otherwise switch Spaces mid-drag, and on the release the spare goes full screen as the window it came from stands. A maximized window that leaves does so at its own size, and the window left behind fills the work area in its place. On Linux a window of ours under the pointer takes the press's release, even one that takes no mouse events, so there the picture hangs just clear of the point of the pointer, where elsewhere it is centered on it. A window there has no opacity to keep it out of sight until it is wanted (one given an opacity stays a few percent see-through, so the drag gives it none), so the spare comes up only on the release, and a window manager there keeps a window a program moves on screen, so a window following the pointer stops at the screen's edge. A Wayland session goes further, telling a window nothing of where it is and letting it place no window, so nothing follows the pointer, the tab stays showing in its strip, and Move Tab to Another Window is the way into another window's strip. GNOME on X11 says a window opening without focus over the focused one "is ready", which a pressed window leaving costs that notice. At a fractional scale on Windows a move that names only a place grows a window by a pixel each time, so whatever follows the pointer names its size on every step.

Main answers which strip the point is over (`phaseAt`), since only it can see every window. Windows are tested front to back from the order they were last focused, because Electron cannot read the OS's stacking order, and a window covering a strip takes the release. A tab held in a strip stays in it for 24px past its edges (`DOCKED_REACH_PX`), so that it does not come straight back out for a pointer that barely moved. Over another window's strip that window draws the tab among its own at the pointer (`kind: "incoming"`), its tabs making way, without loading any of it, and says where the tab stands (`placeTabCarry`), which is where it lands. Let go there, whichever side has less to lose is the one that reopens (`landsBy`): the tab goes to that window as `receiveTab`, and the window stays as it is, unless the tab has a used page, in which case the pressed window takes on the other's tabs in its place, and that window closes. It comes forward only once its strip holds just those tabs (`drawnHolding`), drawing the held tab where the strip it replaces has it (`held`), so the two read as one until the tab settles. With used pages on both sides the tab in hand wins, and the other page reloads when it is next looked at. A window's only tab leaves nothing behind and needs no spare window or picture: its window follows the pointer, and over another strip it goes unseen, where a window can, for that strip to show. A strip the press was already over (`overAtStart`) takes that tab only once the pointer has left it and come back: a window moved a little by its only tab should not jump into the window behind. The press that starts a drag has to reach the page, so app windows set `acceptFirstMouse`: without it the first press on a window behind another only brings it forward, and over the bar it drags the window. An instance kept off screen never shows a window, has no picture, and starts no spare until a drag asks for one, so a drag driven over CDP exercises the same path.

## A page is in one window

A page tab belongs to a group every window can see, but its guest is a `<webview>` in one renderer, and Electron cannot move one between renderers. So a page is in the window that showed it last. [`in-app-browser.md`](in-app-browser.md#a-page-is-in-one-window-at-a-time) has what that does to a guest. A page drawn inside a surface (a file's page in its viewer, the page under Quick Look) is not one of those: its tab is kept in the `window` file of the window drawing it (`fileOfTabGroup`), since the surface makes it as it comes and closes it as it goes, and each window showing that tab draws a page of its own. Such a page never changes windows, but a person having used it keeps the window with the tab like any other (`hostedPages`).

## Coming back

A launch brings back every window that was open, each where it was with its tabs, the one last in front on top (`restoreAppWindows`). A quit leaves those records alone, so closing the app is what keeps them. Closing a window while the app runs moves it to what can come back: File › Reopen Closed Window, or Shift+Cmd+T once no closed tab is left to reopen. The last ten are kept; past that a window's file and place go. With every window closed on macOS, the Dock icon brings back the one closed last.

Closing a window quits the app only where it is the last one on Windows or Linux (`quitsWithLastWindow`), and asks about running work only then. While setup is up, only the window it draws over is open; the rest come back as it goes down, and New Window does nothing until then.
