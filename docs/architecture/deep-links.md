# Deep links

An `instrument://` address names something in the app. Inside the window it is a link in a reply or a document, read by [`open-target.ts`](../../apps/studio/src/client/lib/open-target.ts). From outside (a browser, a note, another app) the OS hands it to the app, and this doc is about that road in.

## The scheme

Each build answers to its own scheme (`appProtocolOf` in [`constants.ts`](../../packages/shared/src/constants.ts)): `instrument` for the app people install, `instrument-local` for development and `instrument-preview-<name>` for a preview, so a link never reaches a build it was not meant for. A reply always writes `instrument://`, and every build reads that as its own inside the window.

## The links

| Address | Opens |
| --- | --- |
| `instrument://chat/<id>` | the chat |
| `instrument://task/<id>?chat=<id>` | the task, in the chat it was started in; without `chat`, only a tab already showing the task comes up |
| `instrument://app/<id>` | the app's page |
| `instrument://skill/<name>` | the skill (`skill/instrument:create-page`) |
| `instrument://memory/<name>` | the memory |
| `instrument://settings/<name>` | the settings section (`settings/models`) |
| `instrument://screen/<name>` | one of `SCREENS` in [`instrument-screens.ts`](../../apps/studio/src/shared/instrument-screens.ts) |
| `instrument://file/<absolute path>` | a file in its viewer, or a folder in Files |
| `instrument://files?path=<path>&path=<path>&group=<word>` | each file or folder as `file/` opens one, up to 20, in tabs of their own; `group` names the tab group they belong in |
| `instrument://page/<id>/<token>` | a copy of the page hosted at `https://<id>.instrument.page/<token>/`, kept in Downloads |
| `instrument://new?text=<words>&project=<id>` | a new chat's draft with the words in it |

A noun names one thing by one path segment and only takes the person to it. `new` is the one verb, and what it makes is written in query parameters, so a later verb has the same shape. A Windows path keeps its drive letter as the first segment (`instrument://file/C:/Users/windows-user/report.pdf`). A `~/` at the start of a file path means the person's home folder, on this computer whatever their user name on it (`instrument://file/~/wireframes/x.html`, `files?path=~/wireframes/x.html`), and nothing else is expanded: `~user/` is read as written.

## How a link arrives

Three roads, all into the launch's `receive` ([`launch.ts`](../../apps/studio/src/electron-main/windows/launch.ts)), which hands a link to `handleDeepLink` in [`index.ts`](../../apps/studio/src/electron-main/index.ts): `open-url` on macOS, the launch's own arguments on Windows and Linux, and `second-instance` when the app is already running there. The first two are listened for before `ready`, because the link that launches the app arrives before it. None runs while the workspace is refused.

[`outside-links.ts`](../../apps/studio/src/electron-main/lib/outside-links.ts) reads the link (`outsideLinkOf` in [`instrument-link.ts`](../../packages/shared/src/instrument-link.ts)) into an ask, and the window's asks queue ([`app-window-asks.ts`](../../apps/studio/src/electron-main/windows/app-window-asks.ts)) holds it until the window can show it: while its page loads and while setup is up. The window comes forward only for a link that opens something or says why it can't, and no window opens until boot has restored the ones the workspace was left with (`windowsMayOpen`), so a link arriving before then waits for those, and brings them up in front of the person.

## A new tab group

Every way something arrives from outside goes through one function in main, `openFromOutside` in [`index.ts`](../../apps/studio/src/electron-main/index.ts): a link, a file handed over from the Finder (a double click, Open With, a drop on the Dock icon), and the files a launch or a second launch names. The Finder hands several files over one `open-file` event each, all at once, so a file arriving within 100 ms of the one before joins it, up to 300 ms after the first (`createFilesTogether` in [`files-together.ts`](../../apps/studio/src/electron-main/lib/files-together.ts)). Hand-overs open in the order they arrived (`inArrivalOrder` in [`outside-links.ts`](../../apps/studio/src/electron-main/lib/outside-links.ts)): a link is read at once, but waits to open until every link and file handed over before it has, since checking a path or fetching a page can make a later link ready first.

One thing alone (a file, a folder, a chat, a task, an app or Settings) comes up where a tab already shows exactly it, in any group of any window: that window comes forward with the group up and the tab up in it, and the tab lights so something visibly happens even when it was already up. Exactly is the identity main reads every window's tabs by (`tabIdentityOf` in [`tab-identity.ts`](../../apps/studio/src/shared/tab-identity.ts)): the same file path, the same Files folder, the same chat or task, the same app, Settings at any of its parts (the tab goes to the part asked for); a file's page counts as the file, and a folder never stands in for a file in it. Main finds the window (`windowWithGroupTabShowing` in [`tab-showing.ts`](../../apps/studio/src/electron-main/windows/tab-showing.ts)) and the window finds the tab (`tabShowingAmong` in [`tab-model.ts`](../../apps/studio/src/client/components/window/tab-model.ts)). With no tab showing it, it opens as a new tab group of one in the window in front. A chat comes up at the tab on it the person last sent from (`workingTabOf`).

Several things in one hand-over always open as one new tab group in the window in front (`outsideOpensOf` in [`app-window-asks.ts`](../../apps/studio/src/electron-main/windows/app-window-asks.ts)), even where a tab already shows one of them: a tab for each file, folder and page, in the order given, all on one side, with the first up. A link never says where in the group a tab goes, since the agent writing it may always guess wrong; the person moves tabs between sides themselves.

Something from outside never joins a group the person has, except by bringing up a tab already there or by naming a group a link made (below): a link taking over a group would be jarring, and making new groups is the model. A new group goes to the top of the window's list, so two hand-overs in a row leave the later one above the earlier.

## A group a link names

A `files` link may carry a `group` parameter, a word for the piece of work its files belong to (`group=New tab row`), so an agent that links each round of one piece of work lands them all in one group. The word is read plain (`linkGroupOf`: unseen characters out, runs of spaces one space, at most `OUTSIDE_GROUP_MAX` characters) and matched whatever its case (`isSameLinkGroup`). A link with one path and a group is still a group's link, never one thing alone.

A group made by such a link keeps the word (`GroupOwn.linkGroup`), and its sidebar row shows it on the second line as a label filled with a color, where a file's folders or a page's site would be, unless the tab the row goes by is a chat. The color is given as the link makes the group (`GroupOwn.linkColor`): the one of the palette's deep row the window's open groups wear least (`newLinkColor` in [`link-label.ts`](../../apps/studio/src/client/components/window/link-label.ts)), so labels open side by side differ until every color is worn. A group kept from a build that gave none takes one from its word. The person never sets the word or the color: they ride along with the links, and only a link sets them. The row's menu offers Remove Label, which takes both off, so the row shows its folders again and a later link with the word makes a group of its own.

A later link with the same word joins the group open under it in any window, the one up last of several (`windowWithLinkGroup` in [`tab-showing.ts`](../../apps/studio/src/electron-main/windows/tab-showing.ts) picks the window, which picks the group). A path already a tab there comes up; each other goes at the end of the group's right side, or its one side, and the first of them comes up and lights. The group comes up and keeps its place in the list. With no group open under the word (closed, or never made), the link makes a new group that goes by it. A build that predates the parameter ignores it and opens a new group, as it would without it. Files dropped on the window from outside are a drag, not a hand-over, and open as a new group in drop order.

An agent usually links a file again because it has just rewritten it, and every viewer already follows its file. A page in its file tab is watched and reloads when written, keeping its place on the page. Markdown, text and code pull a write into the editor, watching only while their tab is up and catching up in one pull when it comes up. An image, a video, a PDF and the other viewers take the file at a URL carrying its modified time, which a tab behind another holds still until it comes up again, so coming up is when a write shows. Each watch looks about once a second, so a link sent the moment a file is written can show the old version for up to that second before the new one replaces it.

## A file that isn't there

A link to a path with nothing at it opens the folder it was in as a tab of the link's group, where the file would have been, and the window says the file is no longer there. Where the folder is gone too, nothing opens and the window says that as well. A path the system won't say anything about (a folder the app may not read) is not counted as missing, so the file opens and its viewer says whose refusal it is.

## Several files at once

Instrument's own website writes `files`, from its `/open` page: a `path` parameter for each file or folder, and `group` where the link it was handed names one, each value as `encodeURIComponent` writes it and read back with `URLSearchParams`, so a space, a `+`, a `&` or a `#` in a name comes through as it was. A value is the plain path, `/Users/mac-user/a.md` or `C:/Users/windows-user/a.md`, with no slash before a drive letter.

Each path goes through everything a `file/` link's does and comes to the same thing: refused, a downloaded page shown in its folder, a folder in Files, a missing file said over its folder, or the file. They open as tabs of one new group, in the order written, and a path written twice, or two ways that lead to one place, opens once. A path is read as written, with no step up taken out of it first, so one with a `..` opens nothing. A web address opens nothing either: the link takes only paths. At most `OUTSIDE_FILES_MAX` (20) open, and the window says how many more the link named, the way it says a file is missing.

However many paths a link has, one window comes forward, once (`showFromOutside` in [`app-window.ts`](../../apps/studio/src/electron-main/windows/app-window.ts)): the window in front, which opens the group. A link left with one path, or one folder for a missing file, is one thing, and comes up where a tab shows it.

## A page from instrument.page

A page the agent shares is hosted at `https://<id>.instrument.page/<token>/`, one self-contained HTML file, and its Open in Instrument control hands the app `instrument://page/<id>/<token>`, which the website writes with nothing but the id and the token: the id one DNS label of lowercase letters, digits and hyphens, 1 to 63 of them, a hyphen at neither end, and the token sixteen lowercase base32 characters (`outsideLinkOf`). The token is random and travels only in the path, so the host, which DNS makes public, does not open the page. A page published before link tokens has none, and its link is `instrument://page/<id>`. A query, a fragment, a second segment that is not a token, a third segment or any other id is not a link.

The link opens no web page. Main ([`hosted-page.ts`](../../apps/studio/src/electron-main/lib/hosted-page.ts)) fetches `https://<id>.instrument.page/<token>/` asking for HTML, from that host and no other: a redirect that stays on the host is followed a few times, and one anywhere else, the pages domain itself included, fails. The page has thirty seconds and sixteen megabytes. What comes back goes into the person's Downloads folder, where their browser would have put it, under the page's own title as a file name (`cleanName`, the same cleaning Save Page As gives a name), else its id, with `.html`, and the ` (2)`, ` (3)` a browser adds when the name is taken; the write claims the name, so two links a moment apart never share a file. The copy carries the system's downloaded-from-the-internet mark, written as the app's own downloads are marked. Then the copy opens as a file link's page would, in a new tab group.

It opens straight from the link, where a marked page a `file` link names is only shown in its folder, because of where it is. A page in the Downloads folder, or anywhere below it, reaches only itself ([`local-file-policy.ts`](../../apps/studio/src/electron-main/browser-view/local-file-policy.ts), judged by name and by where the name really leads): that folder is a pile of unrelated files a browser dropped there, so no page in it needs its neighbors, and a page from the internet opened there reads none of them. A page kept anywhere else would have its folder, which is why the copy goes nowhere else.

When the host answers anything but 200, sends the request elsewhere, takes too long or sends too much, nothing is kept and nothing opens: the window says `<id>.instrument.page didn't answer`, the way it says a file is missing. When the page comes but Downloads takes no file, the window says a copy couldn't be kept. The link counts once against the gate, like a link to a file.

## What keeps a link harmless

A link carries no word of who wrote it, and a site the person has let open Instrument can send one with no click at all. So a link only ever puts something in front of the person:

- **A path is a plain absolute one.** It goes through the same check as the file channel's (`hostPathOfUrlPath` in [`computer-files.ts`](../../apps/studio/src/electron-main/lib/computer-files.ts)) before anything touches the disk: no doubled separator, which is how a network share is spelled (opening one would hand the share the person's Windows sign-in), no backslash where a backslash separates, and on Windows a drive letter. A step up is taken by the address itself before it is read, so the path judged is the one it leads to. Then the places every way of showing a file refuses ([`refused-files.ts`](../../apps/studio/src/electron-main/lib/refused-files.ts)) are refused here too, by name and by where the name leads.
- **A downloaded page is shown, not opened.** A page opened in the app's browser can read its folder and everything below it ([`local-file-policy.ts`](../../apps/studio/src/electron-main/browser-view/local-file-policy.ts)), so a page a site dropped into Downloads could read the rest of the folder. What tells such a page apart is the mark the system puts on a file downloaded from the internet ([`download-mark.ts`](../../apps/studio/src/electron-main/lib/download-mark.ts)), read where the path really leads, so a link to the page carries it too: the `com.apple.quarantine` attribute on macOS, and on Windows a `Zone.Identifier` stream naming zone 3 (Internet) or higher. Linux browsers record the source in `user.xdg.origin.url`, which Node cannot read without a native module, so there a page under the Downloads folder counts as marked, and only there: a page saved anywhere else carries no mark Linux can read. The app's own browser marks what it downloads the same way ([`downloads.ts`](../../apps/studio/src/electron-main/browser-view/downloads.ts)): Chromium writes the Windows stream itself, the app writes the macOS attribute when a download finishes, and on Linux its downloads land in the Downloads folder unless the person picks another place, where they are not marked. A link to a marked page opens its folder in Files with the page selected, and the person opens it from there. Any other page opens like every other file: an image, a PDF, Markdown and text run nothing. The copy a `page` link keeps is the one marked page a link opens, and only because it is in Downloads, where a page reaches only itself.
- **A path with nothing at it is never a file to open.** It becomes the missing file's ask, the folder and the name and nothing the window could load, so a page a site manages to put there a moment later is still not run from the link. The mark reader counts a path that leads nowhere as marked too, for the same reason.
- **A new chat is never sent.** Its words are a draft of its own beside any already open, so nothing the person wrote is replaced, and, like every draft, it carries only what the person adds, never what is on screen. The characters a person cannot see but the model reads (zero-width ones, the marks that turn text around, the tag block) are taken out, longer words than `OUTSIDE_WORDS_MAX` open nothing, and the project is used only when one has that id.
- **A site cannot flood the window.** The same link again within a few seconds is one click, at most ten links a minute open, and once ten asks wait for the window another link is let go (`createLinkGate`). A link to several files counts once against the minute however many paths it has, while each of its paths is an ask that waits.
- **A link the app does not know says only that.** A noun no build has a screen for, a shape a noun refuses (no name, a second segment, a query where none belongs, a web address where a path is required) or an address not in the app's scheme at all puts up one toast in fixed words, which offers a check for updates since a newer build may read the link, and never a word of the link's own: a site chose them, and the window would show them under the app's name. The text of a link leading with a noun the app does not know goes to the `outside-link` log alone, cut to its first 200 characters; a noun the app knows in a shape it refuses, or a link with no noun, is logged by its noun alone, since what follows may be the person's words or a path. It passes the same gate as every other link, so a site looping on one cannot paint the window with toasts, and one the gate lets go says nothing.

There is no link that opens a web page. One would add nothing a link to the person's own browser does not, and paired with `new` it would put a page a site chose in front of the agent, signed in as the person. A `page` link is not one: it names a page by its id and token alone, so the only address it can lead to is one under instrument.page, the app's own host, and what opens is a copy kept on this computer, in the one folder where a page reads nothing beside it.

Asks from outside are answered even while something holds the window: setup's hold can still be up when what waited for setup arrives (`use-window-commands.test.tsx`).
