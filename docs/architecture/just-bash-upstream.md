# just-bash: what we consume, what we work around, what we are waiting on

`just-bash` is the sandbox every agent `bash` call runs in, so its gaps do not surface as stack traces. They surface as an agent giving a confident wrong answer, or writing a prompt-shaped workaround into its own reasoning. That makes the accounting below worth keeping in one place: which build we consume, what we have patched or told the agent to avoid because of it, and what is open upstream.

The failure mode this page exists to prevent is a workaround outliving the bug. Anything added to the registers below needs a removal trigger recorded next to it. See also [agent-sandbox.md](agent-sandbox.md) for what the sandbox contains, and [bash-sandbox-mounts-and-native-binaries.md](bash-sandbox-mounts-and-native-binaries.md) for how the folders a chat reaches are mounted.

## What we consume

We are on the published npm package, not a fork.

- `just-bash@^3.6.0` from npm, declared in `packages/workspace/package.json`.
- One local patch file, carrying twenty-five changes: to `find`, to `stat`, to `MountableFs`'s copy across mounts, to the `python3` worker, a `stdinConnected` flag on the command context, to `ls`, to awk's `printf`, to `sort -h`, to how `python3` treats a worker that dies, to `rmdir` on `ReadWriteFs`, to `pathlib`'s glob in the `python3` worker, `find`'s `-newermt` and `-mmin`, to how `awk`, `sed`, `jq`, and `yq` report an execution limit, to how stdin becomes bytes in `sha256sum`, `gzip`, `base64`, `tar`, and `split`, the message a builtin prints for a failed read, a hook that hands a command name the shell does not know to the embedder, what `ls -l` shows of a file on a real disk, `cp` of a symlink, a write the filesystem refuses in a redirect or `tee`, a glob after a quoted folder, a redirect into a folder that does not exist, the directory listing `MountableFs` answers with types, host code assigning a `process.env` variable while a script runs, a pipeline stage handing its stdout to the next stage while it still runs, a hook that tells the embedder each command the shell runs, and the options `bash` and `sh` take, built from source by `scripts/rebuild-just-bash-patch.ts`; see below. Three of them (the `python3` worker, worker exit, and `pathlib` glob parts) change only just-bash's `python3` runtime, which the agent's shell does not register: `python` and `node` are native commands ([decision record](../decisions/2026-10-12-python-and-node-run-native.md)). They are inert and go at the next rebuild of the patch.
- `run` 2.1.3, a dependency of just-bash rather than ours: the QuickJS-ng runtime behind just-bash's `js-exec` (#394), which the agent's shell does not register either. It strips TypeScript with Node's `module.stripTypeScriptTypes`, falling back to `typescript`, its optional peer, only on a Node without it. Electron's Node has it, so the packaged app leaves `typescript` out (`apps/studio/electron-builder.ts`).

`minimumReleaseAge` in `pnpm-workspace.yaml` holds installs to releases at least seven days old, so the newest published version is routinely not the newest installable one. `minimumReleaseAgeExclude` carries the document-viewer libraries deliberately pinned to exact versions, `agent-browser`, which we do float onto fresh releases, exact versions of one oRPC security release, and an exact just-bash version taken a few days early once its patch was rebuilt and verified against it. An exact-version entry is the way past the gate for a release we have checked and want before the week is out; it goes inert once the version ages past the cutoff. A bare package name is reserved for what we deliberately float.

Upstream cuts releases through changesets and merges a great deal between them, so **a fix being on upstream `main` does not mean we have it**. Check the published version, not the branch, before assuming a workaround can go.

## Moving to a fork build

Mostly unnecessary now. What a fork build was for, carrying our changes as source rather than as edits to minified output, is what `scripts/rebuild-just-bash-patch.ts` does inside the pnpm patch: it builds the release tag with every carried change applied and keeps the result as the patch. A fork build would add only a published artifact of our own, which buys nothing while the patch applies, and would cost the release-age gate and upstream's own publishing checks.

Adopt one only if the patch stops being able to express a change, for instance one that adds a new module the published package does not have; the script stops with a message when that happens.

## Fix upstream, or replace the command

Two ways to change what a just-bash command does, and they are for different problems.

**Fix it upstream and carry the fix** when the defect is in just-bash's own model: a quadratic accumulator, a wrong parse, a leaked rejection. just-bash runs in browsers, in plain Node, and over any `IFileSystem`, in-memory ones included, so a fix that works there is a fix every embedder gets, and carrying it until the release lands costs a manifest entry.

**Replace the command with a custom one** when the better implementation needs what only an embedder running in Node or Electron has: a real binary, a worker thread, or the host disk behind our mounts. That is not something upstream can take, because it cannot assume any of them. `rg` is the real ripgrep binary in a subprocess, `git` is dugite's git with our argv policy, and `du` (`shell-commands/du.ts`) walks the real directories behind the mounts in a worker thread, so a walk over a large folder costs the main thread nothing where the builtin's costs it everything. A replacement resolves paths through the workspace layout with the same containment as the others, and hands anything it does not implement back to the builtin through `ctx.origCommand`, so it never makes a working command stop working.

The replacements are where the performance headroom is. A builtin is interpreted TypeScript on the thread that paints the window; a subprocess or worker is not.

The patch is generated rather than edited. `patches/just-bash-sources/sources.json` names the release tag and every carried part: an upstream pull request pinned to a commit, or a local diff under the same directory where a pull request has to be adapted to the version we install (`cross-mount-copy-3.6.0.diff` and `stdin-connected-3.6.0.diff` are #422 and #448 merged onto a tag that moved under them, and `stdin-bytes-3.6.0.diff` is #573 reshaped to keep 3.6.0's module graph) or where we depart from upstream on purpose (`ls-plain-listing-3.6.0.diff`). A part may name pull requests and a diff together; the diff applies after them. `pnpm scripts:rebuild-just-bash-patch` then:

1. checks out the tag in a cache outside the repository and installs it;
2. builds it unchanged and stops unless the bundle and the shipped declarations are byte-for-byte the published package, which is what makes a rebuilt file a faithful stand-in for a published one;
3. applies every part in order, stopping on the first that does not apply;
4. builds again, and with `--test` runs just-bash's own tests for the directories the parts touch, after the build because the `python3` tests load the worker bundle it writes;
5. pairs each rebuilt bundle file with the published file it replaces, by walking both builds' import lists from the files whose content-hashed names did not change and from the files whose content matches exactly one published file apart from the hashed names they import (a module renamed only because a chunk it imports changed); a part that adds or removes a module outright stops the run rather than guess;
6. writes the files whose content differs, under their published names, into `pnpm patch --ignore-existing` and commits it, which moves the patch hash in `pnpm-lock.yaml`.

`--dry-run` reports the files without writing. On a development machine some of just-bash's tests fail for reasons of their own: `tar`'s xz cases without `node-liblzma`'s native build, and a few timing-sensitive `python3` queue cases and comparison suites that pass on a rerun. Two runs give a byte-identical patch. The rebuilt `index.js` is most of the patch's size: once a change touches the interpreter, the minifier renames identifiers through the whole file, so most of its lines differ from the published ones. `dist/bundle/browser.js` and `dist/bundle/index.cjs` are left out (`skip` in the manifest); Studio loads the ESM entry.

To move to a new version: point the manifest at its tag, drop the parts it already contains, refresh the pins, and run the script. A local diff that no longer applies has to be ported again against the new tag's source. While the new version is inside `minimumReleaseAge`, `pnpm install` refuses a lockfile that resolves it. Work on the upgrade with `pnpm_config_minimum_release_age=0` in the environment of that shell alone; to land it before the version ages in, add the exact version to `minimumReleaseAgeExclude`.

Earlier parts are gone. `patches/just-bash@3.2.0.patch` normalized the namespace of the dynamic `import("undici")` so the pinned connection owner could read `Agent` off it; without that every `curl` failed as `DNS pinning unavailable for private IP enforcement`. Upstream #339 is the same fix and shipped in 3.3.0. `create-bash-env-network.test.ts` is the guard that would catch a regression. The 3.4.1 patch carried five pieces 3.6.0 made unnecessary: #414 (`find` reports an unreadable directory and goes on), #423 (the `python3` program name, which 3.6.0 pins as #444), #390's entry charging in `ls`, and two fixes to the old `js-exec` worker that `run` replaced, one installing the module loader for scripts so a dynamic `import()` loads (decided in [decisions/2026-10-06-carry-the-script-dynamic-import-patch.md](../decisions/2026-10-06-carry-the-script-dynamic-import-patch.md)), the other stopping the bridge when the worker dies. The `find` cases stay as their guards.

## Offering one upstream

A pull request there is reviewed by `auto-maintain`, a bot that runs several
reviewers over the diff (a maintainer pass, a general pass, two adversarial
security passes, and one on bash and host portability) and posts their
findings as advisory comments before any person looks. Everything below is
what it has asked for, so a change that answers these before it is offered
saves a round trip.

**Work the repository's own checks first.** From its root: `pnpm lint`
(biome, per-package banned patterns, workflow security), `pnpm --filter
just-bash typecheck`, and `pnpm --filter just-bash test:run <dirs>` for
every directory the change touches, not only the one it edits. Biome
formats as well as lints, so run `biome check --write` on the files changed
and commit what it does; a formatting-only difference is an error there and
it will be the first thing reported.

**Add a changeset.** `.changeset/<two-or-three-words>.md`, front matter
`"just-bash": patch` (every changeset in the repository is a patch so far),
then a paragraph saying what changes for someone using it. The bot reports
a missing one on every PR.

**Match the commit and title style**: `type(scope): imperative summary`,
lowercase, with the scope being the area rather than the file
(`fix(redirections):`, `perf(fs):`, `feat(find):`). The body carries the
reasoning; the PR body carries the measurements.

**What its reviewers reliably raise**, in the order they have raised them:

- **A fallback that loses the parallelism of the path it replaces.** The
  commands batch `DEFAULT_BATCH_SIZE` (100) filesystem calls through
  `Promise.all`. Code that moves such a loop somewhere else has to keep the
  batching, or a backend answering over a network goes from waves to one
  round trip per entry. Raised by three of the five reviewers at once.
- **Hidden work that a caller's own budget can no longer see.** The
  execution and traversal limits are counted per call at the call site, so
  folding N operations behind one call is read as a way around them.
- **A value that encodes "unknown" as a definite answer.** `DirentEntry`
  has no unknown state, so all three predicates false reads as "none of
  these", and a reader skips a real directory rather than asking again.
- **Host behavior outside macOS and Linux on a local disk.** NFS and FUSE
  answer `DT_UNKNOWN`, Windows spells paths differently, and a reviewer is
  reading for exactly that.
- **An embedder-supplied filesystem.** Every filesystem in the package may
  implement an optional method, so it is easy to forget that the interface
  allows one that does not, and that is the case the reviewers reason about.

**Answer the review in one comment and one commit**, naming what each point
changed. Saying which of them were right, and which case none of them
raised, is worth more than a long reply.

The external commands part is ours and has no pull request yet. The text to open one with, against `main`:

> **interpreter: let the embedder resolve a command the shell does not know.** Adds an optional `resolveExternalCommand(name, { cwd, env })` to `BashOptions`, returning `{ command, path }` or undefined. The interpreter asks it for a name containing `/` before reading that file as a script, and for a bare name after builtins, functions, the shell's PATH and the registry have all missed, so nothing that resolves today changes. `type` (with `-a`, `-p`, `-P`, `-t`), `command -v`/`-V` and `hash` ask it at the same points and report the path it returns, and a command remembered in the hash table under that path resolves through it again rather than through the filesystem. The resolver runs inside `DefenseInDepthBox.runTrustedAsync`, since it is host code that may read `process.env` or stat the host disk, and what it returns is registered the way a custom command is. The motivating embedder runs just-bash over the host's real directories and wants a program on the host's PATH to run as a real, separately sandboxed process under its own name, with `command -v` telling the truth about it; without a hook the choices are registering every name on PATH as a custom command before each call, or rewriting the AST.
>
> A second option, `registeredCommandPath(name)`, names the program a registered command runs (a wrapper around a real interpreter, say) or returns undefined for one that runs inside the shell, and also runs trusted. Setting it says the filesystem is a real disk, where `/usr/bin` holds real programs rather than stubs of the registered commands, so the stub conventions stop holding: a registered command resolves by name ahead of the hash table and PATH (a real `/usr/local/bin/ls` no longer shadows the builtin, and a real binary is never read as a script); `type`, `type -t`/`-p`, `command -v`/`-V` and `hash` describe it by the program it names or as a shell builtin, rather than at a `/usr/bin/<name>` the disk may hold something else at; a builtin is not put in the hash table, as bash does not hash one; the resolver is asked for a bare name before PATH, and an executable that PATH or the hash table finds is offered to it by its path before the shell reads it as a script. An embedder that sets neither option sees no change. Tests: `src/interpreter/external-command-resolver.test.ts`.

### Not yet offered: `ls -l` over a real disk

The `ls -l` part is ours too. The text to open its pull request with, against `main`:

> **ls: show a real file's mode, owner and times in a long listing.** `ls -l` printed `-rw-r--r--` or `drwxr-xr-x` whatever a file's mode, `user user` for every owner, and January 1 for `.` and `..`. It now formats the mode bits from the stat (setuid, setgid and sticky included), takes `.` and `..` from their own stat, lists a link whose target is gone by its own `lstat`, and prints the owner and group names a filesystem puts on a stat, falling back to `user user`. `FsStat` gains optional `owner` and `group`, which `ReadWriteFs` and `OverlayFs` fill for a real file: this process's account by its name (a directory service may hold it apart from `/etc/passwd`), any other id from `/etc/passwd` and `/etc/group`, read once, and an id neither names as its number; none on Windows. `InMemoryFs` fills neither, so a virtual listing keeps its `user user`. ### Not yet offered: a refused redirect fails its command

The refused writes part is ours too. The text to open its pull request with, against `main`, as a follow-up to #561 or in its place:

> **redirections: fail the command, not `exec()`, when the filesystem refuses a redirect target.** On the standard-fd paths (`>`, `>|`, `>>`, `2>`, `&>`, `&>>`, `>&file`, `exec >`) `openOutputEntry` rethrows whatever the filesystem throws, so on a read-only `OverlayFs`, or under any `IFileSystem` that refuses a path, `echo before; echo x > /ro/f; echo after` rejects the whole `bash.exec()`: `before` is lost though it ran, and `after` never runs. Bash prints `bash: /ro/f: Read-only file system`, sets `$?` to 1, and goes on. The catch now reads the errno off the error (`code`, or the `ECODE:` message prefix) and, for any errno `describeFsError`'s table knows, fails the redirect with bash's message; the table gains `EROFS` and `ENOSPC`. A `ControlFlowError` (an execution limit) and an error with no known errno behave as before, and `set -e` stops on the failed redirect, as in bash. `tee` prints the errno's message for a failed write rather than always `No such file or directory`. `process-substitution.readonly.test.ts` asserted the rejection; its cases now assert the failed command. #561 does the same for `ENOENT` and `ENOTDIR` and keeps `EROFS` rejecting `exec()`; this covers both. Tests: `src/interpreter/redirections.refused-target.test.ts`, and a case in `src/commands/tee/tee.test.ts`.

### Not yet offered: printf writes the bytes its escapes name

The printf bytes part is ours. The text to open its pull request with, against `main`:

> **printf: write the byte an escape names, not a Latin-1 character.** `processEscapes` and `%b` turn a byte that is not part of a UTF-8 character into the char with its value, and printf returns its output as text, so the pipe and redirect layers UTF-8 encode it: `printf '\x89' > f` writes `c2 89`, `printf '\303\251'` writes `c3 83 c2 a9` (bash writes `c3 a9`), and `printf '%c' é` writes `c3 83`. `printf.binary.test.ts` passes only because the output boundary decodes the doubled bytes back. Such a byte is now held as a lone low surrogate (U+DC80 + byte), which no text contains, and printf returns its output through `bytesOutput` when it holds one, with the text around each byte UTF-8 encoded; output without one is text as before. An octal escape keeps its low byte (`\777` is 0xff, as in bash). `-v` stores the bytes decoded by `decodeBytesToUtf8`. `processEscapes` takes the behavior as an opt-in third argument, so `find -printf` is unchanged. Tests: `src/commands/printf/printf.bytes.test.ts`.

### Not yet offered: `bash` and `sh` take bash's options, `--version`, and bash's syntax errors

The shell options part is ours: option parsing, `--version`, and syntax errors worded as bash words them, in one change. On `main` it applies as the 3.6.0 diff does, `bash.ts` having gained only `newShell` there, except that `bash.ts` imports `BASH_VERSION` from `shell-metadata.ts` rather than spelling it out (the 3.6.0 diff spells it out because the import moves that module into a new shared chunk the patch rebuild cannot map), and it adds a changeset. Title and body to open its pull request with, against `main`:

**fix(bash): read bash's options and --version, report syntax errors as bash**

> ## Problem
>
> ```sh
> bash -lc 'echo hi'                # bash: -lc: No such file or directory   (exit 127)
> bash -euo pipefail -c 'cmd'       # bash: -euo: No such file or directory  (exit 127)
> bash --version                    # bash: --version: No such file or directory (exit 127)
> printf 'echo ok\nif then\n' > t.sh
> bash t.sh                         # bash: syntax error: Parse error at 3:1: syntax error near unexpected token `fi'
> ```
>
> Bash gives `hi`, runs `cmd` under errexit and pipefail, prints its version, and reports ``t.sh: line 2: syntax error near unexpected token `then'``.
>
> Agent harnesses run nearly every command as `bash -lc '…'`, so a model reaches for that shape first and loses a turn learning that only `bash -c` works. A model that checks `bash --version` before using bash 4 syntax learns nothing. And the syntax error points at a token the script does not contain, on a line past its end, so a model fixing it edits the wrong line.
>
> ## Cause
>
> `bash.ts` takes `-c` only as `args[0]` and reads any other first word as a script path:
>
> ```ts
> if (args[0] === "-c" && args.length >= 2) {
> ```
>
> In the parser, `parseIf` never checks that the condition is non-empty, so in `if then` the `then` ends an empty condition, the body comes out empty at the end of the file, and the empty-body branch falls back to naming `fi`. `while do` and `until do` were accepted outright. `Parser.expect` words its failure as `Expected FI, got EOF`. And `Bash.exec` reports every `ParseException` as `bash: syntax error: Parse error at L:C: …`, whatever script it was reading.
>
> The existing tests could not see the option handling, since the Oils cases that invoke `$SH` with options are marked `## SKIP`, and the parse-error tests assert only that stderr contains `syntax error`.
>
> ## Fix
>
> Options are read as bash reads them: every word up to the first operand, `--` or `-` that starts with `-` or `+`, letters combined, `-c` a flag that makes the first operand the script (so `bash -c -e 'cmd'` works), `-s` reading the script from stdin with every operand a positional parameter. `-l`, `-i`, `--login`, `--noprofile`, `--norc` and `--noediting` are accepted and ignored, there being no profile files or terminal; `--rcfile`/`--init-file` take and ignore a value; `--posix` and `--verbose` map to `set`. `set`'s letters, `-o NAME` and `-O NAME` run as `set`/`shopt` commands prepended to the script's first line, so `$LINENO` still counts the script's own lines and `SHELLOPTS`/`$-` follow, and a name either refuses ends the shell with status 2 before the script runs. An unknown option, or `-c` with no script, is a usage error at status 2. `--help` and `--version` count only in option position, so `bash -c 'ls --help'` runs `ls`.
>
> `--version` prints bash's first line with just-bash where bash names the machine type, from `BASH_VERSION`, and a second line saying it is not GNU bash:
>
> ```
> GNU bash, version 5.1.0(1)-release (just-bash)
> This is just-bash, a bash interpreter written in TypeScript, not GNU bash.
> ```
>
> A syntax error reads `NAME: line N: syntax error …`: `bash: -c` for a command string, the script's path for a file, `bash` for stdin or a top-level `exec()`, the file for `source`, `bash: eval` for `eval`. `ExecOptions` and `CommandExecOptions` gain `scriptName` to carry the name into the nested `exec`. `if`, `elif`, `while` and `until` refuse an empty condition or body at the token that came instead, and `Parser.expect` words a failure as ``syntax error near unexpected token `X'`` or, at the end of the script, `syntax error: unexpected end of file`. A shebang line keeps its newline when it is stripped, so line numbers and `$LINENO` count it.
>
> ## Scope
>
> Unchanged: `ParseException.message` keeps its `Parse error at L:C:` form for callers that read it; the new `reason` field holds the bare message. Exit statuses are unchanged (2 for the shell, 1 for `source` and `eval`).
>
> Not addressed, deliberately:
>
> - Bash's second line quoting the offending source (``t.sh: line 2: `if then'``). Easy to add from the script text; say the word.
> - Bash runs the statements before a syntax error (`echo ok` prints first); just-bash parses the whole script before running any of it.
> - `BASH_VERSINFO` is unset, so `${BASH_VERSINFO[0]}` is empty and a script testing `(( BASH_VERSINFO[0] >= 4 ))` decides it is on an old bash. A small follow-up if wanted.
> - `$-` does not show `c`.
> - Empty bodies of `for`, `select`, `{ }` and `( )` are unchanged.
>
> ## Tests
>
> `src/commands/bash/bash.options.test.ts` covers the option forms (accepted, applied, refused at status 2), `-s`, script files, `--help`/`--version` in and out of option position, `--version` matching `$BASH_VERSION`, and the syntax error's name, line and token for `bash -n file`, `bash file`, `bash -c`, `sh -ec`, `bash < file`, `source`, and a file with a shebang. `src/syntax/parse-errors.test.ts` pins the token and line for ten scripts (empty `if`/`elif`/`while`/`until` conditions and bodies, a missing `fi` at the end of the file, a stray `}`). Two existing assertions on the old wording are updated (`unsupported-reserved-words.test.ts`, `eval.test.ts`), and eight Oils cases lose their `## SKIP`.
>
> The tokens and the file and `source` messages were compared against `/bin/bash` 3.2.57 on macOS. That bash numbers `-c` and `eval` lines one low (`line 1` for the second line of `-c`); the `-c` line numbers here follow bash 5, which was not run.
>
> `pnpm --filter just-bash test:run` after a build: 16372 passed, 5 failed, 98 skipped. The same 5 fail on `main` (16322 passed), verified by running `main` without this change, not inferred: four `tar` xz cases and `package-contents.test.ts`. `test:comparison` passes (1059), as do `pnpm lint` and `typecheck`.
>

## Known gaps with no fix in flight

Not workarounds, so they carry no removal trigger. They are here because each one is a way the sandbox can hand the agent a confident wrong answer, and knowing about them is cheaper than rediscovering them. Each was checked against 3.6.0.

- **`ln -s` does not work.** Symlink creation is off in the shell's filesystem (`allowSymlinks`), deliberately, so `ln -s a.txt b.link` exits 1 with `ln: failed to create symbolic link 'b.link': Operation not permitted`. On 3.4.1 the same refusal read as a hard link on a directory; #391 fixed the message in 3.6.0.
- **Symlink support depends on who is asking.** The shell's filesystem refuses to create one, so `cp -R` of a `node_modules` tree inside the chat's work folder refuses the whole tree up front with `EACCES: permission denied, cp '<link>' contains a symlink`, nothing copied. A real subprocess writes to the host directory directly and is not subject to that, so a Python script can create thousands of symlinks in the same folder where `cp -R` just failed. Nothing in the sandbox surfaces the difference.
- **A copy from one mount into another stopped at the first symlink.** Upstream's `MountableFs` copies a tree across mounts entry by entry and asks the destination to create each link, which every mount we build refuses with `EPERM: operation not permitted, symlink '<dest>'`: everything after the link was left uncopied, and the errno was the one the attached-folders prompt reserved for a macOS denial of the folder. That is the shape of every `cp -R` of a home-directory folder or a checked-out repository. Fixed upstream as #422 and carried locally meanwhile (see Local patches above): the copy finishes around every link and the command exits 1 with `cp: cannot copy '<folder>/Docs': copied all but 2 entries: <folder>/Docs/link.txt: EPERM: operation not permitted, symlink '/work/copy/link.txt'; ...`, every other file in place. The prompt's EPERM rule was narrowed to reads and listings at the same time, so the errno the destination still reports no longer matches it. This bullet goes with the patch.
- **`find -type l` and `cp -L` do not exist.** `find`'s type is `"f" | "d"` upstream, and `cp` has no dereference flag. Together they make a symlinked tree awkward to inspect or flatten, which is how the `cp -R` failure above usually gets discovered.
- **A custom command cannot tell an empty pipe from no pipe.** The command context carries `stdin` as bytes and nothing about where they came from, so `false | rg PATTERN` and a bare `rg PATTERN` arrive identically. Our `rg` is the real binary, which reads stdin when fd 0 is a pipe and walks the working directory otherwise, and the shim had to pick one from the bytes: it picked the walk, so a browser read that failed upstream of `rg` came back as 118 KB of the chat folder's own skill files presented as page text, twice in one production session. Patched locally as the `stdinConnected` part above; the same `stdin ? input : "ignore"` choice in the `ffmpeg`, `ffprobe`, `node`, `python`, and `uv` shims is harmless, since for a reader an empty pipe and `/dev/null` are the same EOF. Upstream's own `rg` had the same bug, reported and fixed in #401 before ours was opened; see the table above for how the two relate.
- **Pipelines are not streaming.** Each stage runs to completion and its whole stdout is buffered as a string, so `tar -cf - big | tar -xf -` trips `total output size exceeded` against `maxOutputSize` even though nothing was headed for the agent. The message names `executionLimits.maxOutputSize`, which reads as "your output is too large" rather than "an intermediate did not fit". The same design means a downstream stage can never end its producer: `rg -l pattern <home folder> | head -200` runs the search to the end of the tree, since `head` does not exist until `rg` has exited, and a promoted call streams every line of it into the live view and the process log regardless of the `head`. A bounded search is unbounded here, and the fix is an interpreter change (streaming stages with backpressure), not a command fix.
- **The error sanitizer hides the paths the agent works at.** `sanitizeErrorMessage` (`fs/sanitize-error` in the package, bundled into the script workers' chunks) is a regex that replaces any path starting `/Users`, `/home`, `/private`, `/var`, `/opt`, `/Library`, `/System`, `/usr`, `/etc`, `/tmp`, `/nix` or `/snap`, and any `C:\` path, with `<path>`; its host-error variant also takes `file://` addresses and more roots. It was written for an embedder whose filesystem is virtual and whose host layout must not leak. The agent here works at real paths, so an error that crosses it names `<path>` and the agent cannot tell which file a rule refused: a script worker (`sqlite3` is the one the shell registers) reports `EACCES: permission denied, ... '<path>' -- <path> is closed in Settings › Permissions`, with the reason intact and the file gone. The main-thread builtins print the path as it is. The workaround is the one in the table above: the shell collects the rules' refusals as they happen and appends them to stderr with the path spelled out, outside the sanitizer's reach. Errors that do not come from a rule (a missing file inside a worker) still arrive sanitized. What would let it go is an option to turn the sanitizer off for a filesystem whose paths are the agent's own. The regex also stops at the first space, since its character class excludes whitespace, so a path with one is only half replaced: `sqlite3` on a chat's `chat.db` under `Application Support` reports `readFileBuffer '<path> Support/Instrument/.../chat.db'`, the tail of the path left in. Matching inside quotes up to the closing quote would cover the common case, but that changes a security boundary, so it is noted here rather than patched. Reproduced on 3.6.0.
- **Host code reached from a builtin may not read the working directory.** The defense-in-depth box (`defenseInDepth`, on by default) swaps `process.cwd` for a proxy that throws `process.cwd is blocked during script execution`, with a message telling the reader to report a bug at security@vercel.com, for as long as a `bash.exec` runs. A command made with `defineCommand` is `trusted` and runs outside the box (`rg`, `du`, `git`, `app`), so the block lands on the builtins and on our own code reached through them: the rules the shell's filesystem asks of every read and write (`reachOf`, from `permissions/rules-fs.ts`). On macOS and Linux nothing notices, since resolving an absolute path reads nothing. On Windows resolving a path that names no drive (`/tmp`, which the path schema takes) has to read the working directory, so a single such path among a chat's rules failed every redirect, `cat` and `sqlite3` write-back in that chat, each reported as the command's own failure (`sqlite3: failed to write database: process.cwd is blocked during script execution`) and none of them naming a path. A layout therefore resolves its rules' paths before the shell starts (`workspace-fs-layout.ts`), and anything else our commands reach through a builtin has to be as careful. The hatch the message names, `defenseInDepth.excludeViolationTypes: ["process_chdir"]`, is not usable as it stands: the type covers `process.chdir` too, and the box is a process-wide singleton that throws when two `Bash` instances resolve different defense options, so every `new Bash` in the process would have to pass the same ones. Splitting the type, or leaving `process.cwd` alone for an embedder whose filesystem is the host's, is what would make it worth asking upstream for. Reproduced on 3.6.0; the guard is `create-bash-env-no-drive-rule.test.ts`.
- **Three text tools print GNU's answer in another shape.** `uniq -c` pads its count to four columns where GNU pads to seven; `sort` collates non-ASCII lines (`naïve`, `日本`) in an order that is neither GNU's `C` nor its `en_US.UTF-8`; and `jq`'s `@csv` quotes a string only when it holds a comma, quote, or newline, where jq quotes every string (deliberately, by the comment beside it). A script comparing output byte for byte, or a CSV consumer that expects quoted text, sees the difference.
- **A parse error fails the whole script.** An unsupported construct anywhere means no statement runs, and the message names the line and the token where parsing stopped, not the construct. Every command before it is silently skipped, where bash runs them before reporting the error.
- **`awk` cannot lex a `/` inside a bracket expression.** `awk '{if (n ~ /^[^/]*\.md$/) print}'` exits on `awk: Expected RPAREN, got RBRACKET`, because the lexer ends the regex literal at the `/` inside `[^/]` rather than at the closing delimiter. gawk accepts it, and `[^/]` is the ordinary way to write "one path segment", so this lands on a shape the model reaches for by default. `IGNORECASE` is unsupported too, which matters less only because it usually fails behind this. The cost is not the parse error itself but where it falls: `awk` is normally the last stage of a pipeline, so the whole search runs first and the error arrives after the expensive part, with nothing to show for it. Escaping as `[^\/]` parses. Reproduced on 3.6.0.
- **`date` and `ls -l` can disagree about a file's time.** Upstream, `date` defaults to UTC when `$TZ` is unset while `ls`'s formatter uses host-local components, so a correctly stored UTC instant can display as the previous day. Our env seeds `TZ` from the host zone (`create-bash-env.ts`), so the two agree here; the gap belongs to any embedder that leaves `TZ` unset. Found while fixing `touch`; reported on #364 rather than fixed, because the fix belongs in `ls` and would move every `ls -l` timestamp in the suite.
- **A compound command's byte output reaches its redirect as text.** Each statement's output is decoded to text where statements are joined (`executeStatement`, `executeScript`, and the group, subshell, loop and `if` accumulators), and the joined result carries no `stdoutKind`, so `{ cat b.bin; } > f` and `for …; do cat "$x"; done > all` write each byte that is not UTF-8 as the two bytes of its Latin-1 character. A simple command's redirect is exact. The fix is for the accumulators to keep bytes, encoding text chunks, and mark the result as bytes, with command substitution and the other text consumers decoding it themselves; that touches a dozen sites, so it is not carried.
- **`echo -e` writes a Latin-1 character for a byte escape.** `echo -e '\x89'` writes `c2 89`, the bug the printf bytes part fixes for `printf`; `echo` has its own escape parser.
- **`sqlite3` dot commands are a parse error.** Already covered as a prompt workaround above; noted here too because it is the one gap upstream has declined rather than deferred.
- **A handful of other coreutils are missing** with no equivalent: `zip`/`unzip`, `dd`, `xxd`, `realpath`, `shuf`, `openssl`, `rsync` (`yes` arrived in 3.6.0, finite since pipelines do not stream). Each appeared once in the production record, in a task probing the sandbox rather than doing work, and `od`, `strings`, `head -c`, `seq`, and the `zip` skill cover the ground between them. Listed so the next reader can weigh a request against the whole set rather than adding them one at a time.

## Checking whether a release has caught up

```bash
npm view just-bash version                       # what latest actually is
npm view just-bash time --json                   # when each version published, against minimumReleaseAge
pnpm why just-bash                               # what we resolve to
```

When the published version moves, walk the registers above and delete every row whose trigger has fired, including the prompt text, then drop those parts from `patches/just-bash-sources/sources.json` and rebuild the patch against the new tag. Removing a stale line from the `sqlite3` description matters as much as dropping a patch: a model told a working command is broken will route around it for as long as the sentence survives.

Verify against the installed build rather than the changelog. `packages/workspace/scripts/run-bash.ts` boots the same sandbox the agent gets, so a claim about behavior is one command away:

```bash
pnpm --filter @instrument-org/workspace run --silent script:run-bash -- "<command>"
```
