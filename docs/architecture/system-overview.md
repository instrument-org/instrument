# System overview

The top-level map of Instrument: the packages, how they layer, the processes at runtime, and how a chat's work flows through them. Start here, then follow the links into subsystem docs.

Instrument is an Electron desktop app. The user talks to it in **chats**. There is one agent, `instrument` ([`agents/instrument.ts`](../../packages/workspace/src/agents/instrument.ts)). A chat runs it with every tool: a shell, file tools, the web, skills, the user's **apps**, and an embedded browser it drives in tabs the chat holds. It does quick work itself, keeps **memory** about the user, and hands slow or multi-step work to **tasks** with `instrument task new --name '<title>' [--tab <id>]`. A task is the same agent carrying on in the background, as a child session of the chat: it reads the chat's conversation up to where it started as the start of its own history, works in the chat's work folder with the chat's folders at the same paths ([`lib/work-dir.ts`](../../packages/workspace/src/lib/work-dir.ts)), runs on the chat's model, and wakes the chat when it finishes.

## Chats, tasks, and the window

- **The app window** ([`windows/app-window.ts`](../../apps/studio/src/electron-main/windows/app-window.ts)) carries app-level tabs across its bar, each a TanStack router of its own kept mounted in one web contents ([`app-tabs.ts`](../../apps/studio/src/client/components/window/app-tabs.ts)). A tab holds a chat or the inbox, Apps, Files, a site, the browser, or a skill; its screens are the routes under [`client/routes/_app/`](../../apps/studio/src/client/routes/_app). Setup draws over it until it is done. See [`apps/studio/AGENTS.md`](../../apps/studio/AGENTS.md#windows).
- **A chat's tabs** (and a draft's, and the one page of a site at the window's level) are groups in one more model: `{ activeByGroup, tabs }`, changed only through the pure reducers in [`tab-model.ts`](../../apps/studio/src/client/components/window/tab-model.ts) and read through [`window-tabs.ts`](../../apps/studio/src/client/components/window/window-tabs.ts). The group on screen is never stored; it is whatever chat or site the window's tab up stands on. A chat's group, like its `/chats/<id>` address, is keyed by its chat id; every other group's key has a colon in it, which no chat id does. A page tab is a browser guest of the window's own; a screen tab is a route of the same tree under a router of its own ([`use-group-tab-routers.ts`](../../apps/studio/src/client/hooks/use-group-tab-routers.ts)), which a route component tells apart from a window tab only by `useGroupTab()`. Back and forward everywhere (the window's arrows and chords, a row's arrows, thumb buttons, a page's menu) walk one rule, `stepOf` in [`tab-steps.ts`](../../apps/studio/src/client/components/window/tab-steps.ts): the page's own history, then the screen's router, then the tab's visits across pages and screens, then, for a site, the window tab's history. Where an open lands is [`placement.ts`](../../apps/studio/src/client/components/window/placement.ts).
- **The inbox** (`/chats`) is the chat list beside an open chat, mail-shaped: one row per chat, opened in place ([`inbox-room.ts`](../../apps/studio/src/client/components/window/inbox-room.ts) decides when it steps aside for a narrow row).
- **Topics** are tags on chats, each a `TOPIC.md` under `Topics/<Name>/` with standing instructions ([`chat/topics.ts`](../../packages/workspace/src/lib/chat/topics.ts)). Every chat filed under a topic is read with its instructions and reaches the folders granted under it on this computer, which are kept in the machine folder's `permissions.json` under `topics` rather than in the file.
- **Apps** are the user's connected services: one folder per app under `Apps/<Name>/` at the workspace's top level, holding an `APP.md` whose YAML front matter is the manifest over its guide, never a secret ([`lib/apps/`](../../packages/workspace/src/lib/apps)). Credentials and OAuth state live in workspace stores in main ([`lib/apps.ts`](../../apps/studio/src/electron-main/lib/apps.ts)). The chat's agent authors and connects them in that folder; a task reaches them through the `app` command, and an app event can wake the chat. Several apps can be one service, like two Gmail accounts: the manifest's `service` names the directory entry they share (`catalogEntryForApp` finds it by slug or address when the manifest does not say), and each one's `account` tells them apart.
- **Chat wiring** ([`chat/attach.ts`](../../packages/workspace/src/lib/chat/attach.ts)) is attached once per workspace actor: it gives `instrument task` its route to the machine, wakes a chat when a child task finishes or an app event lands, and retitles a chat after its first exchange.

## Packages and layering

Dependencies point downward; nothing lower imports anything higher.

```
        studio (Electron app)
             |
        workspace (agents, tools, server)
             |
        ai-gateway (model proxy + model library)
             |
        shared (types, constants, utils)
```

- **`packages/shared`** — types, constants (e.g. `AI_GATEWAY_API_PATH`, `APP_NAME`), and utilities used everywhere.
- **`packages/ai-gateway`** — model access. A mounted Hono app that proxies provider API calls with injected credentials, plus a library for model discovery, identity, and image/web-search model construction. See [ai-gateway.md](ai-gateway.md).
- **`packages/workspace`** — the core: agents, tools, RPC, XState machines, and the workspace HTTP server. See [`packages/workspace/AGENTS.md`](../../packages/workspace/AGENTS.md).
- **`apps/studio`** — the Electron app (main process + React renderer) that hosts everything and is the product UI. See [`apps/studio/AGENTS.md`](../../apps/studio/AGENTS.md).

## Runtime topology

Two OS processes matter: Electron **main** and the **renderer**. Almost all server-side machinery runs in main; the renderer is UI only.

```
 renderer (React 19, TanStack Router)
    |  oRPC over MessageChannel
 main process (Electron)
    |-- Studio RPC routes + workspaceRouter
    |-- workspaceMachine (XState actor)
    |     `-- workspace HTTP server (Hono / @hono/node-server)
    |           |-- CDP bridge
    |           `-- ai-gateway app mounted at AI_GATEWAY_API_PATH
    |-- file channel (instrument://computer-<token>, the renderer's own read of any file on the computer)
    `-- browser view manager (embedded Chromium guests the agent and the person browse in)
```

- **Renderer ↔ main** is [oRPC](../../apps/studio/AGENTS.md) over a `MessageChannel`; the UI never calls remote services directly, only through main-process RPC. Main hosts Studio's own routes (`apps/studio/src/electron-main/rpc/routes/`) plus the workspace router (`workspaceRouter` from `@instrument-org/workspace/electron`).
- **How the UI learns of changes.** A `live.*` route reads once, then again after each burst of changes it subscribed to before that first read (`liveRead` in [`live-read.ts`](../../packages/workspace/src/rpc/live-read.ts)). For records, the change is `record.changed { id, kind }` ([`record-changes.ts`](../../packages/workspace/src/lib/record-changes.ts)), published where the change is made rather than by its caller: every write through a chat's records (`messages`, or `session` for a session record or setting), the state writer (`state`), the permission rules (`settings`), the session actor and the wake queue (`agent`), and trashing (`removed`, once the index has forgotten it). The chat list keeps its rows and reads again only the chats a batch of changes moved, plus every row when the apps change; a chat's tasks, each one's working and step, are `chats.live.tasks`. Transcripts batch the `messages` changes by the message each names (`changedMessageBatches`). The person's own folders (`Skills/`, `Memory/`, `Topics/`, `Apps/`, `Drafts/`) are watched while a view lists them (`watchFolder` in [`folder-watch.ts`](../../packages/workspace/src/lib/folder-watch.ts)): each folder and the ones in it with `fs.watch`, everything below by a read every few seconds, and a change is one only when a file's contents differ ([`folder-fingerprint.ts`](../../packages/workspace/src/lib/folder-fingerprint.ts)), so a save that leaves a file as it was tells no one. Studio main never holds the workspace's event bus: it hears through `appListChanges` and `sessionEnds` and tells through `appChanged`, which publishes `app.updated` and `app.event` together.
- **Boot** happens in [`create-workspace-actor.ts`](../../apps/studio/src/electron-main/lib/create-workspace-actor.ts): it runs the launch's sweeps over the workspace folder (`sweepWorkspaceFolder` in [`workspace-launch-sweeps.ts`](../../apps/studio/src/electron-main/lib/workspace-launch-sweeps.ts): `migrateWorkspaceLayout` for a workspace in the app's own data, then the record converters and the moves of the person's folders out of `.instrument/`), starts the bash worker every agent shell runs in, then starts `workspaceMachine`, injecting `aiGatewayApp`, the apps config, the browser manager, `getAIProviderConfigs`, the signed-in user, the on-disk model cache, the registry and system-skills directories, the workspace's index file (`workspaceDbFile`), the bundled `pnpm` and `uv` binary paths, this computer's folder (`userDataDir`) and the runtime folder in it (`runtimeDir`), the feature-flag getters, and the web-search client, and attaches the chat wiring (`attachChats`).
- **Workspace server** is a Hono app served in-process via `@hono/node-server` ([`server/index.ts`](../../packages/workspace/src/logic/server/index.ts)), and everything on it is for the agent: the CDP bridge `agent-browser` drives a guest through, and the ai-gateway app every in-process model call is pointed at. It serves no files: a page on the computer opens at its `file://` address for the agent as for the person ([in-app-browser.md](in-app-browser.md#a-file-on-the-computer-has-one-address-for-the-person-and-the-agent)). The port falls back to a free one, so multiple dev instances can coexist.
- **The file channel** is how the person's own viewers read a file: `instrument://computer-<token>/<host path>`, an app-scheme handler in main ([`computer-files.ts`](../../apps/studio/src/electron-main/lib/computer-files.ts)) that serves any file the app's user can read, by its real path, but a workspace's records (its `.instrument/` but the folders there that hold the person's own files: what they sent to a chat, their topics, skills, apps and memories) and the machine folder outside the workspaces kept in it ([`refused-files.ts`](../../apps/studio/src/electron-main/lib/refused-files.ts)); a file it refuses in the machine folder is answered 403, so the file tab can say so. The same rule holds the editors' `files.read` and `files.write`, and reaches Files through the workspace config (`isRefusedFile`): `listComputerFolder` answers such a folder as refused by the app and leaves such entries out of a listing. The channel is registered on the app's own session only, so no browser guest can name it, and the host carries a per-launch token the renderer learns over RPC, so a page the agent wrote cannot either.
- **Session and agent machines** (`packages/workspace/src/machines/`) drive an agent turn within a session, the chat's own or a task's (both run agent `instrument`); the workspace machine supervises them per chat and session.
- **Reach** of what the agent's tools can touch is decided by one set of rules, Settings › Permissions: the shell's own commands and the file tools apply them in process, and the programs the agent starts are held to them by the operating system on macOS (Seatbelt) and Linux (bubblewrap). The agent works at the disk's real paths. See [agent-sandbox.md](agent-sandbox.md).

## On-disk layout

Rooted at the workspace folder ([`get-workspace-folder`](../../apps/studio/src/electron-main/lib/get-workspace-folder.ts)), "your Instrument folder" in the app. The app runs only from a workspace the person chose: a first launch opens none, and setup's first step places it in the folder the person picks and starts it in the same process ([`place-workspace.ts`](../../apps/studio/src/electron-main/lib/place-workspace.ts)); `workspaces.json` then names it there. A folder that went missing, or can't be read, sends the launch back to that step, which says where it was so the person finds it or makes a new one. A workspace an earlier build kept in the app's own data (`<userData>/workspace`) stays there until the person moves it, from Settings › Storage or setup's folder step; the next launch moves its `.instrument/` there before anything opens it ([`workspace-move.ts`](../../apps/studio/src/electron-main/lib/workspace-move.ts)). Settings › Storage also opens another Instrument folder, with one restart. Once picked, the folder is also where finished work goes (`outputFolderPath`, `INSTRUMENT_OUTPUT`); until then that is `~/Instrument`, or the older `~/Documents/Instrument` on an install that already made one (`unchosenOutputFolder`), since macOS asks about Documents and nothing about the home folder. A folder somewhere no workspace can be (the home folder, the app's own files, or in or around another workspace: [`workspace-folder-check.ts`](../../apps/studio/src/electron-main/lib/workspace-folder-check.ts), which only warns of riskier places, such as Documents itself, a temporary folder, system folders, apps' data or a disk's top, where the person picks, and offers a new `Instrument` folder inside the home folder or Documents as the better choice) goes back to setup's folder step too. A folder made by a newer build is never opened: the launch says so in a window of its own, which offers to update ([`workspace-refusal.ts`](../../apps/studio/src/electron-main/lib/workspace-refusal.ts)). Its top level is the person's own; what the app keeps in it is in its `.instrument/`, laid out by `workspaceLayout` ([`workspace-layout.ts`](../../packages/workspace/src/lib/workspace-layout.ts)), so the app's part of a workspace travels as one folder:

- `.instrument/chats/<id>/`: one record folder per chat, and a chat is the only record: its id is a `ChatId` ([`schemas/chat-id.ts`](../../packages/workspace/src/schemas/chat-id.ts)) and its record folder a `ChatDir`, holding its logs and settings files with the `blobs/` they point at, a state file per device, `attachments/` (what the person sent, which the agent reads where it lies and never changes) and `handoff-notes.md` (the notes the agent keeps for when its context runs out, the one file there it writes). Nothing else is in it: the chat's work is apart from its records, on this computer (below). `record-folders.ts` indexes where each chat is: `resolveChat(id)` says whether an id is a chat's, and `chatDir` throws `NotFound` for one that is not rather than guessing a folder. The chat id is how the routes, the window and the agent name a chat; its session is internal to its store, read through `chats.session`, and an address written before (`/chats/ses_…`, in an older reply or a memory) is opened at its chat through `chats.ofSession`. The bash worker never reads the index; each command's exec message carries the chat main resolved.
- `.instrument/chats/<id>/settings.<device>.jsonl`: what one device set about the chat, a `set` line per change, newest winning per session and field across devices: each session's title, star, archive, unread and topic, and the chat's model on its own session ([`chat-records.md`](chat-records.md)). Nothing names the chat's own session: it is the one whose log header has no parent. Beside it, `state.<device>.json` is where one device left off in the chat, written and read by that device alone: the tabs its sessions hold, each naming the task session that drives it (none meaning the chat). The permission cards its agent is waiting on are records in the chat's own session's log instead, so every device shows them (`lib/chat/asks.ts`): a `card` record written whole by the computer the card belongs to, and an `answer` record any device appends, the first in log order winning, which that computer takes, grants and closes (`lib/chat/card-answers.ts`). The folders granted in a chat are this computer's, in the machine folder's `permissions.json` under `chats`, as the folders granted under a topic are under `topics`, and so is the name of the chat's own folder under `Chats/` (`chat-folders.json`). A `settings.json` there is from an earlier build, which the launch carries into those places and removes. Every JSON record the workspace keeps (the state files and a topic's settings) is written through [`json-record-file.ts`](../../packages/workspace/src/lib/json-record-file.ts): atomic, queued per path, unknown fields carried forward, and a file it cannot read refused rather than overwritten.
- `.instrument/chats/<id>/*.jsonl`: the chat's records, one append-only log per session per device (`<session>.<device>.jsonl`) and one settings file per device (`settings.<device>.jsonl`), with the bytes they point at in `blobs/`. Every read and write of a chat goes through them ([`chat-records.md`](chat-records.md)): reads through `ChatReads`, writes through `ChatWrites`, which waits for each append. The chat's own conversation is the session with no parent; a task is a session whose header names its `parent` and the `forkedAt` message it carries on from, with a per-chat `handle` (`t1`, `t2`, in creation order, never reused). A task's history is read, never copied: the parent's messages up to `forkedAt`, then its own. The chat's title, its own marks (starred, archived, unread), its topic and its model are settings, a `set` line per change. A `chat.db` beside them is a chat an earlier build wrote, which the converter turns into records at launch and then sets aside.
- `tasks/<id>/` at the top level: a task a 1.x build made, read only by the layout migration, which turns it into a chat of its own; the app never makes one, and a workspace in a folder the person picked has none. Legacy layouts are normalized on boot by `migrateWorkspaceLayout` ([`migrate-workspace-layout.ts`](../../packages/workspace/src/lib/migrate-workspace-layout.ts)), on a workspace in the app's own data only, which first moves the app's folders an earlier build kept at the top level into `.instrument/` (`move-app-folders.ts`), then renames a 2.0 beta's `task.db` to `chat.db`, writes a 1.x task's chat straight to `chat.db`, turns 1.x `projects/` into topics, and then splits each chat an earlier build kept with its work inside its folder (`split-chat-records.ts`): the records up out of its `.instrument/`, the work into its work folder, its virtualenv and `node_modules` dropped to be made again, keeping what it sets aside under `.instrument/.pre-chats/`. Each move is written into the files holding the paths it moved, once (`rewrite-stored-paths.ts`).
- `Topics/<Name>/TOPIC.md` at the top level: one folder per topic, named for it, its file plain YAML front matter over its instructions. A topic an earlier build kept in `.instrument/topics/<Name>/` as `.instrument/settings.json` and `instructions.md` comes out and becomes its `TOPIC.md` at launch (`topics-move.ts`), and the folders such a file listed are granted under the topic once, on a computer where an earlier build kept permission settings for the workspace; a computer opening it for the first time takes in none (`move-topic-folders.ts`).
- `Drafts/<date>/` at the top level: one folder per draft, named for the day the draft was started, holding `DRAFT.md` (plain YAML front matter over the person's own words) and every file or folder that goes with its message, pasted or dropped in. A draft is its `id`, never its folder name, so a folder renamed or moved in a file manager still holds its draft, and a folder holding two `DRAFT*.md` files is read as two drafts. A draft that opens a chat of its own and a reply waiting in a chat's box are both drafts, the reply naming its chat (`chat:`). The format and the folder are the workspace's ([`lib/drafts/`](../../packages/workspace/src/lib/drafts/)); the main process is their one writer while the app runs ([`draft-store.ts`](../../apps/studio/src/electron-main/drafts/draft-store.ts)): windows change them by sending ops, it watches the folder so an edit or a deletion in a file manager reaches every window, and it takes a draft away once it is sent or thrown away ([drafts.md](drafts.md)).
  Sending is crash-safe: the draft is pointed at its chat, the message is written naming the draft (`fromDraft` on its metadata), and the draft's folder is taken away last. The next launch finishes a send stopped partway through, or leaves a draft that can be sent again ([`lib/drafts/send.ts`](../../packages/workspace/src/lib/drafts/send.ts)), and brings out the drafts an earlier build kept in `.instrument/drafts/` ([`lib/drafts/migrate.ts`](../../packages/workspace/src/lib/drafts/migrate.ts)).
- `Apps/<Name>/APP.md` at the top level: one folder per app, named for it, its file plain YAML front matter (its `id`, which the credential store and the connection record are keyed by, and how the service is reached) over its guide, writable for the chat's agent only. An app an earlier build kept in `.instrument/apps/<slug>/` as `app.json` and `guide.md` comes out and becomes its `APP.md` at launch (`apps-move.ts`).
- `Memory/` at the workspace's top level — what the conversation's agent remembers about the user, one Markdown file per memory, written through its `instrument memory` command and read back into every chat ([memory plan](../plans/active/memory.md)). Readable and editable in a file manager; Settings lists them.
- `Skills/` at the workspace's top level: user-authored and imported skills, a folder per skill, writable for the agent, beside the other skill sources, which it reads in place. Skills an earlier build kept in `.instrument/skills/` come out at launch (`skills-move.ts`). Skills discovered elsewhere on the machine (co-installed agent homes like `~/.claude` and its peers, enumerated by `getSkillSources` in `packages/workspace/src/lib/skills.ts`) stay where they are.
- The bundled skills registry is **not** here: `registryDir` points at the `registry/` git submodule in development and at the app's `resources/` when packaged, read-only either way, with the bundled system skills (`systemSkillsDir`) beside it.
- `.instrument/` itself holds the rest of what the app keeps for the workspace: `workspace.json` (its id, name, color, and how far each migration has brought it) and `devices/<device>/`, what only that device writes and every device reads: its activity log and its file of each synced store, `bookmarks.jsonl` among them ([synced-stores.md](synced-stores.md)). The window's own browser tabs and file views are scoped under the id `window` (`WINDOW_ID`), which names no chat and has no record folder.
- What is this computer's own about the workspace is outside it, in `<userData>/machine/<local id>/`, named by the short id `workspaces.json` gives it on this computer: `keys/`, `browser/` (the app window's and the in-app browser's Chromium profiles, history, page pictures, each chat's `agent-browser` home), `window/` (the window's size, layout and view), `permissions.json`, `workspace.db` (the index of its chats, rebuilt from them, and the index of every device's activity log, which lives in the workspace's `.instrument/devices/<device>/activity/`; `workspace-db.ts`), `app-servers/`, and `work-folders.json`, the name of the workspace's folder for its chats' work.
- What the agent makes for the person is in their home folder, in `~/.instrument/work/<workspace>/<id>/`, each chat's work folder: the working folder its agent starts in, at its real path and shared by every task it starts, made by its first command, removed when the chat and its tasks come to rest with nothing in it (`reapWorkDir`), and made again, empty, by the next command, with nothing scaffolded into it: a `.venv` is made by the first `pip install`, and a `package.json` by `pnpm add` in the folder it runs in. `<workspace>` is the workspace's name as the person knows it (the folder they picked, or for one in the app's own data the name of that data folder, which tells copies of the app apart) with a short suffix, lowercase and hyphenated; it is settled the first time the workspace opens on a computer and recorded in the machine folder, so renaming or moving the workspace keeps it, and claimed by making the folder, so no two workspaces or copies of the app share one (`settleWorkFolders` in `apps/studio/src/electron-main/lib/work-folders.ts`). The agent starts in its own chat's work folder and may read and change every work folder in `~/.instrument/work/`, every other chat's and workspace's included; the rest of `~/.instrument` is closed to it.
- The two home-folder names above, `~/Instrument` and `~/.instrument/`, are the installed app's. Each build flavor has its own pair (`homeFoldersOf` in `packages/shared/src/constants.ts`): a dev run uses `~/Instrument Dev` and `~/.instrument-dev/`, and every preview shares `~/Instrument Preview` and `~/.instrument-preview/`. Only the installed app looks for the older `~/Documents/Instrument`. So a dev run or a preview never writes finished work or work folders into the installed app's, and never offers to open its workspace. No workspace may be in or around any flavor's data folder. The workspace's own `.instrument/` keeps that name in every flavor.
- The model cache and the runtime folder live under Electron's `userData`, not the workspace folder. The runtime folder (`<userData>/runtime/`, laid out by `runtimeLayout` in [`runtime-dir.ts`](../../packages/workspace/src/lib/runtime-dir.ts)) holds what the app can always rebuild, shared by every workspace on the computer: the `bin/` links on PATH, the managed Python (`python/`), the caches and config of the app's own uv, pnpm, npm and node-gyp as a chat's commands run them (`caches/`, `config/`) and as the app's builds of what every chat runs do (`build/`, which no chat reaches), the preload every chat's `node` imports (`preload/`), the bundled skills prepared at each launch (`skills/`), and the environments the app builds for skills' dependencies on their first use (`environments/`).

## Workspace instructions

An optional `AGENTS.md` at the workspace root supplies standing user instructions for every chat and task. Nested instruction files are not discovered. Each new message records a snapshot, limited by the same 20,000-character inline budget as topic instructions, with the full file's path when cut short; while the file has been missing or empty for the whole session, a message records none. Unchanged snapshots are rendered to the model once; edits and removal are announced on the next message without rewriting the cached session baseline. Forks inherit the recorded instructions, and a task's later messages capture their current contents. Topic instructions are more specific, and direct user requests take precedence. A missing or empty file adds no instructions; a read failure is reported internally and leaves the previous instructions in force.

## An agent turn, end to end

1. The renderer sends a message via oRPC to the main process, into the chat's record.
2. The workspace/session machine runs the chat's agent, which selects tools per agent ([`create-agent.ts`](../../packages/workspace/src/agents/create-agent.ts)). It does quick work in the turn itself, with tools executed against the chat's work folder. Slow or multi-step work it hands to a task with `instrument task new` ([`task/fork.ts`](../../packages/workspace/src/lib/capabilities/task/fork.ts)): a child session in the chat's records that carries on from the chat's conversation without copying it, runs the same agent in the chat's work folder, and is addressed by its handle (`t1`) in `instrument task send`, `instrument task stop`, `instrument task list` and `instrument task log`. What the chat writes to a task, its assignment and anything sent later, is stored as a `data-fromChat` part on a message with no text of the user's, so the record says which agent spoke ([`from-chat-model-text.ts`](../../packages/workspace/src/lib/from-chat-model-text.ts) is what the task's model reads for it). A message the user types while the chat's turn is mid-work joins that turn at its next step, marked as sent mid-turn ([`chat/mid-turn.ts`](../../packages/workspace/src/lib/chat/mid-turn.ts)): the turn folds it in, or answers it and hands its own work to a task with `instrument task new` when the message is about something else. Only a message that calls the work off ("stop") stops the turn where it is. When a task finishes, the chat wake ([`chat/wake.ts`](../../packages/workspace/src/lib/chat/wake.ts)) runs the chat again to report back.
3. Model calls go through the ai-gateway app (credentials injected there, never in the renderer): the user's own provider keys, plus a first-party provider config synthesized from their auth token when they are signed in, plus one per ChatGPT or Grok account signed in with its plan and one for a Claude account the bundled Claude Code is signed in to ([`get-ai-provider-configs.ts`](../../apps/studio/src/electron-main/lib/get-ai-provider-configs.ts)). Model metadata/selection uses the ai-gateway library.
4. Results are appended as message parts to their session's log and streamed back to the renderer over RPC. A part still arriving (streaming text, a call whose input is being typed, a preliminary output) is held in the turn's memory, which every read sees, and written once it settles.
5. Stopping walks the same chain in reverse: session → agent → the in-flight `executeToolCallMachine`, which writes its own "stopped by you" part before the agent finishes. Cancellation is owned by whichever machine holds the work, because leaving a state that invokes a child hard-stops that child before it can react. A model request is aborted through its own signal instead, and the agent waits for it to return, so the reply it held is written first; a request that ignores its abort is left behind after a few seconds' backstop. In `Finishing`, after `onFinish` has persisted what the turn produced, the agent sweeps any of the run's tool parts still in `input-*` (queued siblings, inputs an aborted stream saved, pending interactive calls) to `output-error`, so no call is left dangling in the record. A turn that ends with both queues drained and no stop skips the sweep, since nothing of it can be dangling. The agent says it is done only once every write the turn asked for has landed, so everything that hears the session end (the wake, the retitle, the chat's folder) reads all of it. A session that has to stop its agent outright, past the stop failsafe, writes what the turn still held in memory as cut off before it ends. A call the record still leaves without a result reaches the model answered as stopped. A process that dies mid-call reaches none of this, so the other sweep runs where a chat's records are first opened (`chat-records.ts`), before anything reads them: every `input-*` tool part in a session's newest assistant message belongs to a process that is gone, and a part snapshot marks it interrupted. The same sweep runs over a `chat.db` on its way through the converter (`interrupted-tool-calls.ts`).
